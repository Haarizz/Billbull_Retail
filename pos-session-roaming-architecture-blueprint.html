BillBull POS — User-Centric Session (Session Roaming) Architecture Blueprint

Status: Design document. No code written, no SQL scripts, no API implementations. This is the official blueprint for redesigning the BillBull POS module from a Terminal-Centric session model to a User-Centric ("Session Roaming") model.

Inputs to this design: pos-architecture-analysis.html (baseline domain audit), pos-session-user-centric-audit.html (session-lifecycle deep dive), pos-terminal-dependency-audit.html (exhaustive dependency sweep). Every design decision below is made with full knowledge of the existing implementation documented in those three passes; this document does not re-derive or re-justify facts already established there except where needed to explain a design choice.

Core principles this design is built to satisfy (given, not derived): User owns the Session. Session belongs to exactly one Branch. Terminal no longer owns the session — it only *hosts* whichever session is currently running on it. Counter is the physical billing location. Hardware always belongs to the Terminal and never follows the User. A session may move between Terminals but never across Branches. One user may have at most one active session per branch. One session runs on at most one terminal at a time. The terminal a session just left must become locked immediately. X-Report, Z-Report, and Day Close must keep working unchanged from the outside.

Chapter 1 — Design Goals

Why the architecture is changing

The existing model (fully documented in the prior audits) makes the Terminal the unit of session ownership: pos_terminals.current_open_session_id is the sole lock authority, every session lookup is terminal-first (findByBranchIdAndTerminalIdAndStatus), and the frontend's entire startup sequence is built around "register this device, then see what session it owns." A cashier's shift is, today, physically welded to whichever browser/device they first opened it on. Moving that cashier to a different till, replacing a faulty terminal mid-shift, or letting a supervisor hand a register to someone else all require either closing and reopening a session (losing shift continuity, splitting X/Z-Report data across two session rows) or working around the model entirely.

Current limitations (carried forward from the dependency audit, not re-derived here)

  • A session cannot survive a terminal swap without being closed and reopened.
  • The one-open-session-per-terminal invariant is enforced twice, redundantly, at the database level (uq_pos_session_terminal_open and uix_one_open_session_per_terminal), both keyed on the terminal, not the user.
  • Idle/hard-timeout auto-suspend leaves the terminal lock held, so a suspended session still blocks that terminal from being used by anyone else — even though nobody is actively using it.
  • Ownership reassignment (reassignSessionOwner, supervisorTakeover) already exists but is hard-restricted to "the same terminal" — the domain has never needed to move a session's terminal identity, so nothing in the codebase does it.
  • Checkout and reprint payloads carry sessionId, terminalId, and branchId as three independent, never-cross-validated fields.

Expected business benefits

  • A cashier can move from a slow or malfunctioning till to a working one without losing their shift, their running totals, or their audit trail.
  • A single register can be freed up the moment its current user suspends or steps away, instead of sitting locked for the rest of the shift.
  • Supervisors gain a real, first-class "move this cashier's session" operation instead of the current close-and-reopen workaround.
  • Reporting (X/Z/Day Close) becomes naturally cashier-centric rather than till-centric, which is closer to how the business actually reasons about a shift.
  • The redesign surfaces and formalizes a capability (device replacement, temporary terminals, remote recovery) that today requires manual database intervention or a lost shift.

Design philosophy

  1. Ownership moves, hosting stays. The User owns the Session. The Terminal hosts whichever Session is currently running on it. These are two different relationships, modeled as two different fields on two different sides — not one overloaded lock column.
  2. Nothing about Hardware changes. Per the given principles, hardware belongs to the Terminal, full stop. This resolves the one open question left dangling in the dependency audit (whether hardware should roam) — it does not, by design. This dramatically shrinks the blast radius: PosPrinter, PosCashDrawer, PosScanner, PosHardwareProfile, and HardwareProfileAssignmentEngine require no structural change.
  3. Every existing invariant that isn't explicitly named for removal is preserved. "One session per terminal at a time" survives, restated as a hosting constraint rather than an ownership constraint. "One session per user per branch" is new. Both can be enforced with the same kind of mechanism (atomic compare-and-swap plus a partial unique index) already proven in production by the current terminal-lock code — we are not introducing a new concurrency primitive, we are pointing the existing one at a different column.
  4. Reporting is decoupled from session-level terminal identity wherever it already is. The audits confirmed that individual invoices/checkouts already stamp their own point-in-time terminalId/counterName independent of the session. This means Terminal Summary and Counter Summary reporting can be built (or rebuilt) on a per-transaction basis rather than a per-session basis, sidestepping the entire "what if the session moved mid-day" problem for anything invoice-shaped.
  5. No big-bang cutover. Every phase in Chapter 14 is independently deployable and independently reversible. The old terminal-centric lock and the new user-centric lock run side by side for a full phase before the old one is ever removed.

Backward compatibility goals

  • Every existing API contract (POST /sessions/open, GET /sessions/active, POST /sessions/{id}/close, etc.) keeps working with its current request/response shape throughout the migration; new capabilities are additive endpoints, not breaking changes to existing ones.
  • Every existing report (X-Report, Z-Report, Day Close, Session History) continues to produce results indistinguishable from today for any branch that never uses transfer.
  • Any client (frontend build, or a third-party integration hitting these APIs) that has not been updated to be transfer-aware continues to function exactly as it does today — it will simply never see a session move, because it has no code path that initiates a transfer.
  • The two legacy DB-level partial unique indexes are not dropped until a phase dedicated to that removal, well after the new model is proven in production (Chapter 14).

Chapter 2 — New Domain Model

Each entity below states its responsibility and who owns it, per the given principles.

Branch

Unchanged. The top-level tenant-scoping entity. Owns nothing new in this redesign; remains the boundary that Sessions, Terminals, Counters, and Hardware are all scoped within, and — critically — the boundary a Session may never cross.

User (Cashier)

Responsibility: the human identity that owns a shift. Ownership: owns exactly zero-or-one *active* Session per Branch (defined precisely in Chapter 8). This redesign elevates User from "a string recorded on the session" (PosSession.openedBy) to "the entity the session's lifecycle is actually keyed on." The existing OwnershipContextHolder primitive — already carrying a real, JWT-derived, numeric userId through every request, already used elsewhere in the application, and confirmed by the dependency audit to be completely unused by POS today — becomes the canonical identity source for this relationship. This is the single most load-bearing decision in the domain model: it means the "user" side of the new architecture is not a new concept being bolted onto the app, it is an existing, already-battle-tested primitive being plugged into POS for the first time.

Session

Responsibility: the shift ledger — cash totals, sales totals, opening/closing balances, X/Z-Report data. Unchanged in that respect. Ownership: owned by exactly one User, scoped to exactly one Branch, for its entire lifetime. New responsibility: a Session now tracks which Terminal is *currently* hosting it, as a mutable pointer rather than a fixed-at-creation value. The session's own identity (its row, its id, its totals, its audit trail) is completely independent of which terminal happens to be hosting it at any given moment.

Terminal

Responsibility: represents a physical device/browser at a fixed Counter within a Branch, and is the anchor for Hardware. Ownership: owns nothing that used to be "session ownership." New responsibility: hosts at most one Session at a time (a *hosting* relationship, not an *ownership* relationship — the distinction is the entire point of this redesign) and owns its assigned Hardware Profile, exactly as today.

Counter

Responsibility: the physical billing location a Terminal is stationed at. Ownership: unchanged — a Counter is assigned to a Terminal (or several), never to a Session or a User directly. A Session's "current counter" is a derived value read through whichever Terminal is currently hosting it, not a fact the Session owns for itself. This is elaborated in Chapter 6.

Hardware Profile / Printer / Cash Drawer / Scanner

Responsibility: unchanged from today in every respect. Ownership: belongs to the Terminal, exclusively, permanently, by explicit design principle. A Session roaming from Terminal A to Terminal B does not take "its" printer with it — it starts using whatever printer Terminal B has. This is a deliberate business decision (hardware is nailed to the counter it sits on) and it is the reason the hardware layer requires zero structural changes in this redesign.

Reports (X-Report, Z-Report, Day Close, Session History)

Responsibility: unchanged in output shape. Ownership: X-Report is owned by the Session (as today — it is a snapshot of one shift's activity, regardless of how many terminals hosted that shift along the way). Z-Report/Day Close is owned by the Branch+Date, aggregating across all Sessions that were active that day (as today). Terminal Summary and Counter Summary reporting, where they need to attribute activity to a specific physical location, are owned by the transaction/history record, not the Session — see Chapter 9.

Cash Movements

Responsibility: unchanged — a cash drop-in/out event during a shift. Ownership: belongs to the Session (as today, via the posSession FK), performed by a User (strengthened from a raw string to a real identity, per Chapter 11). Cash movements are not terminal-owned in the new model any more than they were meaningfully terminal-owned in the old one — the only terminal-coupling that existed was the activity-tracking side effect, which is resolved naturally once the session's "current terminal" pointer is kept live (Chapter 4).

Invoices (Checkout)

Responsibility: unchanged — the system of record for a completed sale. Ownership: belongs to the Session that recorded it, but — as the dependency audit confirmed — each invoice already independently stamps its own point-in-time terminalId/counterName/branchId at the moment of checkout. This per-transaction stamping is untouched by this redesign and becomes the foundation for Terminal/Counter-level reporting under roaming (Chapter 9).

Held Sales / Draft Sales

Responsibility: parked carts. Ownership: belongs to the Session (the existing Layaway-based "hold" mechanism already filters by posSessionId, confirmed session-first in the dependency audit) — this redesign changes nothing about held-sale ownership, only removes the incidental terminal-coupling that existed purely as denormalized metadata on the hold payload.

Chapter 3 — Entity Relationships

Who owns Session? The User. A Session has exactly one owning userId for its entire life. This is a hard, unconditional fact — nothing in this design allows a Session to change owner except through the explicit, audited Supervisor Takeover / Reassignment operation (Chapter 4/7), and that operation is a deliberate ownership *transfer*, not a side effect of moving terminals.

Who owns Hardware? The Terminal. Unconditionally, per the given principle. This relationship is identical to today's and is not part of the migration surface at all — it is called out here only so the document is unambiguous that "session roaming" and "hardware roaming" are two different, unrelated concepts, and this redesign implements only the first.

Who owns Counter? The Terminal (a Terminal is assigned to a Counter; a Counter may have several Terminals pointed at it, unchanged from today). A Session does not own a Counter — it observes whichever Counter its current hosting Terminal happens to be assigned to. This is why Counter behavior needs its own chapter (Chapter 6): under roaming, "the session's counter" stops being a fixed fact and becomes a fact that changes when the hosting terminal changes, exactly as it should, since the counter is a physical place and the session is now free to move between physical places.

Who owns Reports? X-Reports are owned by the Session (one X-Report life-cycle per session, regardless of how many terminals hosted it). Z-Report/Day Close is owned by Branch+Date, unchanged. Terminal-level and Counter-level reporting is owned by the transaction/history layer (invoices' own stamped fields, plus the new Session-Terminal-History record introduced in this chapter's Session Transfer discussion and detailed in Chapter 9) — not by the Session itself, because a single session may have legitimately operated from more than one physical location in one shift.

Who owns Cash Movements? The Session, unchanged. A cash movement recorded while a session was hosted at Terminal A remains attributed to Terminal A at the moment it happened (via its own denormalized snapshot, following the same pattern invoices already use), even after the session later transfers to Terminal B.

Who owns Held Sales / Draft Sales? The Session, unchanged — this was already true before this redesign (the dependency audit confirmed the existing hold/recall filter is session-first, not terminal-first). Roaming makes this relationship *more* correct, not less: a cashier who transfers to a new terminal mid-shift can already, today, only recall holds tied to their own session id — under roaming, that continues to work identically regardless of which terminal is currently hosting the session.

Why this shape, specifically

The prior model conflated two relationships — "who is allowed to use this terminal right now" and "who owns this shift" — into one column (current_open_session_id) living on the Terminal. This redesign's central move is to split that into two explicit, independently-lifecycled relationships:

  • Ownership (Session.ownerUserId): who this shift belongs to. Set once at session creation. Changes only via an explicit, audited reassignment operation.
  • Hosting (Terminal.hostedSessionId / Session.currentTerminalPk): which physical device is currently displaying/operating this shift. Mutable, expected to change over the life of a session, and — this is the important part — changing it never touches ownership.

Everything else in this document follows from that one split.

Chapter 4 — Session Lifecycle

States (unchanged set)

The externally-visible PosSessionStatus set stays exactly OPEN, SUSPENDED, CLOSED — no new status value is introduced. This is a deliberate compatibility decision: X-Report, Z-Report, and every existing status-based query/report continues to filter on the same three values. Transfer is a same-status event (a session moves from OPEN-hosted-at-A to OPEN-hosted-at-B); it is never itself a status.

Full lifecycle

stateDiagram-v2 [*] --> Authenticated: Login (JWT, carries userId) Authenticated --> Resolving: Enter POS (terminal self-registers, independent of session) Resolving --> Resumed: Existing active session found FOR THIS USER, hosted on THIS terminal Resolving --> TransferPrompt: Existing active session found FOR THIS USER, hosted on ANOTHER terminal Resolving --> AutoClaimed: Existing SUSPENDED session found for this user (not hosted anywhere) Resolving --> NoSession: No active session found for this user in this branch NoSession --> Open: Create Session (unchanged validations: day not closed, no stale prior-day session) TransferPrompt --> Open: Transfer confirmed (Chapter 7) TransferPrompt --> NoSession: Transfer declined (cashier opens a fresh session instead — rare, supervisor-gated) AutoClaimed --> Open: silently re-hosted on this terminal, no interruption elsewhere Resumed --> Open Open --> Open: Sales, Cash Movements, Held Sales (unchanged) Open --> Suspended: Manual suspend, idle timeout, or hard-timeout (terminal is released — see below) Suspended --> Open: Resume (on ANY terminal — this is what "roaming while suspended" means) Open --> Transferring: Transfer initiated (Chapter 7) — short-lived internal guard, not an external status Transferring --> Open: Transfer completed (now hosted on new terminal) Transferring --> Open: Transfer failed/rolled back (still hosted on original terminal) Open --> Closed: Close Session Suspended --> Closed: Close Session (valid from Suspended too, unchanged) Closed --> [*]: Terminal released, X-Report auto-stamped if needed, Z-Report snapshot built Closed --> DayClosed: Day Close (branch+date aggregate, unchanged)

Key behavioral change: Suspend releases the terminal

Today, an idle/hard-timeout auto-suspend leaves pos_terminals.current_open_session_id set, so the terminal stays locked even though nobody is using it. Under the new model, suspend releases the hosting terminal (clears Terminal.hostedSessionId, terminal returns to ACTIVE/IDLE and is immediately available to host a different session). This is not an incidental side effect — it is the direct, intended consequence of splitting ownership from hosting: a suspended session still belongs to its User, but it is not *using* any terminal right now, so there is no reason for a terminal to sit locked on its behalf. This also means "resume" is now inherently roaming-capable — resuming a suspended session on any terminal is architecturally identical to a fresh transfer-in, not a special case.

Step-by-step

  1. Login — unchanged. JWT carries userId (via the existing OwnershipContextHolder pipeline).
  2. Terminal self-registration — unchanged mechanism, but its *purpose* narrows: it establishes hardware/heartbeat/print-target identity for this device. It is no longer, by itself, a gate on session resolution.
  3. Find Existing Session — a new, user-first resolution call: "does this user have an active (OPEN or SUSPENDED) session in this branch?" This replaces terminal-first lookup as the primary resolution path (Chapter 12 details the service responsible).
  4. Resume — three sub-cases, as shown in the diagram: already hosted here (silent), hosted elsewhere-and-OPEN (needs a Transfer confirmation, because interrupting a live till has consequences), or SUSPENDED-and-hosted-nowhere (silently re-hosted, since nothing active is being interrupted).
  5. Create Session — unchanged validations (business day not closed, no stale prior-day session — these remain branch-wide checks per the existing behavior, which the dependency audit already noted is naturally roaming-compatible). New: the duplicate-check is now user-first (findByOwnerUserIdAndBranchIdAndStatusIn(OPEN, SUSPENDED)) rather than terminal-first.
  6. Sales / Cash Movements / Held Sales — unchanged behaviorally; the only structural change is that any code path that used to reach for "the session's terminal" now reaches for "the session's *current* terminal," which is always accurate because Transfer keeps it live (Chapter 7).
  7. Suspend — releases the hosting terminal (see above).
  8. Transfer — detailed fully in Chapter 7; a same-status relocation of the hosting terminal while OPEN.
  9. Resume — from SUSPENDED, on any terminal, no different in mechanism from a fresh AutoClaim.
  10. Close — unchanged behavior: releases the hosting terminal, auto-stamps X-Report if needed, builds the immutable Z-Report snapshot, posts GL (still best-effort/non-blocking).
  11. Day Close — unchanged branch+date aggregate; unaffected by how many terminals any given session touched during the day (Chapter 9).

Chapter 6 — Counter Behavior

Counter ownership: unchanged — a Counter belongs to a Branch and is assigned to one or more Terminals. This redesign does not introduce Session-owned or User-owned counters.

Counter assignment: unchanged mechanism (assignCounter(terminalId, counterId)), still Terminal-scoped, still non-exclusive (multiple terminals may share a counter, exactly as today).

Counter after session transfer: the session's *current* counter becomes whatever counter its *current* hosting terminal is assigned to. This is now a live-derived value, read through the hosting relationship at query time (or refreshed onto the session row at the moment of transfer, for query convenience — an implementation detail for Chapter 11, not a design ambiguity), rather than the "snapshot taken once at session-open and never touched again" behavior that exists today.

Counter history: the new Session-Terminal-History record (introduced in Chapter 4/7) is also, transitively, a counter history — because each history segment records which terminal hosted the session, and a terminal's counter assignment at that moment is resolvable from that segment's timestamp range plus the terminal's assignment log (terminal-to-counter reassignment is rare and already audited via the terminal's own update timestamps). A session that worked Counter 1 for the morning and Counter 3 after lunch has that fact fully reconstructable after the day is over.

Counter in reports: reports that need "which counter did this activity happen at" (Cash Summary, Sales Summary, Counter Summary) should read the counter from the transaction-level stamp (invoices and cash movements already denormalize their own point-in-time terminal/counter identity, per Chapter 2/3) rather than from "the session's counter," because a single session may span multiple counters in one shift under roaming. The session-level counter field remains useful for *display* ("where is this cashier right now") but must not be treated as authoritative for historical attribution.

Counter snapshots: the existing pattern (denormalize onto the session at a point in time) is kept, but its *meaning* changes from "the counter for this session's entire life" to "the counter as of the last time this session's hosting terminal changed." This is the recommended approach.

Recommended approach and justification

Recommendation: keep Counter as a purely Terminal-owned, physical-location concept; never introduce a Session-Counter or User-Counter relationship. Represent "where is this session right now" as a derived/refreshed field on the session (for cheap reads), and represent "where has this session been" as an explicit, append-only history table keyed by (session, terminal, counter, start, end) rather than trying to infer it after the fact from terminal update logs.

Justification: a Counter is a fixed, physical thing — a numbered lane, a specific desk. It cannot roam, was never asked to roam by the given principles, and giving it any owner other than the Terminal it's bolted to would contradict the explicit "Hardware always belongs to the Terminal" principle by implication (since a counter is where the hardware sits). Making the session's counter a live/refreshed pointer rather than a one-time snapshot is the smallest change that makes the existing denormalization pattern correct under roaming, without inventing a new relationship type. The explicit history table is what makes reporting (Chapter 9) trustworthy without forcing every report query to reconstruct "where was this session at 2pm" from scattered audit logs.

Chapter 7 — Session Transfer

Overview

Transfer is the operation that moves an OPEN session's hosting terminal from A (source) to B (target) without changing its owner, its id, its totals, or its status. It is the one genuinely new capability in this architecture; everything else in this document exists to support it correctly.

Every scenario

  • Cashier logs into another terminal while their session is still actively OPEN elsewhere: the flow above — explicit Transfer Confirmation is required, because a live till at Terminal A may have an in-progress cart, an unresolved payment, or a customer standing at the counter. This is a deliberate friction point, not an oversight.
  • Existing session detected: handled by the Session Resolution Service (Chapter 12), which is consulted independently of terminal registration on every POS entry.
  • Transfer confirmation: a modal/screen the cashier must actively accept; declining leaves the session where it is and does not force a new session to be created (the cashier can go back to Terminal A, or a supervisor can intervene).
  • Current terminal (source) locking: happens as part of the same atomic transaction that attaches the session to the target — there is no window where the session is hosted "nowhere" or hosted on *both* terminals simultaneously (see Race-Condition Protection, Chapter 10).
  • New terminal activation: the target terminal's hostedSessionId is set in the same transaction; from the target's perspective, activation is instantaneous and indistinguishable from a normal session resume.
  • Failure recovery — transfer request fails mid-flight (network drop between confirm and server ack): the transfer transaction is atomic (Chapter 10) — either it fully committed (target hosts the session, source is LOCKED) or it fully rolled back (source still hosts it, target shows nothing happened). The client's job on reconnect is simply to re-run Session Resolution, which will report the true current state either way — there is no client-side state to reconcile.
  • Unexpected browser close (on the source terminal, mid-shift, no transfer initiated): not a transfer scenario at all — this is identical to today's idle-timeout path. The session auto-suspends after the idle window, which (per Chapter 4's new behavior) releases the terminal. No data is lost; the cashier resumes from anywhere.
  • Unexpected browser close (on the target terminal, mid-transfer, after confirmation but before the server responds): the transfer either completed server-side (in which case the session is now correctly hosted on the target and simply waiting for a browser to reconnect to it) or did not (in which case it's still on the source) — never both, never neither, by virtue of the transaction being atomic. Reconnecting anywhere re-runs Session Resolution and shows the true state.
  • Terminal crash (source terminal dies mid-shift, no clean disconnect): the session on it eventually auto-suspends via the existing idle/hard-timeout scheduler (unchanged mechanism), which releases the hosting terminal. The cashier (or a supervisor) can then resume/transfer the session onto a working terminal, with no special "crash recovery" code path needed — the existing timeout machinery already covers it.
  • Network interruption (during an active transfer): covered by the atomic-transaction guarantee above; from the client's perspective this is indistinguishable from "browser closed mid-transfer."
  • Session timeout during a pending transfer confirmation (cashier has the confirmation dialog open but doesn't act in time): the underlying session may auto-suspend on the source in the background; when the cashier does eventually confirm, the transfer service re-verifies current state (the "re-verify" step in the sequence diagram) and — since a SUSPENDED session isn't hosted anywhere — this degrades gracefully into an AutoClaim rather than a true transfer, with no error shown to the user.
  • Supervisor takeover interacting with transfer: takeover (reassigning ownerUserId) and transfer (reassigning hosting terminal) are orthogonal operations that can be composed — a supervisor can take over a session (become its new owner) and, in the same or a following action, transfer it to a different terminal. Neither operation is a special case of the other; both go through their own audited, atomic paths.

Chapter 8 — Business Rules

  1. One active session per user, per branch. "Active" means OPEN or SUSPENDED (not CLOSED). Enforced atomically, the same way the current one-per-terminal rule is enforced today (Chapter 10). *Why*: this is the direct restatement of the given principle, and mirrors the concurrency-safety pattern already proven in production for the terminal-based version of this same rule.
  2. A user may hold active sessions in more than one branch simultaneously. Not prohibited by any given principle ("Session may NOT move across Branches" governs a single session's movement, not a user's total session count across branches) — a multi-branch user opening a shift in Branch A and, separately, one in Branch B is two independent sessions, each obeying rule 1 within its own branch. *Why*: nothing in the given principles forbids this, and forbidding it would be a new restriction this redesign has no mandate to introduce.
  3. A session belongs to exactly one branch for its entire life and can never move to a different branch. Transfer is terminal-to-terminal *within* the same branch only; a target terminal registered under a different branch is not a valid transfer target and the operation is rejected outright, before any confirmation is even shown.
  4. A session can be hosted on at most one terminal at a time. Restated, not removed, from today's "one open session per terminal" — the direction of the relationship flips (terminal no longer *owns*, but a session still cannot be simultaneously live on two screens), enforced by the same style of atomic compare-and-swap as before, now applied to the hosting pointer rather than the ownership pointer.
  5. Transferring a session locks its previous terminal immediately, unconditionally, as part of the same atomic operation. No transfer can complete while leaving the source terminal in any state other than LOCKED.
  6. A LOCKED terminal cannot host a new or resumed session until explicitly unlocked (self-service acknowledgment or supervisor override), even if the user standing in front of it is a different cashier entirely.
  7. Session ownership changes only via explicit reassignment (Supervisor Takeover / shift handover), never as a side effect of a transfer. Moving terminals never changes who the session belongs to.
  8. Suspend releases the hosting terminal. A suspended session holds no terminal lock; resuming it (on any terminal) is architecturally identical to a fresh AutoClaim.
  9. Held Sales / Draft Sales remain session-owned, recallable regardless of which terminal currently hosts the session, unchanged from today's already-correct behavior.
  10. Checkout requires a valid, currently-OPEN session whose current hosting terminal matches the terminal the checkout request actually originates from — this closes the "three uncorrelated fields" gap the dependency audit flagged, by making terminal/session agreement a server-side validation rather than an unchecked assumption (Chapter 10).
  11. Printing always targets the requesting terminal's own hardware, never anything associated with the session's owner or the session's prior hosting terminals — a direct consequence of "hardware never follows the user."
  12. Cash movements remain session-owned, and their point-in-time terminal/counter attribution is a snapshot taken at the moment of the movement, not a live-follow of wherever the session is hosted now — consistent with how invoices already behave.
  13. X-Report is generated per session and reflects the session's full life, regardless of how many terminals hosted it — no change to when or how it is triggered.
  14. Z-Report / Day Close eligibility is redefined from "every terminal has reported" to "every active/closed session for the branch+date has reported" — since a terminal may have hosted zero, one, or several sessions across the day under roaming, the terminal-count framing no longer maps cleanly to a completeness check; the session-count framing does (Chapter 9).
  15. Day Close's business-day-advance and reconciliation math are unchanged — they already operate at branch+date granularity and were already confirmed roaming-agnostic.
  16. A transfer requires the transferring user to be the session's current owner (or a supervisor acting on their behalf) — a cashier cannot transfer someone else's session without a supervisor-authorized takeover first.

Chapter 10 — Security

User authentication: unchanged — JWT-based, app-wide login, no POS-specific credential. The redesign's dependency is on the JWT's userId claim being reliably present and already flowing into OwnershipContextHolder on every request, which the dependency audit confirmed is already true today.

Terminal validation: unchanged status-gate checks (BLOCKED/MAINTENANCE/DECOMMISSIONED/ARCHIVED reject registration; the new LOCKED status joins this family and additionally blocks *hosting* — a LOCKED terminal can still heartbeat and still exists, it simply cannot host a session until unlocked).

Branch validation: unchanged mechanism (BranchAccessService/BranchContextHolder, JWT + X-Branch-Id header resolution), and it gains one new hard rule: a transfer's target terminal must resolve to the *same* branchId as the session being transferred, checked before any confirmation UI is even shown, and re-checked server-side as a non-negotiable precondition (Rule 3, Chapter 8).

Session ownership validation: strengthened. Today, ownership is checked by comparing currentUser() (a string) against PosSession.openedBy (a string). Under the new model, ownership is validated against the numeric ownerUserId FK, sourced from OwnershipContextHolder.currentUserId() — a stronger, tamper-resistant comparison than a username string match, and the same primitive already trusted elsewhere in the application for ownership-restricted records.

Supervisor takeover: unchanged mechanism (BCrypt-verified PosSettings.supervisorPin, or the credential-based supervisor-auth alternative) — this redesign does not alter *how* a supervisor proves themselves, only clarifies that takeover changes ownerUserId while transfer changes hostedSessionId/current-terminal, and the two are independently authorized (a supervisor takeover does not implicitly authorize a transfer, and vice versa).

Session transfer authorization: new. A transfer may be initiated by (a) the session's current owner, authenticated normally, with no additional PIN/credential required for a same-user transfer (this is just "I am moving my own shift," not a privilege escalation), or (b) a supervisor acting on another user's session, which does require the same supervisor authorization already used for takeover — a cashier cannot transfer a session they don't own without supervisor sign-off, closing off "steal someone else's shift by transferring it to my terminal" as an attack.

Audit logging: every transfer writes: an audit-log entry on the source terminal (action: session left), an audit-log entry on the target terminal (action: session arrived), and a dedicated Session Transfer Log row (from-terminal, to-terminal, session, initiating user, timestamp, whether supervisor-authorized). Lock and unlock events are audited identically.

Race-condition protection: the transfer operation is a single atomic database transaction (Chapter 7's sequence diagram) guarded the same way today's session-open lock is guarded — an atomic compare-and-swap that can only succeed if the session is still, at the instant of the swap, OPEN and still hosted on the claimed source terminal. Two concurrent transfer attempts for the same session (e.g., a cashier double-clicking "confirm," or confirming on two devices) resolve with exactly one winner; the loser receives a clean "already moved" response and re-runs Session Resolution rather than erroring destructively. This mirrors, rather than reinvents, the concurrency pattern already proven by the existing terminal-lock CAS mechanism.

Concurrent login protection: unchanged in spirit — "one active session per user per branch" (Rule 1) is itself the concurrent-login guard. A user who is somehow authenticated on two devices at once and tries to open a *second* session in the same branch is rejected by the same duplicate-check that exists today, just re-keyed to the user instead of the terminal; their only path forward on the second device is to either resume/transfer their existing session or have a supervisor intervene.

Chapter 11 — Database Strategy

*(Design-level only — no SQL.)*

Entities that change

  • PosSession: gains a canonical, non-nullable owner reference (ownerUserId, a real foreign key to the user table) alongside the existing openedBy display string, which is retained during migration for backward-compatible reads and eventually becomes a pure display/audit field. Gains a live-refreshed "current terminal/counter" pair (reusing the existing terminalPk/terminalId/counterId/counterName columns, but changing their update discipline from write-once-at-open to updated-on-transfer). The existing PosCashMovement.performedBy string gains an equivalent performedByUserId FK for the same reason.
  • PosTerminal: the existing current_open_session_id column is repurposed in meaning (hosting, not owning) rather than replaced — this is a deliberate reuse to minimize schema churn, since its atomic CAS access pattern is exactly what the hosting relationship needs. Gains the new LOCKED status value in its existing status enum, plus supporting fields for *why* and *when* it was locked and *which* session it was hosting at the moment it was (for the unlock-acknowledgment screen and for audit).

New entities

  • Session-Terminal-History: an append-only log of hosting segments (session, terminal, counter-at-the-time, started-at, ended-at). This is the entity that makes Counter/Terminal history (Chapter 6) and any future "where was this session at time T" question answerable without inference.
  • Session Transfer Log: a purpose-built audit record for transfer events specifically (distinct from, and complementary to, the general PosAuditLog), optimized for building a fast "transfer history" view without scanning the general audit trail.

Entities that remain unchanged

Everything in the hardware layer (PosPrinter, PosCashDrawer, PosScanner, PosHardwareProfile, PosHardwareProfileDevice), PosCounter, PosDayClose, PosXReportSnapshot, PosReportSequence, PosSettings, PosHeldSale, PosLayaway and its payments, PosAuditLog (structurally — it already has every column this redesign needs), and every hardware-adjacent scheduled-job table. This is the majority of the POS schema by table count, confirmed unaffected by the dependency audit's classification of the hardware layer as exclusively Terminal-scoped.

New relationships

Session.ownerUserId → users.id (new, real FK, replacing the informal string-match relationship). Session ↔ Terminal becomes explicitly a *current-hosting* relationship rather than an ownership relationship, even though it may reuse the same physical columns. Session-Terminal-History introduces the first explicit temporal relationship in the POS schema — a session's location becomes a *timeline*, not a single fact.

New ownership model

Ownership (User → Session) and hosting (Terminal → Session) become two independently-updatable relationships instead of one overloaded one. This is the schema-level expression of the design philosophy stated in Chapter 3.

Migration philosophy

Additive first, cutover second, cleanup last — never destructive in the same phase that introduces something new. Every new column is nullable/backfillable and every new table is populated going forward without requiring a backfill of historical data (history before the migration simply has no transfer records, which is correct — those sessions never transferred). The two existing legacy DB-level partial unique indexes are left in place, unmodified, until a session's ownership-based locking has been proven correct in production for a full phase (Chapter 14) — they continue enforcing "one open session per terminal" as a *hosting* constraint, which remains true and desirable even under the new model (Rule 4, Chapter 8), so in practice they may never need to be dropped at all, only reinterpreted.

Backward compatibility strategy

The existing openedBy string column and the existing terminal-CAS lock mechanism keep functioning throughout the migration — new code paths are added alongside them, not in place of them, until the new user-first paths are proven (Chapter 14). Any report, integration, or client that only ever reads the old columns continues to see correct, meaningful data at every phase.

Future cleanup strategy

Once every client is confirmed migrated to user-first session resolution (verified by the phase-gating in Chapter 14, not by a deadline), the openedBy/performedBy string columns can be demoted to pure audit-display fields (never read for logic), and the DB-level terminal-string-keyed unique index (uq_pos_session_terminal_open, the older of the two redundant indexes) can be retired in favor of relying solely on the numeric terminal_pk-keyed one, removing the last piece of duplicated enforcement. None of this cleanup is a precondition for shipping the new model — it is deliberately deferred to keep every migration phase small and reversible.

Chapter 12 — Backend Strategy

*(Design-level only — no code.)*

New services

  • Session Resolution Service: the new primary entry point for "what session, if any, is active for this user in this branch, and where is it currently hosted." Replaces terminal-first lookup as the first thing the POS frontend consults on entry. Returns one of: hosted-here, hosted-elsewhere (triggers Transfer Confirmation), suspended-and-unhosted (triggers AutoClaim), or none (triggers Create Session) — exactly the branches in Chapter 4's state diagram.
  • Session Transfer Service: owns the atomic detach/attach/history/audit transaction described in Chapter 7. This is a genuinely new capability with no analog in the existing codebase (the existing reassignSessionOwner/supervisorTakeover change *owner*, not *host* — the new service changes *host*, and is explicitly designed to compose with, not replace, those existing operations).
  • Terminal Lock/Unlock Service: owns the LOCKED state transition and its acknowledgment/override paths, including the "your session moved" notice delivered to the source terminal.

Existing services — responsibility changes

  • PosSessionService: its openSession/getActiveSession duplicate-check and lookup logic is re-keyed from terminal-first to user-first (delegating the actual "where is my session" question to the new Resolution Service), while closeSession, suspendSession, cash-movement handling, and report generation keep their existing responsibilities, adjusted only to read the session's *current* hosting terminal instead of a fixed one.
  • PosTerminalService: unchanged responsibility for registration/heartbeat/approve/reject/archive/decommission; gains awareness of the new LOCKED status in its existing status-transition validation, and its archive/decommission guard is updated per Chapter 5's table.
  • PosTerminalActivityService: its six existing call sites (Chapter 5 of the dependency audit) continue to record activity against "the terminal a request actually came from," which — once the session's current-terminal pointer is kept live by the Transfer Service — is now always the terminal the caller is genuinely operating on, resolving the staleness risk the dependency audit flagged.
  • HardwareProfileAssignmentEngine, printer/scanner/drawer services: entirely unchanged — no new responsibility, no new coupling to session or user.
  • PosSessionScheduler: unchanged trigger logic (idle/hard-timeout), but its suspend action now also releases the hosting terminal (Chapter 4), which is a one-line-of-responsibility addition to an otherwise-unchanged job.

API philosophy

New capabilities are added as new endpoints (session resolution, transfer, lock-acknowledgment) rather than by overloading existing ones. Every existing endpoint's request/response contract is preserved exactly; where an existing endpoint's *internal* resolution logic changes (e.g., GET /sessions/active becoming user-aware rather than purely terminal-scoped), its external behavior for any caller who hasn't started using the new user-first flow remains identical to today, because a terminal that has only ever hosted one user's session behaves indistinguishably under either model.

Validation strategy

Validation gains one new class of check that didn't need to exist before: cross-field agreement. Where checkout/reprint today accept sessionId/terminalId/branchId as three independent, uncorrelated fields (a gap the dependency audit explicitly flagged as High risk), the new backend strategy requires that the terminal identified in a request actually be the session's *current* hosting terminal before honoring session-mutating operations — closing the exact gap identified.

Session resolution strategy

User-first, always. Terminal registration and session resolution become two independent, parallel operations on POS entry rather than a sequential dependency (today's registerTerminalAndResumeSession conflates them; the new startup flow, Chapter 13, runs them side by side). Terminal registration answers "what hardware do I have here." Session resolution answers "what shift am I running, and where."

Transfer strategy

Optimistic-confirm, pessimistic-commit: the frontend shows a transfer confirmation based on a read-only resolution result (optimistic, cheap, no lock held), but the actual transfer transaction re-verifies and atomically commits under a lock (pessimistic, correctness-critical) — never the reverse. This avoids holding any lock during the "cashier is looking at a confirmation dialog" window, which could otherwise be arbitrarily long.

Chapter 13 — Frontend Strategy

Startup flow: unchanged shape at the top level (login → enter POS → initialize), but internally reordered: terminal registration and session resolution now happen as two independent calls rather than one gating the other. Terminal registration failures (blocked/archived/etc.) still hard-stop the UI, exactly as today, since a terminal that can't be used is a hardware problem, not a session problem. Session resolution failures/results now drive a new decision tree (Chapter 4's diagram) instead of the old "resume-if-mine, 409-if-someone-else's" binary.

POS initialization: everything not related to session/terminal identity (departments, customers, products, printer/scanner config, held sales) is unaffected and continues exactly as today, since none of it was ever coupled to terminal-owns-session in the first place (confirmed by the dependency audit).

Resume session flow: three visually distinct outcomes instead of today's one: (1) silent resume (session already hosted here — no UI change from today), (2) silent AutoClaim (suspended session found, nothing interrupted, brief "resumed your session" toast at most), (3) Transfer Confirmation (session found hosted elsewhere and still OPEN — a modal, not a toast, since it has real consequences for whatever is happening at the other terminal).

Transfer popup: presents the source terminal's identity/counter (so the cashier can confirm this is really their own shift and not a mistaken match), a single confirm/decline action, and — for a supervisor-initiated transfer of someone else's session — the existing supervisor-auth challenge reused verbatim from the takeover flow.

Session locked screen: shown on the *source* terminal once it receives (via its existing heartbeat cadence — no new polling channel required, the heartbeat response simply gains a "you are now LOCKED, here's why" field) notice that its hosted session was transferred away. Presents a clear explanation ("This session moved to Terminal B, opened by you") and a single acknowledgment action that unlocks the terminal for its next use.

Recovery flow: on any unexpected reload/reconnect (browser crash, network drop, terminal crash-and-restart), the frontend's only required recovery action is to re-run Session Resolution — because the backend transaction guarantees (Chapter 7/10) mean there is never an ambiguous server-side state to reconcile, only a possibly-stale client that needs to ask again.

Failure handling: transfer confirmation failures (409 "already moved," "already closed," "no longer yours") are treated uniformly as "re-run resolution and show whatever it says now" rather than as distinct error states requiring bespoke handling — this keeps the frontend's error-handling surface small despite the new capability.

State management philosophy: unchanged at the architectural level — the existing local-component-state approach (no Redux/Zustand/dedicated context, per the dependency audit's finding) is preserved; the new session-resolution result simply becomes one more piece of state POSSales.jsx (or its eventual successor) owns, following the exact same pattern currentSession/currentTerminal already follow today. This redesign does not mandate a state-management-library migration as a precondition — that would be scope creep beyond what session roaming requires.

Chapter 14 — Migration Strategy

Each phase is independently deployable and independently rollback-safe: a phase can be deployed and, if a problem surfaces, the *previous* phase's behavior can be restored without data loss, because every phase is additive until explicitly stated otherwise.

Phase 1 — Foundation. Purely additive schema changes: the new ownerUserId FK (nullable at first, backfilled from openedBy via the existing username→user lookup already used for resolveDisplayName), the new Session-Terminal-History and Session Transfer Log tables (written to going forward, read by nothing yet). No behavior changes anywhere. Rollback: drop the new columns/tables; nothing depended on them yet.

Phase 2 — Parallel resolution. The new Session Resolution Service is deployed but runs in shadow mode — it computes its user-first answer on every request and logs it alongside the legacy terminal-first answer, without either the frontend or any other backend code consuming its output yet. This phase exists purely to build confidence that the new resolution logic agrees with the old one in every case where they *should* agree (i.e., every session that has never transferred). Rollback: stop calling the shadow service; zero user-facing impact either way, since it was never consumed.

Phase 3 — Transfer capability. The Session Transfer Service, the LOCKED terminal status, and the Transfer Confirmation/Locked-screen UI are shipped, but gated behind a feature flag defaulting off. Enabled first for a single pilot branch. This is the first phase where the new capability is actually usable, and it is the phase most worth rollback-testing explicitly before wider rollout. Rollback: disable the flag; terminals never enter LOCKED because transfers are never initiated, and the system behaves exactly as it did in Phase 2.

Phase 4 — Cutover. The frontend's startup flow switches its primary resolution path from terminal-first to the (by now proven) user-first Session Resolution Service, across all branches. The "suspend releases the terminal" behavior change (Chapter 4) ships in this phase, since it only matters once user-first resolution is live everywhere. Rollback: revert the frontend to terminal-first resolution (Phase 2/3's code paths remain in place and functional, since nothing from Phase 1-3 was removed) — this is the primary reason every earlier phase was additive rather than replacing anything.

Phase 5 — Reporting alignment. Z-Report eligibility and Terminal/Counter Summary reports are updated to their new session-based / per-transaction bases (Chapter 9). Deployed after Phase 4 has been stable, since these reports are the ones most likely to surface subtle discrepancies if the underlying resolution logic had any edge case. Rollback: revert report queries to their prior terminal-based logic — safe, since the underlying data (invoices' own stamped fields, the new history table) has been accumulating since Phase 1 regardless of which report logic is active.

Phase 6 — Cleanup (optional, deferred, no fixed deadline). Only after a full operational cycle (at minimum, several complete Day-Close cycles) with zero rollback events, the legacy string-based ownership fields are demoted to display-only and the older of the two redundant DB unique indexes may be retired. This phase is explicitly optional — the system is fully correct and fully supported indefinitely without ever executing it, per the Database Strategy chapter's cleanup philosophy.

Not breaking existing customers: at every phase boundary, a branch/tenant that has not opted into the new flag (Phase 3+) continues to experience the terminal-centric model exactly as it exists today — session roaming is never forced on a tenant, only made available.

Chapter 15 — Risks

Business risks

  • Cashier confusion during the transition if Transfer Confirmation and Locked-screen UX aren't clearly explained/trained before Phase 3-4 rollout. *Mitigation*: pilot-branch rollout (Phase 3) specifically to surface UX gaps before wide release, plus the deliberate choice to make Transfer an explicit, confirmed action rather than a silent one.
  • Perceived loss of terminal accountability ("who used this till today" becoming less obvious once sessions roam). *Mitigation*: the Session-Terminal-History table exists specifically to answer this question better than today's system can, not worse.

Technical risks

  • The openedBy/performedBy string-to-FK backfill (Phase 1) matching incorrectly for any historical username that doesn't cleanly resolve to a current user record (renamed/deactivated users). *Mitigation*: the FK is nullable and additive; any row that fails to backfill cleanly simply keeps functioning off the legacy string field until manually reconciled — it is never a blocking condition.
  • Session Resolution Service and legacy terminal-first lookup disagreeing in some untested edge case. *Mitigation*: this is exactly what Phase 2's shadow mode exists to catch before Phase 4 makes the new path load-bearing.

Migration risks

  • Phase 4 cutover exposing a resolution-service bug at full scale that Phase 2/3's smaller-scale validation didn't catch. *Mitigation*: Phase 4 is explicitly the highest-scrutiny phase in the plan and the rollback path (revert frontend to terminal-first) is kept intact and functional through Phase 5, not removed early.
  • Feature-flag sprawl if Phase 3's pilot-branch flag lingers too long. *Mitigation*: flag removal is folded into Phase 4's cutover, not left indefinitely optional the way Phase 6 is.

Concurrency risks

  • Two simultaneous transfer attempts for the same session (double-click, or two devices racing). *Mitigated structurally* by the same atomic compare-and-swap pattern already proven for today's terminal-lock, applied to the new hosting/ownership fields (Chapter 10) — this is a known, already-solved problem in this codebase, not a novel one.
  • A transfer racing against a concurrent Close or Suspend of the same session. *Mitigation*: the transfer transaction's re-verification step (Chapter 7) re-checks the session's status immediately before committing, inside the same atomic operation — a session that closed or suspended a moment before the transfer commits causes the transfer to cleanly fail rather than commit against stale state.

Data integrity risks

  • Session-Terminal-History gaps if a code path ever changes a session's hosting terminal without going through the Transfer Service (e.g., a future direct-DB fix). *Mitigation*: this is a process/discipline risk, not architectural — flagged here so the implementing team treats the Transfer Service as the *only* sanctioned path to changing a session's host, never a manual update.
  • Denormalized counter/terminal fields on PosSession drifting from the true current hosting terminal if the "refresh on transfer" step is ever skipped. *Mitigation*: keeping this refresh inside the same atomic transaction as the hosting-pointer change (rather than a separate follow-up step) is a hard architectural requirement of this design, not a nice-to-have.

Operational risks

  • Support/ops staff needing new runbooks for "a terminal is stuck LOCKED and nobody is unlocking it" (e.g., the original cashier went home without acknowledging). *Mitigation*: the supervisor force-unlock path (Chapter 5/10) exists precisely for this, and should be part of Phase 3's pilot-branch training material.
  • Reporting discrepancies noticed by finance/ops during Phase 5 if Terminal/Counter Summary numbers shift from their historical (terminal-owns-session) basis to the new per-transaction basis, even where the new basis is more correct. *Mitigation*: this is a communication risk more than a technical one — flagged so the rollout plan includes explaining the reporting basis change before Phase 5 ships, not after someone notices a number moved.

Chapter 16 — Future Enhancements

Naturally enabled, not required, by this architecture:

  • Full session roaming — this document's core deliverable, but future phases could extend it further (e.g., cross-device handoff initiated remotely by a supervisor without the cashier present at the target terminal).
  • Improved supervisor takeover — since takeover (ownership) and transfer (hosting) are now cleanly separated primitives, a supervisor could be given a combined "reassign and relocate in one action" tool, or fine-grained permission to do one without the other.
  • Device replacement — a terminal physically dying mid-shift becomes a "transfer the session to a spare terminal" operation instead of a data-loss incident, since the session was never tied to the dead hardware's identity in the first place.
  • Temporary/pop-up terminals — a terminal that only needs to exist for a single event or a single day becomes low-stakes to register and decommission, since it never "owns" anything that outlives it — sessions it hosted simply transferred elsewhere or closed normally.
  • Remote recovery — a supervisor or admin, from any authenticated device, could resolve a stuck/LOCKED terminal or force-transfer a session without needing to be physically present at either terminal, since the Transfer Service's authorization model (Chapter 10) already supports supervisor-initiated transfers.
  • Multi-device dashboards — the Session-Terminal-History and Session Transfer Log tables (Chapter 11) are ready-made data sources for a "live view of who is where" operational dashboard, which the old terminal-owns-session model had no clean way to construct (it could only ever answer "who is on this terminal right now," never "where is this cashier right now").
  • Advanced auditing — the strengthened ownerUserId/performedByUserId FKs (Chapter 11) enable reliable "everything this specific user did today, across every session and every terminal they touched" queries, which are unreliable today given the string-based identity fields.
  • Future offline support — because Session Resolution is now a single, well-defined question ("what does this user own, and where is it hosted") rather than a terminal-coupled handshake, it becomes a cleaner target for an eventual offline-first client to reason about and reconcile against once connectivity returns — this document does not design offline support, but notes that this architecture does not foreclose it the way the terminal-centric model implicitly did.
