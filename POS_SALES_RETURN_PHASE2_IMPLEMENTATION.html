Phase 2 implementation report

Sales Return: the Economic Foundation and the Split

BillBull Retail / ERP · branch feature/posclient · 2 October 2026 · code, schema and tests changed; no historical data touched

Phase 2 is implemented, with three sections deliberately left unbuilt because they depend on business decisions that are not approved anywhere in the repository. The system now has one definition of invoice balance, one definition of effective customer outstanding, and one server-derived answer to how much of a return is money owed back — unpaidPortion = min(returnValue, invoiceOutstanding), computed inside the existing invoice row lock, with refundAmount overwritten rather than defaulted. The return journal is byte-for-byte unchanged, and the five-row settlement table survives intact.

Concurrency: the split is computed inside the lock that already existed

assertReturnableQuantitiesStillAvailable already took a PESSIMISTIC_WRITE lock on the linked sales_invoices row before anything was written. It now returns that locked instance, and the split is computed from it rather than from a second query. No new locking was introduced, and SalesReturnApprovalSplitTest verifies the identity of the instance — that findByInvoiceNumber is never called on this path — because an unlocked re-read is precisely how two concurrent returns would both consume the same outstanding.

lock Sales Return findByIdForUpdate → authorize, assert method settleable, assert same branch → lock linked invoice assertReturnableQuantitiesStillAvailable → SalesInvoice → resolveSettlementSplit(saved, lockedInvoice) ← overwrites refundAmount → assertSettlementMethodMatchesSplit(saved, split) → applyBatchReturns / applyNonBatchStockReturns (restock plan) → postJournalForApprovedReturn ← UNCHANGED: Cr AR for the full value → applyReturnCreditToInvoice(saved, split, invoice) ← allocation row + recompute → applySerialReturns → cashRefundService.recordCashRefund → pays paidPortion → issueCreditVoucherIfRequired(saved, split) → issues paidPortion → postRefundSettlementIfRequired(saved, split) → settles paidPortion → auditApproval(saved, authorization, split) commit

refundAmount is overwritten, not defaulted

This was the sharpest defect in the module. Every settlement path read refundAmount ?? totalAmount; the return screen sent refundAmount: summary.totalRefund; and applyEntryPointDefaults filled the field only when it was null. So the amount of cash that left the drawer was whatever the browser said. Three changes close it together, and any one alone would have left a hole:

  • the server computes paidPortion and assigns it over whatever arrived, logging the override;
  • the frontend stops sending the field at all;
  • every ?? totalAmount fallback is deleted — in the cash service, the voucher path and the card/bank settlement — so a null pays nothing rather than paying everything.

SalesReturnApprovalSplitTest proves an inflated client figure (99999.00 against a 2,500 return) cannot enlarge the paid portion, and that a null no longer pays out the full total on a part-paid invoice.

Why the inbound stock index is scoped to SALES_RETURN

The existing identity index is WHERE quantity < 0, so the positive rows a return approval posts were protected only by the approval row lock — nothing at the database level stopped a retry from raising on-hand twice while GL 1200 was debited once. A blanket inbound index would have been wrong: a purchase receipt can legitimately carry two lines of the same product, batch and bin, so the index would fail to build on existing tenant data and the try/catch would leave no guard at all. One return posts at most one row per product/warehouse/bin/batch/expiry, so for this source the identity is exact and the index is safe to create.

The central invariant, and why there is no allocation journal

Cr AR (return journal) returnValue Dr AR (settlement leg) paidPortion ——————————— net Cr AR unpaidPortion ≡ Δ invoice.balance ≡ Σ allocation rows

The allocation carries no GL entry of its own. The return journal already credited AR for the full value and the settlement leg debits back only the paid portion, so the residue is the receivable reduction; posting an allocation journal would double-count it. GL 1100 and the AR sub-ledger therefore agree by construction for every refund method, with no new journal shape and no per-method branching. Tested as a property over six positions in theNetCreditToArAlwaysEqualsTheAllocation.

No GL account was created, and none was invented. Account 2062 does not exist and was not added to SystemAccountSeeder. Every account named above is one the codebase already posts to.

IRemaining risks and what blocks Phase 3

1. Decision 7 blocks the Customer Credit instrument entirely. Without account 2062 there is no held-credit ledger, no issue or application journal, no open-credit-pool report, and no CREDIT_HELD/CREDIT_APPLICATION statement rows. The operational consequence is concrete: a cashier taking a return on a fully or partly paid invoice from a named account customer cannot choose Customer Credit and must use cash, card, bank or voucher. Everything else about the method still works.

2. The residual reconcileAR drift is closed for new returns but not retrospectively. Invariant 3 (GL 1100 = Σ opening.outstanding + Σ invoice.balance) now holds by construction for every return approved under Phase 2. For returns approved before it, the drift stands at whatever the queries in §H report — the model is live but history has not been brought to it.

3. Decision 1 means there is no authorized over-refund path. A branch wanting to settle a dispute or goodwill case above the paid portion cannot, and the economic model's own argument is that a hard block pushes staff into cancelling and reissuing invoices, which destroys the audit trail. The machinery to add it exists (SalesReturnAuthorizationService); only the decision is missing.

4. Phase 3 items not in scope and still open. Held-credit allocation (manual and FIFO) and refund-to-cash; refund Payment rows for cash, card and bank, which would also make the dormant totalRefunds metric meaningful and give the card settlement operator a per-day refund figure; POS Net Sales net of returns on a VAT-inclusive base, forward-dated, together with the back-office gross-profit basis mix; rejecting unlinked returns with a manual credit note; scrap routing to quarantine; removing the dead exchange buckets; historical remediation.

5. The frontend's display split is a mirror, and mirrors can drift. useSalesReturn.js recomputes the split client-side so controls react as lines are picked. It is display-only and the server recomputes authoritatively under the lock, so it cannot affect accounting — but if the server's rule changes, the mirror must change with it. The shared eligibility figures reduce the exposure; the arithmetic itself is duplicated.

6. V111 has not been executed against any database. No datasource was available in this session, so the migration is unverified at runtime and the seven @SpringBootTest classes that need a reachable DB did not load — as they do not on any bare mvn test.
