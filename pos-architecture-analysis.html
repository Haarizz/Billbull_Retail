BillBull POS — Terminal / Counter / Session Architecture Analysis (As-Built)

Scope: This document describes the *existing* implementation only, derived from the codebase at c:\Users\hp\Desktop\Billbull_Retail on branch feature/posclient. No redesign, no recommendations. Every claim is grounded in a file reference; where behavior is ambiguous or unread, this is stated explicitly rather than guessed.

Primary sources: billbull-backend/src/main/java/com/billbull/backend/pos/**, billbull-backend/src/main/resources/db/migration/V*.sql, billbull-frontend/src/pages/Sales/POSSales.jsx and src/pages/Sales/POS/**, src/api/pos*.js.

1. Executive Summary

The POS subsystem is a package-by-feature Spring Boot module (pos/, 12+ subpackages) backing a single React mega-component (POSSales.jsx, ~14.5k lines) that owns nearly all client-side POS state. There is no dedicated POS login** — POS reuses the app-wide JWT login and instead performs *terminal registration* as its own bootstrap step, keyed off a browser-generated device fingerprint, not a user action. A Terminal is a per-branch, per-device registration record (roughly "this browser/device on this branch"), a Counter is a lightweight named billing point terminals can be assigned to (optionally carrying a default cash drawer/printer), and a Session (PosSession) is the cashier shift ledger — one row per open/close, exactly one OPEN session allowed per terminal at the database level. Sessions roll up into a daily Day Close (PosDayClose, one per branch per business date), gated by every terminal having produced an X-Report first. GL posting is real (via PostingEngineService) for session close and cash movements, but is deliberately non-blocking (wrapped in try/catch) for session close. Concurrency safety for "one open session per terminal" rests on a DB partial unique index plus an application-level atomic compare-and-swap on pos_terminals.current_open_session_id — not JPA optimistic locking (@Version is unused anywhere in pos/**).

2. Domain Model

2.1 Entity reference

All POS entities live under com.billbull.backend.pos.*. Per common.BaseEntity (common/BaseEntity.java:41-43), the primary-key strategy is @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id — a plain auto-increment Long. This corrects an assumption in CLAUDE.md's UuidV7 mention: POS entities do not use UUIDv7; that generator exists elsewhere in the codebase but is not used here. PosDayClose, PosAuditLog, and PosLayawayItem do not extend BaseEntity at all — they declare their own identity @Id.

PosTerminal (pos/terminal/PosTerminal.java, table pos_terminals)

  • Purpose: registration record for a physical/browser device operating POS at a branch — "this device, on this branch, currently at this counter."
  • PK: id (BaseEntity, Long identity).
  • Key fields: branchId/branchName, terminalId (unique business identifier, format T001-XXXX), terminalName, counterName (legacy string) + counterId (FK → pos_counters.id), deviceFingerprint, deviceInfo, operatingSystem, browser, ipAddress, isMainPos (single-flag "primary" terminal per branch, app-enforced not DB-enforced), lastSeenAt/lastHeartbeatAt, registeredBy, status (PosTerminalStatus), registrationStatus (raw string PENDING/APPROVED/REJECTED), currentOpenSessionId (the session-lock column), hardwareProfileId+assignedProfileVersion, archive fields (archivedAt, archiveReason), decommission fields (decommissionedAt, decommissionReason — no restore path), auto-archive lifecycle fields (staleAt, staleWarningSentAt, lastActivityAt, autoArchiveExempt, archiveContextJson TEXT).
  • FKs: counterId → pos_counters; branchId is a loose Long, not a JPA relationship (resolved manually via BranchRepository/BranchAccessService).
  • Status enum (PosTerminalStatus): NEW, PENDING_REGISTRATION, ACTIVE, IDLE, OFFLINE, INACTIVE, MAINTENANCE, BLOCKED, STALE, DECOMMISSIONED, ARCHIVED.
  • Constraints: unique composite index on (device_fingerprint, branch_id) (V47__pos_terminal_device_branch_composite_unique.sql, replacing an earlier global-unique on device_fingerprint alone) — terminal device identity is scoped per branch; terminal_id itself is also unique.
  • Lifecycle: NEW/PENDING_REGISTRATION → ACTIVE ⇄ IDLE ⇄ OFFLINE → STALE → ARCHIVED, with side branches to BLOCKED/MAINTENANCE and a terminal DECOMMISSIONED (permanent, no restore).

PosCounter (pos/counter/PosCounter.java, table pos_counters)

  • Purpose: a named billing point/lane a terminal can be assigned to; carries defaults (drawer, printer) but is not itself hardware.
  • PK: id (BaseEntity).
  • Key fields: branchId/branchName, counterCode (unique per branch, CTR-NNN), counterName, description, status (PosCounterStatus: ACTIVE/INACTIVE/MAINTENANCE), defaultCashDrawer, defaultReceiptPrinter, displayOrder.
  • Constraints: unique composite (branch_id, counter_code).
  • Lifecycle: soft-delete only (isActive=false + status→INACTIVE); deactivation/deletion blocked (409) while any terminal still references the counter, via terminalRepo.countByCounterIdAndStatusIn/countByCounterId.

PosSession (pos/session/PosSession.java, table pos_sessions)

  • Purpose: one cashier shift — the ledger of a terminal being "open for business" from open to close, with running sales/cash totals.
  • PK: id (BaseEntity).
  • Key fields: branchId/branchName, terminalId (string) + terminalPk (FK → pos_terminals.id), counterName+counterId, openedBy/closedBy (raw usernames) + display-name shadow columns, sessionDate, openedAt/closedAt, durationSeconds, lastActivityAt, idleTimeoutMinutes, sessionTimeoutAt, dayCloseId (FK → pos_day_closes), status (PosSessionStatus), openingCash/closingCash/expectedCash/cashDifference (BigDecimal 15,2), per-tender totals (totalSales, totalCashSales, totalCardSales, totalCreditSales, totalMixedSales, totalOnlineSales, totalRefunds), totalVoids, invoiceCount, X-Report fields (xReportPrinted, xReportGeneratedAt/By+displayName), Z-Report fields (zReportPrinted, zReportJson — immutable snapshot), closingDenominationsJson, card-settlement fields (cardBatchNo, cardSettlementVerified, cardClosingCash, cardDifference), closing signatory/remarks fields.
  • Relationships: @OneToMany(mappedBy="posSession", cascade=ALL, orphanRemoval=true, LAZY) → List<PosCashMovement>.
  • Status enum (PosSessionStatus): OPEN, CLOSED, SUSPENDED.
  • Constraints: index idx_pos_sess_lookup (branch_id, terminal_id, status); DB partial unique index uq_pos_session_terminal_open ON pos_sessions(terminal_id) WHERE status='OPEN' (created in V13__pos_safety_fixes.sql, later superseded conceptually by a terminal_pk-keyed compare-and-swap on the terminal row itself — see §10 for the exact mechanism, which is application-level, not this index directly).
  • Lifecycle: OPEN ⇄ SUSPENDED → CLOSED (terminal). No re-open from CLOSED.

PosCashMovement (pos/session/PosCashMovement.java, table pos_cash_movements)

  • Purpose: a single cash drop-in/drop-out event during a session (safe drops, till top-ups, petty cash, etc.).
  • PK: id (BaseEntity).
  • Key fields: @ManyToOne(LAZY) posSession (@JsonIgnore), movementType (PosCashMovementType: DROP_IN/DROP_OUT), amount, description, performedBy/performedAt, reference, status (PosCashMovementStatus: ACTIVE/VOIDED), voidReason/voidedBy/voidedAt, editedBy/editedAt/editCount, originalDescription/originalReference (first-edit snapshot), denormalized businessDate/branchId, categoryId (FK → PosCashMovementCategory, optional), postedAccountCode/postedAccountName (denormalized GL leg — resolved once at creation so a later void reversal always mirrors the original posting even if the category's account mapping later changes).
  • Lifecycle: created → (optionally edited, description/reference only) → (optionally voided). Amount/type/session are structurally immutable post-creation. Locked entirely once the owning session's business day has a PosDayClose (dayCloseId != null).

PosDevice (pos/device/PosDevice.java, table pos_devices)

  • Purpose: shared parent row for all hardware types (printer/scanner/cash drawer/card terminal/customer display/scale/generic) — the Device Manager's unifying record.
  • Key fields: deviceCode (unique), deviceName, branchId/branchName, counterName, deviceType (PosDeviceType), terminalId, status (PosDeviceStatus: admin-controlled axis — NEW/ACTIVE/INACTIVE/MAINTENANCE/DISABLED/DECOMMISSIONED), runtimeHealth (PosDeviceRuntimeHealth: system-observed axis — UNKNOWN/ONLINE/OFFLINE/BUSY/DISCONNECTED/ERROR/PAPER_OUT/COVER_OPEN), lastHeartbeat, notes.
  • Note the deliberate two-axis design: status (what an admin set) is independent of runtimeHealth (what the last heartbeat observed).

User (user/User.java, table users)

  • Relevant fields for POS: username (unique — the raw identity string stored in PosSession.openedBy/closedBy and PosCashMovement.performedBy, never resolved to a FK), fullName, linkedEmployee (@OneToOne → hr.employees.Employee), branch (@ManyToOne, default landing branch), additionalBranches (@ManyToMany), roles/primaryRole. getResolvedDisplayName() (prefers linked Employee name → fullName → username) is what populates the *DisplayName shadow columns on PosSession/PosDayClose.

Branch (settings/branch/Branch.java, table branches)

  • Own @Id GenerationType.IDENTITY (not BaseEntity). Fields: name, code, address, trnNumber (ZATCA), bank fields, sortOrder, isDefault, isHeadquarters, type, @ManyToOne(LAZY) defaultWarehouse → Warehouse. Every POS entity's branchId is a loose FK, not a JPA relationship.

Warehouse (inventory/warehouse/Warehouse.java, table warehouses)

  • Extends BaseEntity. name, type, address, status, capacity, utilization, @ManyToOne(LAZY) branch. Not directly referenced by POS terminal/counter/session entities — stock deduction on checkout flows through StockMovement/DeliveryNoteService using the branch's defaultWarehouse, per CLAUDE.md's stock-movement-as-source-of-truth convention.

No PosShift entity

Grep across pos/** found no PosShift class. "Shift" as a concept is represented entirely by PosSession.

Cash Register / Printer / mapping tables

There is no single "Cash Register" entity — its role is split across PosCashDrawer (physical drawer hardware, pos/cashdrawer/PosCashDrawer.java, table pos_cash_drawers: deviceCode unique, deviceId FK → PosDevice, branchId, terminalId, attachedPrinterId mandatory — the drawer has no standalone connection, its kick command rides the attached printer's ESC/POS cable — status, lastKickAt/lastKickResult) and PosSession's cash fields (the accounting register). PosPrinter (pos/printer/PosPrinter.java, table pos_printers) is the printer device record: deviceCode unique, deviceId FK → PosDevice, deviceType (RECEIPT_PRINTER/KITCHEN_PRINTER/LABEL_PRINTER), connectionType (USB/NETWORK_IP/BLUETOOTH/WINDOWS_QUEUE/ZEBRA_BROWSER_PRINT), systemPrinterName, deviceIdentifier, ipAddress/portNumber, printTemplate, defaultPrinter, status, runtimeStatus. PosHardwareProfileDevice (table pos_hardware_profile_device, unique (hardware_profile_id, role)) is the actual mapping table binding role-tagged devices (e.g. "receipt printer", "kitchen printer") into a PosHardwareProfile, which is in turn assigned to terminals.

3. Terminal Concept

What it represents: a per-branch registration of a physical device/browser session running the POS UI — closer to "this machine, at this branch" than to a business concept like "checkout lane" (that's the Counter's job). It is logical + device-bound: identity is a client-generated deviceFingerprint (stored in localStorage['billbull:pos:device_fingerprint'] on the frontend) plus a server-issued terminalId string, not a physical asset tag.

  • Creation flow: no admin "create terminal" form exists. Terminals self-register the first time POSSales.jsx mounts, via registerTerminalAndResumeSession() → POST /api/pos/terminals/register (PosTerminalController, endpoint intentionally not permission-gated — any authenticated user can trigger it, since it's device self-service). PosTerminalService.registerOrRefresh looks up by terminalId first, falling back to the (deviceFingerprint, branchId) composite unique lookup. New terminals are capped by PosSettings.maxTerminalsPerBranch (default 5, ARCHIVED+DECOMMISSIONED excluded from the count) and, if PosSettings.requireTerminalApproval is set, start in PENDING_REGISTRATION rather than ACTIVE.
  • Assignment flow: assignCounter(terminalId, counterId) — 404 if counter missing — sets PosTerminal.counterId; done from POSConsole.jsx's terminals tab (live UI) or the orphaned standalone POSTerminals.jsx page (not routed anywhere — see §14).
  • Activation/Deactivation: approve/reject only from PENDING_REGISTRATION; archive/decommission blocked (409) while currentOpenSessionId != null — a terminal with an open session cannot be archived or decommissioned. Decommission has no restore path (documented as permanent in code). restore only from ARCHIVED, re-validated against the terminal-limit.
  • Authentication: none, beyond the ambient JWT of whichever authenticated user's browser is registering. There is no separate terminal credential/token — see §6.

Answers:

  • Can multiple users use one terminal? Yes, sequentially — a terminal's currentOpenSessionId ties it to one session (and thus one openedBy user) at a time, but different shifts/users can each open a session against the same terminal over time. reassignSessionOwner/supervisorTakeover also let a session's owning user change mid-shift.
  • Can one user use multiple terminals? Yes — nothing in the schema restricts a user to one terminal; PosSessionService.getActiveSession only checks that a given terminal's open session belongs to the requesting user, not the reverse.
  • Can one terminal belong to multiple counters? No — counterId is a single nullable FK on PosTerminal (one counter at a time, reassignable).
  • Can terminals move between branches? Not observed as a supported flow — (deviceFingerprint, branchId) is the composite identity, so the same device fingerprint registering under a different branch creates (or resolves to) a *different* PosTerminal row rather than moving the existing one.

4. Counter Concept

A Counter is a logical workstation / named billing point — not itself a piece of hardware, not a physical fixed asset record. It carries *default* device references (defaultCashDrawer, defaultReceiptPrinter) as plain strings, but actual hardware binding happens through PosHardwareProfile/PosDevice, assigned to the *terminal*, not the counter.

  • Creation: PosCounterService.create — auto-generates a CTR-NNN code if omitted; 409 if (branchId, counterCode) already exists.
  • Editing: update — standard field mutation.
  • Assignment: counters are assigned *to* terminals (PosTerminal.counterId), not the reverse — a counter doesn't hold a list of its terminals as a first-class relationship, it's discoverable only by querying terminals with that counterId.
  • Removal: soft-delete (isActive=false, status→INACTIVE); blocked with 409 if any terminal still references it.

Relationships:

  • Branch: loose branchId FK, counter codes unique per branch.
  • Terminal: one counter can have many terminals pointed at it (counterId FK on PosTerminal); a terminal has at most one counter.
  • Session: no direct FK — PosSession.counterName/counterId are copied from the terminal at session-open time (denormalized snapshot, not a live join).
  • User: none.
  • Printer / Cash Drawer: only as free-text default strings (defaultReceiptPrinter, defaultCashDrawer) on the counter — not FK relationships to PosPrinter/PosCashDrawer rows. Actual device binding is via PosHardwareProfile on the terminal.
  • Warehouse: none observed.

The PosCounterController has no RBAC/module-permission gating at all beyond isAuthenticated() — notably weaker than the terminal controller, which is permission-gated action-by-action.

5. Session Concept

PosSession (pos/session/PosSession.java, service pos/session/PosSessionService.java, 2098 lines) is the cashier-shift ledger.

  • How a session starts: PosSessionService.openSession(terminalId, counterName, openingCash). Resolves branch via BranchAccessService, resolves current business date via PosBusinessDateService. Guards, in order: (1) 403 if the business day is already closed; (2) 409 PREVIOUS_DAY_SESSION_OPEN: ... if any unclosed session exists from a prior business date for that branch (a machine-readable prefix the frontend parses to offer "go close that session" instead of generically retrying); (3) 409 if an OPEN session already exists for branch+terminal under a *different* cashier ("Terminal is already in use by active cashier: ..."), or hands the existing session back if it's the same user. A new PosSession row is inserted (status OPEN, zeroed totals, idle/max-duration timeouts pulled from PosSettings), then the terminal lock is claimed atomically (terminalRepository.setOpenSession, a native UPDATE ... WHERE current_open_session_id IS NULL); if that update affects 0 rows (lost the race), the just-inserted session row is deleted and a 409 is thrown.
  • How a session closes: closeSession(...) (4 overloads). Rejects if already CLOSED, or if status is neither OPEN nor SUSPENDED. expectedCash is computed via the shared computeExpectedCash() helper = openingCash + tenderCash + cashDropIn - cashDropOut. If |closingCash - expectedCash| > PosSettings.cashVarianceThreshold and the caller hasn't set supervisorApproved, a 422 is thrown requiring supervisor sign-off. On success: status→CLOSED, closedBy/At, durationSeconds set; card reconciliation is recomputed server-side (never trusts a client-sent boolean); X-Report is auto-stamped if never explicitly generated; an immutable Z-Report JSON snapshot is built and stored; the terminal lock is released via a matching atomic clearOpenSession; GL posting (PostingEngineService.createJournalFromSessionClose) is attempted but wrapped in try/catch so a GL failure never blocks the close.
  • States: OPEN ⇄ SUSPENDED → CLOSED (suspendSession/resumeSession, each validating the current state before transition; no re-open from CLOSED).
  • Opening balance: openingCash, computed client-side from a fixed AED denomination breakdown (see §14) and passed in on open.
  • Closing balance / cash counting: closingCash from the same denomination-count UI at close; closingDenominationsJson persists the breakdown server-side.
  • Expected cash / variance: expectedCash (server-computed, see above) vs. closingCash (counted) → cashDifference; the variance-threshold supervisor gate is the only hard validation tied to the count.
  • Reports: generateXReport/getXReport (per-session, idempotent first-call stamp + immutable snapshot persistence via PosXReportSnapshot), getZReport/generateDynamicZReport (per-branch-per-date, aggregates sessions), closeDay (Day Close, the actual finalize-the-day transaction).
  • Associations: openedBy/closedBy (User, by raw username), terminalId+terminalPk (PosTerminal), counterName+counterId (PosCounter, denormalized snapshot at open), branchId (Branch). No direct Warehouse association — inventory effects flow through StockMovement at checkout, independent of the session record.

6. Session State Machine

stateDiagram-v2 [*] --> TerminalRegistered: POST /api/pos/terminals/register TerminalRegistered --> SessionOpen: POST /api/pos/sessions/open\n(guards: day not closed,\nno prior-day unclosed session,\nterminal lock CAS) SessionOpen --> SessionSuspended: POST /{id}/suspend\n(idle timeout OR manual) SessionSuspended --> SessionOpen: POST /{id}/resume\nOR supervisor-takeover SessionOpen --> SessionOpen: Sales (checkout), Payments,\nRefunds, Cash Movements\n(recordInvoiceOnSession /\naddCashMovement) SessionOpen --> XReportGenerated: POST /{id}/x-report/generate\n(idempotent, required before\nZ-Report eligibility) SessionSuspended --> SessionClosed: close (also valid from SUSPENDED) SessionOpen --> SessionClosed: POST /{id}/close\n(variance gate: 422 if over\nthreshold w/o supervisorApproved) SessionClosed --> [*]: terminal lock released\n(clearOpenSession) SessionClosed --> DayClosed: POST /close-day\n(all sessions for branch+date\nmust be CLOSED, all must have\nX-Report, sales+cash\nreconciliation must balance) DayClosed --> [*]: business date advanced +1

Failure paths observed in code:

  • Open blocked: business day already closed (403); unclosed prior-day session exists (409, PREVIOUS_DAY_SESSION_OPEN: prefix); terminal already occupied by another cashier (409); lost the terminal-lock CAS race (409, session row rolled back).
  • Close blocked: already CLOSED (400); status neither OPEN nor SUSPENDED (400); variance over threshold without supervisor approval (422).
  • Suspend/resume blocked: wrong starting state (400 in each case).
  • Day close blocked: already closed for that branch+date (409); any OPEN session exists date-wide (400); any SUSPENDED session exists (400); resolved session range empty (400); range excludes sessions without acknowledgement (SessionRangeExclusionException); DRAFT invoices in range (400); PENDING/FAILED payments in range (400); sales reconciliation mismatch >0.05 (ReconciliationException("SALES", ...)); cash reconciliation mismatch >0.05 (ReconciliationException("CASH", ...)).
  • Terminal-side failure paths that block session flow indirectly: terminal ARCHIVED/BLOCKED/DECOMMISSIONED/MAINTENANCE rejects registration/heartbeat (403, "Terminal is {STATUS}"), which prevents ever reaching Session Open.

7. Login Flow

There is no POS-specific login screen. POS reuses the app-wide login (src/auth/login.jsx) — JWT stored in sessionStorage.token, attached as Authorization: Bearer by axiosConfig.js's request interceptor. Route: /sales/pos → <ResourceGuard module="sales.invoice"><POSSales /></ResourceGuard> (src/App.jsx:461-468).

What actually happens on entering POS is terminal registration + session resume, traced in POSSales.jsx:

sequenceDiagram participant U as User Browser participant FE as POSSales.jsx participant BE as PosTerminalController participant SVC as PosSessionService U->>FE: navigate to /sales/pos (already JWT-authenticated app-wide) FE->>FE: read/create deviceFingerprint (localStorage) FE->>FE: read cached terminalId for this branch (localStorage) FE->>BE: POST /api/pos/terminals/register {terminalId, deviceFingerprint, deviceInfo} alt terminal blocked/archived/decommissioned/maintenance BE-->>FE: 403 "Terminal is {STATUS}" FE->>FE: setTerminalRegistrationError, block UI else success BE-->>FE: terminal record (ACTIVE or PENDING_REGISTRATION) FE->>FE: cache terminal.terminalId in localStorage FE->>SVC: GET /api/pos/sessions/active?terminalId= SVC-->>FE: existing OPEN session (if any) or null FE->>SVC: GET /api/pos/sessions/day-status?terminalId= SVC-->>FE: prior-day-open-session block info (if any) FE->>FE: render dashboard / Start Session dialog end

No explicit role/branch/warehouse/counter *picker* UI exists in this flow — branch comes from the app-wide BranchContext branch selector (mirrored to sessionStorage.activeBranchId, sent as an X-Branch-Id header), and the counter comes from whatever counter is already assigned to the terminal server-side. Re-registration is triggered by the window event billbull:branch-changed fired by BranchContext when the user switches branches.

8. POS Startup Flow

All in one "POS initialization" useEffect in POSSales.jsx (~lines 1880-2056), gated by posInitLoading:

  1. getPosSettings() → merged into ~80 template-designer fields (tplXxx, t2XxxShow*).
  2. getBranchTaxConfiguration() / per-branch variant → tax-inclusive flag, default VAT rate.
  3. registerTerminalAndResumeSession() → terminal registration, active-session resume, day-status check (§7).

Independent, separately-triggered effects:

  • Departments: getDepartments() → posDepartments.
  • Customers: loadPosCustomers → getAllCustomers/searchCustomersAllFields.
  • Products: loadPosProducts (paginated, AbortController-guarded) + loadMorePosProducts (infinite scroll).
  • Printer config: getPosPrinters({branchId}) (inside POSConsole.jsx devices tab), resolved per-context via resolvePrinterForContext (localPrintAgent.js).
  • Scanner config: persisted to/from localStorage['billbull:pos:scanner:{branchId}:{terminalId}']; consumed by a raw keydown listener in POSTouchScreen.jsx implementing keyboard-wedge barcode capture — there is no dedicated scanner-hardware runtime utility.
  • Cash drawer: posCashDrawerApi.js manages only the device *record*; the actual kick command is bundled into the ESC/POS receipt payload sent via localPrintAgent.js at print time, not a standalone call.
  • X-Report: loadXReport fires when currentView==='x-report' or when dashboarded with an active session and no cached report.
  • Held sales: loadHeldSales, part of the syncPosData umbrella refresh (also re-runs customers/products/X-report after checkout or session close).
  • Business day / pending items: getPosDayStatus (§7) and getDeliveryOrders(branchId) for the Delivery Settle feature.
  • Heartbeat: useHeartbeat(terminalId) — POST heartbeat every 60s, failures swallowed silently.
  • Idle timeout: useIdleTimeout({timeoutMs, sessionId, onIdle}) — locks the terminal UI on inactivity, and independently touches touchSessionActivity(sessionId) every 30s to keep the backend's idle clock in sync regardless of whether the idle threshold has been hit.

Payment methods, taxes: taxes loaded via getBranchTaxConfiguration; no separate "payment methods" load call was identified in this pass (payment method list appears to be a fixed set handled in checkout UI, not fetched — not fully confirmed, flagged as unread).

9. Terminal Validation Logic

From PosTerminalService:

  • Terminal status must not be BLOCKED/MAINTENANCE/DECOMMISSIONED/ARCHIVED to register (403, "Terminal is {STATUS}").
  • Terminal status must not be ARCHIVED/DECOMMISSIONED/BLOCKED to heartbeat (MAINTENANCE deliberately excluded here so a mid-shift maintenance flag doesn't sever an already-open session's heartbeat).
  • New-terminal registration enforces PosSettings.maxTerminalsPerBranch (default 5, ARCHIVED+DECOMMISSIONED excluded from the count).
  • If PosSettings.requireTerminalApproval, new terminals start PENDING_REGISTRATION (not usable until approve).
  • approve/reject only valid from PENDING_REGISTRATION (else 400).
  • archive/decommission blocked (409) while currentOpenSessionId != null — duplicate-session prevention indirectly, since you can't archive out from under an active shift.
  • restore only from ARCHIVED, re-checks the terminal limit.
  • Device identity resolved by (deviceFingerprint, branchId) composite unique lookup, then by terminalId — this is the closest thing to "device validation."
  • Registration has a documented retry-once pattern for DataIntegrityViolationException (handles React StrictMode double-mount races) — a concurrency safeguard, not a business validation.
  • Permission checks: PosTerminalController uses ModulePermissionService gating per action-key (permissions.pos.terminal.<action>) for every admin action (rename/assign-counter/set-main/approve/reject/archive/restore/decommission/block/unblock/keep-active/set-auto-archive-exempt); register/heartbeat are deliberately left ungated (device self-service).
  • Concurrent login prevention: not really "login" — enforced instead as "one open session per terminal" (see §10) rather than a terminal-level login lock.

10. Counter Validation Logic

From PosCounterService:

  • Counter code uniqueness per branch — 409 on duplicate (branchId, counterCode).
  • Setting status to INACTIVE/MAINTENANCE blocked (409) if any terminal is still assigned with an active status (countByCounterIdAndStatusIn > 0).
  • Delete blocked (409) if any terminal references the counter at all (countByCounterId > 0).
  • No wrong-branch/wrong-warehouse/wrong-terminal checks were found beyond the composite unique code constraint — counters aren't validated against a warehouse at all (no relationship exists).
  • No "existing session" check on the counter itself (sessions don't hold a live counter FK to check against — see §4).
  • PosCounterController has no RBAC/permission gating, unlike terminal — flagged for §18 (Current Problems, observation only).

11. Session Validation Logic

From PosSessionService (full breakdown in §5/§6):

  • Session already open (for same terminal, different user) → 409.
  • Business day already closed → 403 on open.
  • Prior-day unclosed session exists → 409 PREVIOUS_DAY_SESSION_OPEN:.
  • Different terminal/counter: not independently re-validated per call — getActiveSession checks the requesting terminal matches; a 409 is thrown if the terminal is "locked by active cashier" (different user) or registered under a different branch.
  • Cash mismatch: variance-threshold supervisor-approval gate at close (422 without approval).
  • Draft invoices / pending or failed payments: checked at Day Close time (closeDay), not at session close — 400 if any exist in the resolved session range.
  • X-Report pending: gates Z-Report eligibility (generateDynamicZReport computes pendingTerminals); assertXReportPrintable throws 409 unless the session is CLOSED.
  • Z-Report pending: assertZReportPrintable throws 409 unless a PosDayClose row exists for that branch+date.
  • Sales/cash reconciliation: at Day Close, computed totals vs. persisted session totals must match within 0.05 tolerance, else ReconciliationException.
  • No independent "session already closed" check beyond the close-guard itself (already covered in state-machine failure paths, §6).

16. Business Rules

  • One session per terminal at a time — enforced at both DB (partial unique index) and application (atomic CAS) level. Not "one session per user" or "one session per counter" directly — those are derived effects of the terminal-level rule plus the terminal→counter assignment.
  • Shared terminals: yes, sequentially across shifts/users (see §3).
  • Shared counters: yes, across multiple terminals (counterId FK is many-to-one from terminal to counter).
  • Multiple cash drawers: schema allows many PosCashDrawer rows per branch/terminal; each must have exactly one attachedPrinterId (mandatory FK).
  • Multiple printers: yes, PosPrinter rows are independent, role-tagged via PosHardwareProfileDevice when bound through a hardware profile.
  • Branch restrictions: pervasive — nearly every POS entity carries a branchId; terminal device identity, counter codes, day close, business date are all branch-scoped.
  • Warehouse restrictions: not directly modeled at the POS terminal/counter/session level; inventory effects resolve through the branch's default warehouse at checkout time (stock movement layer), not through a POS-entity FK.
  • Role restrictions: minimal at the endpoint layer — only Day Close (close-day) hardcodes SUPERVISOR/MANAGER/ADMIN roles; everything else uses fine-grained ModulePermissionService permission keys or plain isAuthenticated() (Counter controller has none at all).
  • Business day restrictions: session open blocked if the business day is already closed; a prior-day unclosed session blocks new-day session opening; Day Close requires zero OPEN/SUSPENDED sessions and complete X-Reports across the branch for that date; the business date advances by exactly one day on successful Day Close (never jumps to "now").

17. Reporting Flow

  • X-Report: per-session. Data source is the session's own accumulated fields (totalCashSales etc., populated via the atomic incrementSessionTotals UPDATE on every checkout) plus a computed expectedCash. First call to generateXReport stamps xReportGeneratedAt/By and persists an immutable PosXReportSnapshot row; subsequent calls just re-read. Print is hard-gated (assertXReportPrintable, 409 unless session is CLOSED) though the on-screen preview is available while the session is still open.
  • Z-Report / Day Close: per-branch-per-business-date. getZReport returns the persisted PosDayClose.zReportJson snapshot if the day is already closed, otherwise dynamically builds one (generateDynamicZReport) and reports eligible=false with a pendingTerminals list if any terminal hasn't generated its X-Report yet. closeDay is the actual finalize transaction — see §6/§11 for its full validation set (reconciliation, exclusions, draft invoices, pending payments).
  • Session Report / history: getSessionHistory/GET /history — paginated browse for X-Report reprint/review, filterable by branch/date/terminal/status.
  • Cash Report: derived from PosCashMovement rows (sumAmountByMovementTypeForSessionIds), folded into both the X-Report's cash-position section and the session's expectedCash computation.
  • Sales Summary: buildCashierWiseSummary, buildTopSellingItems, buildReturnsSummary/buildSessionReturnsSummary — private helpers inside PosSessionService feeding both X and Z reports.
  • Dependencies: strict session → terminal → branch chain; Day Close additionally depends on all terminals in the branch having completed X-Reports, and on the resolved session range across the whole branch (not just one terminal).
  • Locking: no explicit pessimistic lock for Day Close despite the code comment claiming one (§12) — actual double-close protection is the DB unique constraint on (branch_id, close_date).

18. Hardware Integration

Ownership, from the entity FKs:

  • Printer (PosPrinter) — belongs to a PosDevice (parent), optionally role-bound into a PosHardwareProfile which is assigned to a Terminal (PosTerminal.hardwareProfileId). Also has a legacy direct terminalId field on PosDevice itself, predating the hardware-profile model (both models coexist — additive, not migrated away).
  • Scanner (PosScanner) — explicitly documented in code as a "lightweight, registration-only" entity: editing it has zero runtime effect. Runtime scanning is pure client-side keyboard-wedge capture in POSTouchScreen.jsx, unrelated to the DB row beyond bookkeeping.
  • Cash Drawer (PosCashDrawer) — belongs to a PosDevice, and mandatorily to a Printer (attachedPrinterId) since the kick command physically rides the printer's cable — not independently addressable hardware in this system.
  • Customer Display / Payment Terminal / Weighing Scale: PosDeviceType enum includes CARD_TERMINAL, CUSTOMER_DISPLAY, SCALE as recognized types, but no dedicated child-entity classes (unlike printer/scanner/drawer) were found for these — they appear to exist only as generic PosDevice rows without specialized behavior, flagged as unconfirmed/unread rather than asserted absent.
  • Belongs-to summary: printers/scanners/drawers belong to PosDevice (branch+optionally terminal); hardware *profiles* (bundles of role-tagged devices) belong to a terminal; a counter only carries free-text default-device strings, no FK relationship to actual device rows.

19. Current Problems (Observations Only — Not Recommendations)

  • PosCounterController has no permission gating (isAuthenticated() only), inconsistent with PosTerminalController's per-action ModulePermissionService gating for a structurally similar admin surface.
  • POSTerminals.jsx is dead code — a fully-built, permission-aware terminal admin page that is never routed or imported; POSConsole.jsx reimplements equivalent terminal-admin UI inline instead, meaning the same logic/UI exists in two places with only one reachable.
  • Two POS component directories differing only by case — src/components/pos/ (lowercase, SupervisorTakeoverDialog/TerminalStatusBadge) and src/components/POS/ItemEntry/ (capital) — both exist side by side, relying on Windows' case-insensitive filesystem; this would break on a case-sensitive filesystem (Linux CI/deploy) if not already handled by exact-case imports.
  • closeDay's "lock branch" comment doesn't match the code — it performs a plain findById, not a pessimistic lock; actual concurrency protection for double-Day-Close is an unrelated DB unique constraint. The comment could mislead a future maintainer into assuming a stronger guarantee exists than actually does.
  • No optimistic locking (@Version) anywhere in pos/** — all concurrency safety is via targeted atomic native UPDATEs or DB unique constraints, which works for the specific races handled (session-open CAS, activity-touch, totals-increment) but means any *other* concurrent read-modify-write path on these entities (if one is ever added) would have no such protection by default.
  • PosSessionService is 2098 lines covering session lifecycle, cash movements, X-Report, Z-Report, and Day Close in one class — a large surface area with many private helper methods, which the request explicitly asked not to be redesigned but is worth naming as a size/cohesion observation.
  • Terminal identity via device fingerprint is heuristic, not cryptographic — collision or fingerprint-reset behavior (e.g. clearing browser storage) was not traced in this pass; the registration flow's fallback to terminalId string lookup versus fresh (deviceFingerprint, branchId) lookup could, in principle, create duplicate logical terminals if localStorage is cleared — not confirmed as an actual bug in this pass, flagged as worth checking if terminal proliferation is ever observed operationally.
  • Payment-methods loading in POS startup was not conclusively located — flagged as unread/unconfirmed in §8 rather than asserted.
  • pos/search, pos/receipt, pos/businessdate, pos/admin, pos/reports internals were not read line-by-line in this pass (confirmed to exist and their table/migration footprint verified, but full method-level behavior wasn't traced) — a follow-up pass would be needed before those areas could be redesigned with confidence.
