Separating BillBull POS from BillBull Retail

A full audit of the POS surface as it exists in the repository today — what it is, what it is tied to, and the smallest architectural change that yields a genuinely standalone POS product without putting a single sale at risk.

The headline finding is more encouraging than the raw line counts suggest. The backend is already a POS API. There is a coherent com.billbull.backend.pos package of 20 controllers, 32 dedicated tables, a Business Day engine, a session/terminal/counter model, a denomination ladder, X/Z report sequencing, layaways, held sales, cash movements, a print-job spine and a device manager. A standalone POS client would not be inventing an API — it would be consuming one that already exists and is already the only thing the current POS UI talks to for POS-specific operations.

The coupling that actually matters is almost entirely on the frontend, and almost entirely structural rather than semantic. The POS is one route (/sales/pos) rendered inside the Retail Sidebar shell, in a single 15,818-line component that imports 25 API modules — 11 POS-specific and 14 shared with Retail. Critically, that component does not use react-router at all: it drives its own internal seven-view switch (console, touch-screen, customer, dashboard, x-report, z-report, sales-analytics). Nothing inside POS reads the URL, calls useNavigate, or depends on Retail route structure. That is an unusually clean seam for a component of this size.

The three real obstacles are, in order:

  1. The monolith itself. POSSales.jsx is the single largest risk in this migration. It is not coupled to Retail so much as it is coupled to itself — cart state, session state, printing, reports, settings, terminal registration and eight modal workflows share one component scope.
  2. Authentication shape. The JWT lives in sessionStorage, expires in 24h, and has no refresh token. A till that must stay logged in through a trading day, on a device that may be closed and reopened, is not served by this. CORS is a hard-coded hostname allowlist, which blocks any desktop-shell origin outright.
  3. Checkout is not one transaction. PosCheckoutController.checkout() runs four committed steps with hand-written compensating deletes. It is idempotent (via a unique pos_checkout_key) and it is well-commented, but it is the place where a network-flaky standalone client is most likely to expose an edge the embedded client never did.
Recommendation in one line

Option B — extract POS into its own Vite application in the same repository, sharing the existing Spring API unchanged in shape, with a small shared package for the genuinely common code. No second backend. No second database. No microservices. Ship it as a browser/PWA app in kiosk mode first; keep the existing local print agent; treat a Tauri shell and offline mode as later, separately-justified phases.

Confirmed facts

  • Multi-tenancy is database-per-tenant. One Spring profile, one JVM, one port and one Postgres database per client (DEPLOYMENT_8_CLIENTS.md). There is a single CompanyProfile row per database. Company → Store maps to Database → Branch, not to rows in a shared table.
  • Branch is the store/outlet concept. settings/branch/Branch.java carries address, TRN, logo, stamp, bank details and a defaultWarehouse. Scoping is enforced by security/BranchScope + BranchContextHolder, fed from the X-Branch-Id request header and the JWT's branchIds/isAllBranches claims.
  • Auth is stateless JWT, 24h, no refresh. config/JwtUtil.java, jwt.expiration=86400000. Claims: userId, roles, branchId, branchIds, isAllBranches, defaultWarehouseId. POST /api/session/switch-branch re-mints a token for a different active branch.
  • Authorization is RBAC over a role_permissions table, default-deny, ALLOW-wins across roles. security/ModulePermissionService exposes requireCanView/Create/Edit/Delete/Approve/Export(module). Feature toggles rbac.<module>.enabled gate whole module groups.
  • Stock movement is the inventory source of truth. purchase/stockmovement/StockMovement is an append-only ledger; on-hand quantities are derived aggregates. POS never writes stock directly — it writes an invoice, and the invoice status transition posts the movement.
  • Financial posting is centralised. financials/generalledger/postingengine/PostingEngineService is the auto-posting entry point every module calls.
  • No realtime layer. Zero WebSocket or SSE usage in either module. Everything is polled: terminal heartbeat 60s (hooks/useHeartbeat.js), device dashboard 8s via a cheap refresh-token endpoint.
  • Caching is minimal. Caffeine backs exactly two @Cacheable sites: ProductService.getProductList and BranchTaxConfigurationService. Rate limiting is bucket4j in-memory, ratelimit.dry-run=true for everything except the login brute-force limiter.
  • File storage is a local directory. StaticResourceConfig serves file:./uploads/ at /uploads/**, permitAll. No object store.
  • External dependencies: Playwright headless Chromium for HTML→PDF (document/HtmlPdfService), Apache POI for Excel, spring-boot-starter-mail for SMTP. No third-party payment gateway integration is wired — BNPL and card are recorded, not authorised.

Confirmed defect risk — read carefully

Steps 1–4 are not one transaction. save(), updateStatus() and each recordPayment() commit independently, and the controller compensates by hand with deleteQuietly(saved.getId()) when a later step throws. The code is aware of this and comments it thoroughly. But the compensation only covers failures it can catch: a JVM kill, a connection reset or a DB failover between Step 2 and Step 3 leaves a posted, stock-deducted, GL-journalled invoice with no payment recorded.

Evidence this is a known live condition: config/PosOrphanedPaymentDetectionJob.java exists and runs nightly at 02:30. A standalone client on a less reliable network widens this window rather than creating it.

Cross-cutting API findings

  • Authorization at the boundary is weak. Effectively every POS endpoint is @PreAuthorize("isAuthenticated()"). Only /sessions/skip-day carries a role check. Real authorization sits inside services via ModulePermissionService and, in places, only in the UI. For an embedded module that is tolerable; for a client shipped to customer-controlled hardware it is not.
  • Idempotency exists in exactly one place. posCheckoutKey, a unique column on sales_invoices. Session close, cash movements, layaway payments and delivery settlement have no equivalent key — a retried request creates a duplicate.
  • Error handling is inconsistent in shape but well-coded. POS uses machine-readable string markers inside messages (PREVIOUS_DAY_SESSION_OPEN, SESSION_CLOSING_WORKFLOW, SUPERVISOR_AUTHORIZATION_REQUIRED) that the client string-matches. Structured error codes would serve an external client far better; PostingErrorCode shows the pattern already exists elsewhere in the codebase.
  • No API versioning at all. The /capabilities endpoint is the de-facto compatibility mechanism, and it is a good one — a standalone client that can lag the server by weeks needs it formalised, not replaced.
  • Rate limiting is in dry-run (ratelimit.dry-run=true) except login. Enabling enforcement without a POS exemption class would throttle a busy till.

07Database Audit

Verdict

A standalone POS can and should use the existing database through the existing API. There is no technical case in this codebase for a second POS database. 09Offline Capability Audit

Assessment

NOT OFFLINE READY

Not "partially". There is no offline mechanism of any kind in the repository.

What was checked, and found absent

  • No service worker. No manifest.json. No PWA plugin in vite.config.js.
  • No IndexedDB, no Dexie, no SQLite, no WASM database.
  • No navigator.onLine handling anywhere in src/.
  • No request queue, no outbox, no pending-sale persistence.
  • localStorage is used at 29 sites across the whole frontend. In POS it holds exactly three things: a device fingerprint (billbull:pos:device_fingerprint), the terminal ID per branch, and scanner configuration. No business data is cached.

What breaks the moment the API is unreachable

Everything. The product grid, /api/pos/resolve, customer lookup, session state, and checkout are all direct calls. There is no cart persistence — a page reload loses the cart. The axios interceptor's only network resilience is a single retry for GETs on HTTP 429.

What true offline POS would require

RequirementWhy it is hard here
Local catalog (products, barcodes, prices, tax)Needs the new /api/pos/catalog?since= delta endpoint. Tractable.
Local customer subsetTractable for walk-in + recent customers; unbounded for full A/R.
Offline invoice numberingHard. Numbering is a single server-side row lock. Offline sales need a reserved per-terminal block or a terminal-prefixed scheme — a schema and business-rule change with tax-authority implications.
Queued sales replayRequires idempotency on every POS write, not just checkout. Currently one endpoint has it.
Stock correctnessSerials, batches and FEFO cannot be reserved offline. Overselling is unavoidable without a reservation model — and the repo shows a study for one (BillBull-Stock-Reservation-Architecture-Study.html) but no implementation.
Store credit & voucher redemptionCannot be safely drawn down offline — double-spend across terminals.
Business Day / session integrityThe gates that make Z reports trustworthy all evaluate server-side against a single clock.
GL postingDeferred posting means a period could close before offline sales replay.

Realistic conflicts

Overselling the same batch or serial from two offline terminals; a voucher redeemed twice; an offline sale replaying into a closed accounting period or after Day Close; a customer's credit limit exceeded; invoice-number collision on replay.

Recommendation

Do not build offline mode now, and do not let the standalone-POS project become an offline project. They are separable, and conflating them roughly triples the scope and multiplies the financial-correctness risk. Build the standalone POS assuming connectivity, but make two cheap decisions now that keep the door open: (1) put every POS write behind an idempotency key, and (2) build the catalog as a versioned delta feed rather than a page-by-page fetch. Both are worth doing on their own merits — offline just becomes possible later instead of impossible.

A pragmatic middle step, worth far more than full offline for most retailers: resilient online — persist the cart to localStorage, show a connection banner, block checkout when disconnected, and retry safely on reconnect. Days of work, not months.

15Recommended Architecture

Recommendation

Option B. Extract POS into its own frontend application over a shared package, on the existing API and the existing database.

Why B

  • The backend is already the POS API. 20 controllers, 32 tables, a Business Day engine and 70 test classes exist. The gap is a client, not a platform. Option C rebuilds what already works; Option B ships what already works.
  • The seam is genuinely clean. POS uses no router, holds all its own state, and lives under three directories. That is not typical of a 15k-line component and it should be spent.
  • Sharing the arithmetic is non-negotiable. Tax, price floors, discount handling and receipt rendering all run client-side. If two copies exist, they will diverge, and the symptom will be a receipt whose VAT does not match the invoice. Only B structurally prevents that.
  • It fits the deployment model unchanged. DB-per-tenant, one JVM, nginx. A second static bundle at a second path is the entire infrastructure delta.
  • It is reversible. Every phase ships on its own and the existing /sales/pos route stays live until the new app has replaced it in production.

Why the alternatives are weaker

A trades three months of future correctness for three weeks of present convenience, in the one part of the system where correctness is money. C converts a working in-process transaction into a distributed one, doubles the operational footprint per tenant, and addresses no finding in this audit.

What to avoid

  • Do not copy vatMath.js, printGenerator.js, documentTemplateRenderer.js or the receipt templates. Share them.
  • Do not create POS-specific duplicates of sales, returns, vouchers, stock or GL logic on the backend.
  • Do not build a second database or a POS-specific sync layer.
  • Do not start with a desktop shell. Nothing in the hardware audit requires one.
  • Do not attempt offline in the same project as the extraction.
  • Do not refactor PosSessionService or PosCheckoutController internals during the move. Behaviour preservation is the constraint.

What stays unchanged

The entire com.billbull.backend.pos package's business logic. SalesInvoiceService, PostingEngineService, the stock-movement ledger, all 32 POS tables, Flyway, the DB-per-tenant model, and the print agent's protocol.

What must be refactored

  1. POSSales.jsx decomposed into a POS app shell + feature modules (cart, session, payments, reports, printing, settings, terminal).
  2. Direct sessionStorage reads inside POS routed through one context accessor.
  3. CorsConfig from a compiled allowlist to configuration.
  4. Auth: refresh token, terminal-bound, persistent storage appropriate to a till.
  5. POS endpoints given real permission checks at the controller boundary.
  6. Checkout returns a DTO.

What can be postponed

Offline mode. Desktop shell. Per-terminal settings. Store-specific pricing. Promotions/loyalty. Card-terminal integration. Per-branch invoice numbering. The TradePOS-vs-Console decision (extract whichever is production today; decide the other later).

20Final Recommendation

Build BillBull POS as a separate frontend application over a shared code package, consuming the existing BillBull API and the existing per-tenant database. Ship it as a browser/PWA application in kiosk mode. Keep the local print agent exactly as it is. Do not build a second backend, a second database, an offline layer or a desktop shell as part of this project.

The reason this is the right call is not architectural preference — it is what the audit found. The POS backend is already a coherent, well-tested, independently-shaped domain with 20 controllers and 32 tables. Every hardware integration BillBull actually has already works from a browser tab, by deliberate design. The POS UI is already router-independent and already lands as the default screen for three tenants. The work that remains is a client extraction and six targeted API additions — not a platform rebuild.

The single thing that could go badly wrong is the 15,818-line component, and the plan addresses it directly: decompose it in place, on the live route, behind golden-receipt tests, and only then move it. Everything else in the migration is comparatively routine.

Two items deserve to be scheduled independently of this project, because they are real today and this project neither causes nor fixes them: the non-transactional checkout sequence, and the committed default JWT secret alongside database credentials in the repository root.

Final Verdict
Recommended architecture
Option B — separate POS frontend over a shared packageTwo apps, one shared package, one API, one database per tenant. No new services, no new infrastructure.
POS application model
Browser / installable PWA in kiosk modeSame React 19 + Vite 7 stack, its own build, its own shell, no Retail sidebar.
Should POS become an .exe?
Not now — and not for hardware reasonsEvery device BillBull supports already works from a browser tab via the local print agent and HID input. Revisit a Tauri shell only if you later want offline, auto-update, or serial/OPOS devices. If you do, fix CORS first — the compiled allowlist blocks desktop origins outright.
Should POS have its own backend?
NoThe pos package already is one, in-process. Splitting it turns a working checkout transaction into a distributed one and doubles the per-tenant footprint for no measured benefit.
Should POS have its own database?
NoNothing in the codebase justifies it. POS writes sales, stock and GL through Retail domain services by design — that is why POS sales are financially correct.
Should POS share the BillBull API?
Yes — with six targeted additionsRefresh tokens · POS permissions at the controller boundary · configurable CORS · /api/pos/bootstrap · /api/pos/catalog?since= · checkout DTO. Everything else already exists.
Offline mode — now, later, or never?
Later, and only if the business case is provenThe system is NOT offline ready — zero mechanisms exist. Do "resilient online" now (cart persistence, connection banner, safe retry). Keep the door open by making every POS write idempotent and building the catalog as a delta feed. Full offline is a separate project with its own financial-correctness risks.
Biggest current blocker
POSSales.jsx — 15,818 linesCart, session, payments, printing, reports, settings and terminal registration in one component scope, with no frontend test coverage over the parts that matter.
Biggest architectural risk
Checkout is not one transactionFour committed steps with hand-written compensating deletes. A crash between stock posting and payment recording leaves a posted, unpaid invoice — the nightly PosOrphanedPaymentDetectionJob is evidence this already happens. A standalone client on a weaker network widens the window.
First step after approval
Phase 0 — build the safety netEnable the failsafe plugin so the two POS concurrency *IT tests actually run; add characterisation tests for cart totals, VAT and price floor; freeze golden ESC/POS and HTML receipt fixtures. Nothing moves until these are green. In parallel, answer Question 1: is TradePOS the future shell?
Estimated complexity
HighNot Very High — the backend needs no restructuring and the API already exists. The complexity is concentrated almost entirely in Phase 3, and it is manageable because it can be done in place with a rollback.
