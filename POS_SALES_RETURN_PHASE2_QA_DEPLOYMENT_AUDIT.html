01

Executive summary

Phase 2 was audited against code, against migration V111 executed on a restored tenant database, and against the live data of the testdb tenant (210 invoices, 20 approved returns, 2,368 customers). The verdict divides cleanly between the implementation and the data it will land on.

What holds

  • One owner for the invoice balance. sales_invoices.balance is written from exactly one place in the codebase — InvoiceBalanceService. No native SQL, no JPQL UPDATE and no other service writes it. There is no second economic definition.
  • The split reconciles. returnValue == unpaidPortion + paidPortion holds by construction, is asserted at runtime, and all four specified cases are covered by named tests.
  • The migration is safe. V111 applied in 73 ms on a restored copy of a real tenant, in correct order after V110, with zero row-count or AR drift and every historical row's new columns left NULL.
  • AR reconciles exactly. An independent recomputation of outstanding from the receipt, advance and return-credit ledgers matched the stored balance on 197 of 197 live invoices. Difference: 0.00.
  • All three unapproved decisions remain closed. Account 2062 does not exist anywhere in the codebase, there is no heldCustomerCredit term in the credit-limit calculation, and over-refund is structurally unreachable rather than merely unauthorised.
  • The client cannot influence the accounting. The frontend no longer sends refundAmount at all, and the server overwrites it unconditionally on approval.

What does not hold

Two findings are genuine, and neither is a code defect. Both are historical data that the corrected model reads differently than the old one did.

  • 8,400.00 of currently invisible AR will become visible for one customer. Three invoices are stamped PAID while carrying a full unpaid balance and zero completed receipts. Every AR surface excludes PAID, so today they are reported nowhere; the first canonical recompute touching them reclassifies them and the money appears. This is the §14 effect the brief anticipated — arriving through stale status rather than through legacy CUSTOMER_CREDIT.
  • 2,875.00 was settled as store credit against receivables the customer still owed. Three approved CREDIT_VOUCHER returns pre-date the split and handed back redeemable value for goods not fully paid for. Under Phase 2 that portion would have reduced AR instead.
The one piece of good news in the history

The brief's most feared population — legacy CUSTOMER_CREDIT returns, whose removal from the derived subtraction would make reported outstanding rise — is empty on this tenant. The analysis script returns total_ledger_credit_returns = 0 and total_outstanding_restatement = 0. The restatement risk from that specific mechanism is zero here, and must be re-measured per tenant before each rollout.

Scope of the evidence, stated plainly

The economics (§6–§12, §14) are validated by 148 focused tests and code inspection, not by return approvals executed through the running application. Driving an authenticated POS return approval end-to-end was outside what this environment allowed, and §3 forbids writing transactions against the tenant. The migration, schema, AR reconciliation and historical quantification are backed by execution against a real tenant database. Where a claim rests on tests rather than on live transactions, the section below says so.

The payment-list running balance now tells a slightly wrong history Warning

PaymentService.recomputeInvoiceBalances reconstructs "balance after this payment" by taking the current invoice balance as terminal and walking backwards, adding back payment amounts only. Now that the canonical balance also nets return credits, the reconstructed figure for payments that pre-date a return credit will be understated by that credit.

Display-only: it affects the invoiceBalance column shown on payment rows, not AR, not the GL, not the credit limit, and not any reported outstanding. It is also pre-existing logic, unchanged by Phase 2 — Phase 2 merely introduces a term it does not know about. It is listed as a warning rather than noise because a finance user reading a payment history on a returned invoice will see numbers that do not tie to the statement. No allocation rows exist on any tenant yet, so nothing is currently mis-displayed.

DRAFT invoices are counted by the aggregates but carry no receivable per-invoice Warning

effectiveOutstanding() returns ZERO for a DRAFT invoice — correctly, since a draft carries no receivable. But the three aggregate queries above exclude only CANCELLED and PAID, so drafts are included. On testdb that is 13 invoices carrying 22,702.52 inside the reported AR figure and inside the credit-limit check.

Pre-existing and not a Phase 2 regression: the aggregates are unchanged, and the DRAFT rule in effectiveOutstanding is new but is consumed only by the return split and the eligibility response. Its practical reach is therefore narrow — a return against a draft invoice would treat the whole return value as a paid portion. It is recorded because it is a genuine divergence between the per-invoice canonical definition and the aggregate surfaces, and because 22,702.52 of draft balance inflating a credit-limit check is a decision someone should make knowingly. Out of Phase 2's scope to change.

Return split validation

SalesReturnSettlementSplit.of(returnValue, invoiceOutstanding) computes unpaid = value.min(outstanding) and paid = value.subtract(unpaid), both at HALF_UP 2-decimal money scale and both floored at zero. The paid portion is defined as the residue, which is why the central invariant cannot be broken by arithmetic.

That is the conservative reading: it never credits AR for a receivable nobody can point to. Live check: 0 unlinked approved returns on this tenant, so the fallback is currently unexercised by real data.

Concurrency validation

The requirement is that two simultaneous returns against one invoice cannot both consume the same AR balance, and that this is achieved with database row locks rather than application-memory locking. Both are satisfied.

The lock strategy, as implemented

Two genuine PESSIMISTIC_WRITE locks, verified on the repository methods: 

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT r FROM SalesReturn r WHERE r.id = :id")
Optional<SalesReturn> findByIdForUpdate(Long id);           // SalesReturnRepository

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT s FROM SalesInvoice s WHERE s.invoiceNumber = :invoiceNumber")
Optional<SalesInvoice> findByInvoiceNumberForUpdate(String); // SalesInvoiceRepository

No synchronized block, no ReentrantLock and no in-memory guard participates. The ordering inside updateStatus is what makes this work:

  1. The return row is locked before status is read. A double-clicked or retried approval blocks here, then sees APPROVED and is rejected — so stock, journals and the cash payout each happen exactly once.
  2. Authorization is resolved from persisted state.
  3. assertReturnableQuantitiesStillAvailable takes the invoice row lock and returns the locked instance.
  4. resolveSettlementSplit computes the split from that same locked instance, inside the same lock. A split read from a second, unlocked query could be stale, and two concurrent returns would then both claim the same outstanding.
  5. Only then does anything move: stock, GL, allocation, and last of all the drawer cash-out.

A true two-transaction test would need a DB-backed test class — and note that this project has no failsafe plugin, so such a class must be named *Test, never *IT, or it silently never runs. The lock annotations and the call ordering are verified by inspection and are correct; the runtime behaviour under genuine contention is argued, not demonstrated. Listed as a warning in §19.

The server is unconditionally authoritative. resolveSettlementSplit runs before any settlement step and performs:

Settlement validation

The governing rule is that the refund method chooses where the paid portion goes and has no say over the unpaid portion. Every settlement leg draws on split.paidPortion() and returns early when it is zero.

MethodAmount movedPaid portion = 0Paid portion > 0
CASH_REFUNDgetRefundAmount(), overwritten to paidPortion at approvalRefused 422Drawer DROP_OUT for the paid portion

BANK_TRANSFERsplit.paidPortion()Refused 422Settlement journal for the paid portion

assertSettlementMethodMatchesSplit enforces both halves. When !split.hasPaidPortion() && method.movesValueToCustomer() it refuses with 422 and an explanation naming the invoice and its outstanding, directing the cashier to Customer Credit. Under the old model a cashier could press Cash Refund on a part-paid invoice, hand over the cash, and leave the customer still owing the full balance; that outcome is now unreachable rather than merely discouraged.

For a return where paidPortion = 0, no external money refund occurs — and this is guaranteed twice: the method is refused outright, and every settlement leg independently returns early on a zero or negative amount. The old fallback to totalAmount is gone. A return with no refund method at all is not gated by the split (aReturnWithNoRefundMethodIsNotGatedByTheSplit).

Covered by SalesReturnRefundSettlementTest (6), SalesReturnCashRefundServiceTest (9) and the settlement tests in SalesReturnApprovalSplitTest, including everyMoneyMovingMethodIsRefusedWhenNothingHasBeenPaidFor, customerCreditIsTheOneMethodAvailableOnAnUnpaidInvoice and aMoneyMovingMethodIsAllowedWhenThereIsAPaidPortionToMove.

The return journal was deliberately left unchanged, and no additional return journal was created. The invariant is produced by the interaction of the two existing journals rather than by per-method branching.

Verified in PostingEngineService.createJournalFromSalesReturn:

Return journal Cr AR = salesReturn.getTotalAmount() = returnValue Settlement Dr AR = split.paidPortion() = paidPortion ───────────────────────────────────────────────────────────────── Net AR reduction = returnValue − paidPortion = unpaidPortion ✓

The net credit to GL 1100 is therefore exactly the unpaid portion — which is exactly the amount the allocation row reduces the invoice balance by. GL AR and the AR sub-ledger agree by construction, with no new journal shape, no new account and no per-method branching. The allocation itself posts no GL entry of its own; doing so would double-count the receivable reduction, since the residue between the two journals already is that reduction.

Note that CREDIT_VOUCHER debits AR and credits liability account 2061 Credit Vouchers Issued, which already exists. No new GL account was introduced by Phase 2, and none was created during this audit.

Customer credit boundary

Held Customer Credit is not implemented. The boundary that exists instead is:

unpaid portion → AR allocation row (sales_return_credit_applications) paid portion + CUSTOMER_CREDIT → 422, refused: Decision 7 not approved

The refusal is deterministic (a pure function of the method and the split, with no timing, configuration or role dependency) and auditable: it is a ResponseStatusException(UNPROCESSABLE_ENTITY, …) carrying the return number and the exact paid portion, raised before any side effect, inside the transaction that would otherwise have written them. A refused return leaves nothing behind.

Letting the recomputation surface it — by doing nothing — is then the correct outcome, and any subsequent write-off is a manual journal voucher through the existing maker-checker flow (above the 10,000.00 AED threshold it requires a second approver, and 8,400.00 does not).
  • If the sales did not happen: invoice cancellation already has a reversal path (reverseJournalFromInvoiceCancellation), which for a fast-sale-posted invoice reverses revenue, VAT and the settlement leg.

Whichever is chosen, the posting date of any corrective entry is not a developer's choice.

21.5   PostgreSQL concurrency evidence — and a new Phase 2 defect

§19's warning 11 (“concurrency is argued, not demonstrated”) is closed by a new real-database test:

src/test/java/com/billbull/backend/sales/returns/SalesReturnApprovalConcurrencyTest.java

Named *Test, not *IT: there is no failsafe plugin in this build, so an *IT class is never executed by any phase. It is a @SpringBootTest against real PostgreSQL, driving the real SalesReturnService.updateStatus through the real PESSIMISTIC_WRITE lock. No repository is mocked, no H2 is substituted, no in-memory synchronisation stands in for the lock, and nothing asserts call order or generated SQL.

The fixture and the discriminator

invoice total = 10,000.00 completed receipts = 6,000.00 effective outstanding= 4,000.00 return A = 3,000.00 return B = 2,000.00 -> 5,000.00 of return value against 4,000.00 of receivable

Both threads rendezvous on a CyclicBarrier(2) immediately before the call, and the test records each thread's start and end instants and asserts the two windows overlapped — so a run in which the threads happened not to contend cannot pass as evidence. Quantities are deliberately not the constraint (10 units sold, 3 and 2 requested), so the only thing the two returns contend over is the outstanding balance. Both lines are DAMAGED (scrap), so nothing restocks and no unit cost or product master is involved.

The allocation total is the discriminator: unlocked, both threads read effectiveOutstanding = 4000 and allocate their full value, totalling 5,000.00 against a 4,000.00 receivable. Locked, the loser re-reads the outstanding after the winner commits and its min(returnValue, outstanding) cap trims it to the residue.

New Phase 2 defect, found by this test and fixed fixed

Every approved Sales Return silently lost its RETURN_APPROVED audit row. §15 lists “approval audit” as an acceptance criterion, and it did not work for realistic data.

AuditLogWriter.saveDomainEvent writes the same detail string to two columns: details, which is TEXT, and denialReason, which is a plain String and therefore varchar(255). The Phase 2 approval detail — return number, split figures, invoice, customer, business date, branch, authorization — is 354 characters for ordinary customer and branch names, and 222 even in the most minimal possible case. The INSERT therefore failed with value too long for type character varying(255), and because the writer is @Async the exception went to SimpleAsyncUncaughtExceptionHandler — so the approval succeeded and the audit row simply never existed.

Provenance. auditApproval does not exist at HEAD, so the long string is new code. AuditLogWriter is unmodified in the working tree (committed in 99b81c66), so the narrow column mirror is pre-existing. The defect is the interaction, and it is new. Corroboration: the QA clone holds zero RETURN_APPROVED rows (only one RETURN_AUTHORIZATION_DENIED), and the longest denial_reason across roughly 75,000 audit rows is 183 characters — so no pre-existing caller had ever reached the limit.

Fix. Truncate the 255-character mirror; details keeps the full, untruncated string. No schema change, no migration, no other behaviour touched, and no widening of a column on tenants that would then need a migration. The concurrency test now asserts both that each committed approval leaves exactly one RETURN_APPROVED row and that LENGTH(details) > 255, so the regression cannot return unnoticed.

Test data isolation (§13)

The test runs against billbull_concurrency_test, a throwaway TEMPLATE clone carrying a real tenant's schema and seeded chart of accounts. A test-method @Transactional rollback would not help — the service commits its own transaction — so @AfterEach deletes every row keyed on a per-run nanosecond id and assertNoResidue fails the test if anything survives. Verified after a clean run: zero rows across invoices, returns, allocations, journal entries, journal lines, ledger entries, receipts, customers, audit rows and branches.

Two incidental findings from building the isolation, recorded because they will bite the next person: Flyway cannot build this schema from an empty database (V1 is a baseline and Hibernate owns the DDL, so an empty database fails at V15 — hence the TEMPLATE clone), and an outlet-backfill runner creates an outlets row for any branch it finds on a later boot, which makes a leftover test branch undeletable. Cleanup removes the dependant first. A race in the test itself — the @Async audit write landing after cleanup had deleted it — appeared only under full-suite load and is waited out rather than tolerated.
