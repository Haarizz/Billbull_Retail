01Executive Summary

Fact The denomination count is a frontend-only artifact. The browser multiplies each denomination by its quantity in JavaScript floats, sends the resulting scalar to the server as closingCash, and the server never checks that scalar against the denomination map it is sent alongside. Everything downstream — variance, GL, reports — is built on a number the client asserted.

Fact Cash variance exists in exactly three places after a close: pos_sessions.cash_difference, a hand-built JSON string in pos_sessions.z_report_json, and a free-text audit sentence. It reaches no ledger account. There is no Cash Over/Short account anywhere in the codebase — a grep across all of financials/ returns nothing.

Fact The session-close journal entry posts Dr Bank / Cr Cash in Hand for the counted amount, not the expected amount. The variance is therefore silently absorbed as a permanent, unexplained residual balance in Cash in Hand — a debit stub on a shortage, a credit (negative asset) on an overage. Nothing ever clears it.

Fact The Z-Report does not carry the X-Report's variance forward. The persisted pos_day_closes row has an expected_cash column and no counted-cash or variance column at all. On screen, the Z-Report renders Cash Variance as a literal em-dash, and the Day Close checklist hardcodes { label: 'Cash Variance Within Limits', passed: true }.

Fact Where the Z-Report does compute a variance — the print/PDF view-model — it uses a different Expected Cash formula than the X-Report, omitting cash drops. Any day with a drawer drop prints two different variance figures for the same money.

Inference The pieces that are right suggest this was built correctly for sales and then never finished for cash: the Day Close row is DB-trigger-immutable, the session range resolution is genuinely single-source, and the correction system is a clean non-destructive overlay. The gap is specifically the cash-count leg.

The one-line answer

Denomination variance does not flow into the Z-Report. It is computed in the browser, stored once on the session row, excluded from the day-close snapshot's structured fields, rendered as — on screen, recomputed with a different formula in print, and absorbed into the Cash in Hand GL balance where nobody will ever look for it.

03The Actual Formula and Sign Convention

Expected Cash — the authoritative definition

private static BigDecimal computeExpectedCash(PosSession session, BigDecimal tenderCash,
                                              BigDecimal cashDropIn, BigDecimal cashDropOut) {
    return nz(session.getOpeningCash()).add(tenderCash).add(cashDropIn).subtract(cashDropOut);
}

PosSessionService.java:249–253 — shared by closeSession(), getXReport() and availableCashInDrawer().

So: openingFloat + cashTenderReceived + dropIn − dropOut. Where tenderCash is PaymentType.RECEIVED, cash-bucket, keyed on Payment.posSessionId, excluding only CANCELLED/FAILED — PENDING cash payments are counted as if collected. Cash refunds, cash-mode sales returns, and cash paid out through the returns module are all absent.

Cash Variance — the authoritative definition

BigDecimal variance = actualClosing.subtract(expectedCash).abs();  // unsigned, gate only

Convention: Actual Counted − Expected. Positive = overage/excess, negative = shortage. The frontend agrees (POSSales.jsx:8558, posReportViewModel.js:113). The supervisor-threshold gate uses the absolute value, so overage and shortage are treated identically for approval purposes.

What variance is treated as

Fact Report-only value and operational metadata. It is not an accounting adjustment, not a settlement value, not a ledger movement, and not — in practice — an approval item: PosSettings.cashVarianceThreshold defaults to BigDecimal.ZERO and the gate is written if (threshold.signum() > 0 && ...), so on a default install every variance closes unapproved.

Atomicity assessment

  • Safe Session closes but denominations not saved — cannot happen; same row, same transaction.
  • Safe Denominations saved but closure fails — cannot happen; both roll back together.
  • Broken GL fails after closure — expected behavior by design. The empty catch means the cash-pickup JE is silently skipped and never retried. There is no dead-letter, no flag, no log line.
  • Broken Audit orphan — @Async audit can commit while the close transaction rolls back, producing a SESSION_CLOSED audit row for a session that is still open.
  • Exposed Duplicate close — no idempotency key. The second request 400s only if the first already committed; concurrently, both pass the status check.
  • Exposed Re-submit — the "Close Session & Print Report" button carries no disabled attribute and no in-flight guard (POSSales.jsx:10812).

The reconciliation check checks the wrong thing

closeDay's "CASH reconciliation" (:2158–2175) compares the day's aggregate Expected Cash against the sum of each session's stored Expected Cash. Both sides come from the same formula over the same rows, so it is very nearly a tautology — it detects only drift in stored session state, never a physical cash discrepancy. A branch could close a day 50,000 short and this gate passes.

Fact A single printed Z-Report therefore contains three mutually inconsistent cash pictures: §0 lists per-session expected cash including drops; §4 "Cash Drawer Summary" prints an aggregate expected cash excluding drops; §1 totals denominations from the overlay-corrected map while the headline Actual Cash sums the uncorrected closingCash.

The intended equation, derived from code

Expected  = openingFloat + cashTenderRECEIVED + dropIn − dropOut
            (cash refunds, cash-mode returns and cash-outs via returns are absent)
Actual    = Σ(denomValue × qty)   — computed in the browser, asserted to the server
Variance  = Actual − Expected     — signed; + = overage, − = shortage

Z-Report headline (print) = Actual − (openingFloat + cashTender)
                            ≠ Σ per-session variance whenever any drop exists

The delta between the X and Z variance for the same day is exactly −(dropIn − dropOut). On a day where a cashier drops 5,000 to the safe, the Z-Report print reports a 5,000 overage that does not exist.

Worked example — overage

Expected 10,000 · Counted 10,200 · Variance +200. The close credits Cash 10,200 against 10,000 of debits, driving Cash in Hand 200 negative — a credit balance on an asset account. Repeated overages compound into a nonsensical balance sheet line. No income is recognized.

Two compounding GL asymmetries

  • Critical Opening float is never debited to Cash at session open. A grep of openSession() (:297–540) finds no postingEngine call. But the close credits the whole counted amount out of Cash — which includes the float. Every session therefore over-credits Cash in Hand by the float, independently of any variance.
  • High closingCash.signum() <= 0 returns null silently — a session closed with no denomination count posts no JE at all, so its cash sales stay debited in Cash in Hand with no offsetting pickup.

Inference Combining these: the Cash in Hand account balance in this system is not reconcilable to physical cash by construction. Its drift per session is (cashSales − countedCash), i.e. −(float + variance − drops), accumulated indefinitely with no clearing entry.

09Confirmed Issues

Each below is proven by the cited implementation, not inferred.

C-1 · Variance never reaches the ledger; it corrupts Cash in Hand

Critical
Location
PostingEngineService.java:3030–3053; called from PosSessionService.java:911–917
Evidence
The JE posts Dr Bank / Cr Cash for closingCash (counted), not expectedCash. A repo-wide search for Cash Over, OverShort, over_short returns zero hits — no Over/Short account exists in the chart of accounts or AccountSelectionRules.
Why wrong
Double-entry requires the difference between expected and counted cash to be recognized somewhere. Here it is netted into the credit side, leaving an unexplained residual in an asset account and no P&L recognition of till losses.
Repro
Open session float 0. One cash sale of 10,000. Close with denominations totalling 9,800. Query journal_lines for ref = 'SESSION_CLOSE-{id}' → Bank Dr 9,800 / Cash Cr 9,800. Trial-balance Cash in Hand is 200 higher than the drawer.
Impact
Cash in Hand permanently unreconcilable. Till shrinkage invisible to finance. Audit-blocking for any statutory review.

C-2 · closingCash is client-asserted and never validated against the denominations

Critical
Location
PosSessionController.java:151–155; PosSessionService.java:825
Evidence
closingCash and closingDenominations are read from the request body as independent values. closeSession never sums the map. The only server-side derivation of a total from denominations anywhere in the codebase is PosSessionDenominationCorrectionService.total() — used exclusively for corrections.
Why wrong
The physical count and the declared cash total are the same fact. Accepting them separately means the audit record can contradict itself, and a crafted request can declare any closing balance while showing a plausible breakdown.
Repro
POST /api/pos/sessions/{id}/close with {"closingCash": 10000, "closingDenominations": {"1000": 0, "500": 0}}. Session closes with closing_cash = 10000, closing_denominations_json = '{"1000":0,"500":0}', variance clean, GL posts 10,000.
Impact
Cash-count fraud with no detectable trace; the breakdown that would expose it is stored but never compared.

C-3 · pos_day_closes has no counted-cash or variance column

Critical
Location
PosDayClose.java:54–95; V53__pos_reports_module.sql:15–40
Evidence
Money columns are gross_sales, net_sales, total_discount, total_vat, cash_sales, card_sales, credit_sales, other_sales, expected_cash. Nothing for counted cash or variance. closeDay writes only setExpectedCash(expectedCashSessions) (:2194).
Why wrong
The Z-Report is the statutory end-of-day record. Its structured form cannot answer "did the day balance?" — that requires parsing a TEXT blob and re-implementing the arithmetic.
Repro
SELECT expected_cash FROM pos_day_closes WHERE close_date = … — there is no sibling column to compare it to.
Impact
No queryable day-level cash-integrity metric; back-office reporting on shrinkage is impossible without blob parsing.

C-5 · Cash refunds never reduce Expected Cash

High
Location
PosSessionService.java:249; PaymentRepository.java:123 vs :149
Evidence
tenderCash comes from sumTenderByModeForSessions, which filters paymentType = RECEIVED. aggregateRefunds (MADE) is computed and reported as totalRefunds but is never passed to computeExpectedCash. buildCashPosition makes the gap explicit: result.put("cashRefundsSupported", false) (:2438).
Why wrong
A cash refund removes notes from the drawer. Expected Cash must fall by the same amount or the count can never balance.
Repro
Cash sale 500, then cash refund 200 in the same session. Drawer holds 300. Expected Cash reports 500. Permanent −200 variance.
Impact
Systematic false shortages proportional to refund volume; cashiers learn to ignore the variance figure entirely.

10Potential Risks

Conditions required, not yet proven to fire in production.

RiskSevCondition requiredWhat to verify
Float arithmetic in the count
calculateDenominationTotal sums parseFloat(note) * count in IEEE-754 doubles (POSSales.jsx:2693, posReportViewModel.js:39).		 Med Counts involving 0.05 / 0.10 / 0.25 in quantity. e.g. 3 × 0.10 → 0.30000000000000004. The tail reaches the server, becomes a BigDecimal, and cashDifference is computed before the NUMERIC(15,2) round-trip, so z_report_json can carry a non-zero variance where the DB stores 0.00. Check a session closed with coin quantities.
PENDING cash payments inflate Expected Cash Med A Payment row in PENDING with a cash mode and this posSessionId. The query excludes only CANCELLED/FAILED (PaymentRepository:126). Whether the POS checkout path can ever leave a cash payment PENDING. If yes, false shortages follow.
Duplicate X-Report snapshots Low Two concurrent generateXReport calls both observe xReportGeneratedAt == null. pos_x_report_snapshots has a unique index on report_number only, not session_id. Whether the sequence service serializes enough to make this unreachable.
Report rendering is not versioned Med The pos_day_closes row is DB-immutable, but every displayed figure is recomputed by posReportViewModel.js at view time. Changing the frontend formula retroactively changes what a historical Z-Report prints. report_version is set to the literal "1.0" and never consulted.

11Data Integrity and Session Isolation

Sound Session attribution is explicit and correct. Every cash-side aggregate keys on an authoritative column rather than resolving through invoices:

  • Tender and refunds → Payment.posSessionId (the collecting session), documented at PosSessionService:820–823. A delivery order rung up weeks ago and settled today lands in today's drawer, which is right.
  • Cash movements → PosCashMovement.posSession FK.
  • Advances → ReceiptVoucher.posSessionId.
  • Denominations → columns on pos_sessions itself.
  • Day membership → pos_sessions.day_close_id, stamped at closeDay:2210–2214.

No indirect session resolution through invoice → terminal → cashier exists on this path. Cross-session leakage of denomination data is not reachable.

Sound Reopening is impossible. CLOSED is terminal — closeSession rejects it (:791), no reopen endpoint exists, and PosDayCloseLockTriggerInstaller installs a BEFORE UPDATE OR DELETE trigger that rejects any mutation of a pos_day_closes row.

Weak One real isolation defect: the X-Report filters Sales Returns to the session's own invoices (buildSessionReturnsSummary, :1668, with an explicit comment about cross-session leakage) — but returns still carry no posSessionId and no payment mode, which is the root cause of C-5. The isolation was patched at the reporting layer without fixing the missing linkage.

14Recommended Improvements

Recommendation Ordered by priority. None of these were applied — no code was modified during this audit.

P0 — Financial and reconciliation correctness

  1. Derive closingCash server-side from the denomination map. Accept closingDenominations as the only cash-count input; compute the total with BigDecimal in closeSession exactly as PosSessionDenominationCorrectionService.total() already does. Treat a client-sent closingCash as advisory and reject on mismatch, or drop the field. Fixes C-2 and the float-arithmetic risk in one change.
  2. Post the variance to a Cash Over/Short account. Change createJournalFromSessionClose to take expected and counted separately: Dr Bank (counted) / Dr-or-Cr Cash Over / Short (variance) / Cr Cash in Hand (expected). Add the account to SystemAccountSeeder and AccountSelectionRules. Fixes C-1.
  3. Post the opening float at session open. Dr Cash in Hand / Cr Bank for openingCash, mirroring the close. Without it the Over/Short line in (2) will absorb the float.
  4. Subtract cash refunds from Expected Cash. Add cashRefunds to computeExpectedCash, sourced from aggregateRefunds(...).byBucket.get("cash"). Requires giving SalesReturn a payment mode and a posSessionId — the same missing linkage buildCashPosition already flags. Fixes C-5.

P1 — Audit integrity

  1. Add structured columns to pos_day_closes: counted_cash, cash_variance, variance_session_count, reconciliation_status. New Flyway migration, additive and to_regclass-guarded per repo convention. Fixes C-3.
  2. Move the X-Report snapshot to close time, or add a second snapshot type taken at close that includes the denomination block and variance. Fixes C-6.

18Final Verdict

The source-of-truth hierarchy, as actually implemented

Payment rows (posSessionId)  ─┐
PosCashMovement (ACTIVE)     ─┼─▶ computeExpectedCash() ──▶ pos_sessions.expected_cash
pos_sessions.opening_cash    ─┘         (backend, authoritative, recomputed at close)

Browser denomination inputs ──▶ JS float total ──▶ client-asserted closingCash
                                                      │
                                                      ├─▶ pos_sessions.closing_cash
                                                      ├─▶ pos_sessions.cash_difference   (= closing − expected)
                                                      └─▶ GL: Cr Cash in Hand            (variance buried here)

pos_sessions.closing_denominations_json ──▶ display only, never summed server-side
      └─ overlay: PosSessionDenominationCorrection ──▶ display only, diverges from closing_cash

pos_day_closes ──▶ expected_cash only  +  z_report_json blob
      └─▶ Z-Report render: frontend recomputes everything, with a different formula

The chain has two authoritative links and one broken one. Expected Cash is genuinely single-source and correct within its own definition. The persisted session record is immutable and well-attributed. But counted cash is asserted by the client and never verified, and from that point on the variance is carried by convention rather than by structure — no ledger account, no day-close column, no report field, no approval record.

How does denomination variance from the X-Report actually flow into the Z-Report?

It doesn't. The X-Report's variance is computed in the browser and never persisted as part of any X-Report. At close, the session row records a variance that no Z-Report code path reads. pos_day_closes has no field for it. The on-screen Z-Report prints —. The printed Z-Report recomputes a variance from scratch using a formula that omits cash drops, so it disagrees with the X-Report on any day with a safe drop.

What happens to it financially? Nothing recognizes it. The session-close journal entry credits Cash in Hand by the counted amount rather than the expected amount, so a shortage leaves a permanent debit residual in Cash in Hand and an overage drives that asset account negative. No expense, no income, no Over/Short account — the account does not exist in this codebase. Combined with the opening float never being debited at session open, the GL Cash balance drifts by (cashSales − countedCash) every single session, whether or not there was a variance.

What happens to it operationally? It is shown to the cashier live, stored on the session, written into a free-text audit sentence, and then dropped. The supervisor threshold that would gate it defaults to zero — disabled. The approval flag that would override it is an unauthenticated JSON boolean the UI never sends. The Day Close checklist item that would surface it is hardcoded to pass.

What should change to make closing audit-safe? Five things, in order. Compute the counted total server-side from the denomination map and reject any client-supplied total that disagrees. Introduce a Cash Over/Short account and post the variance to it, with the float posted at session open so the entry balances. Deduct cash refunds from Expected Cash. Add counted_cash and cash_variance columns to pos_day_closes and have the frontend read backend-computed figures instead of recomputing them. Replace the supervisorApproved boolean with a credential-backed grant that records the approver. Until at least the first two land, the cash-reconciliation figures this system produces should be treated as advisory, not as accounting.
