BillBull POS — Session Roaming Implementation Roadmap

Status: Engineering implementation plan, derived from the approved pos-session-roaming-architecture-blueprint.html. This document does not revisit or alter any architectural decision or business rule from that blueprint — it converts the blueprint's six macro-phases (Chapter 14) into sprint-sized engineering phases, each independently deployable, each rollback-safe, none of them breaking existing POS functionality for any customer at any point in the rollout.

How to read this document: each phase below maps to one of the blueprint's six macro-phases (noted in the phase header). Phases are sized to be completable and independently shippable within roughly one sprint by a small backend/frontend pair, though team velocity will vary. No phase depends on a *later* phase; every phase depends only on phases before it.

Phase 1 — Schema Foundation

1. Objective

Introduce every new database structure the redesign needs, purely additively, with no application code yet reading or writing to it in a way that affects behavior.

2. Components Affected

  • Backend: none behaviorally — JPA entity classes are extended with new nullable fields/associations, unused by any service yet.
  • Frontend: not affected.
  • Database: yes — this phase is entirely a database change.
  • APIs: not affected.
  • Services: not affected.
  • Reports: not affected.
  • Security: not affected.

3. Files/Modules Likely to Change

  • New Flyway migration file(s) under billbull-backend/src/main/resources/db/migration/.
  • pos/session/PosSession.java — add nullable ownerUserId field, nullable current-hosting refresh timestamp.
  • pos/session/PosCashMovement.java — add nullable performedByUserId field.
  • pos/terminal/PosTerminal.java — add fields to support the future LOCKED status (lockedReason, lockedAt, lockedSessionId), unused this phase.
  • New entity classes: PosSessionTerminalHistory (new package or under pos/session/), PosSessionTransferLog (new package or under pos/session/ or a new pos/transfer/).
  • New repositories for the two new entities.

4. Database Migration Required

Yes. New Flyway migration(s):

  • ALTER TABLE pos_sessions ADD COLUMN owner_user_id BIGINT NULL (no FK constraint enforced yet, or a nullable FK — team's choice, but must not be NOT NULL).
  • ALTER TABLE pos_cash_movements ADD COLUMN performed_by_user_id BIGINT NULL.
  • ALTER TABLE pos_terminals ADD COLUMN locked_reason VARCHAR NULL, locked_at TIMESTAMP NULL, locked_session_id BIGINT NULL.
  • CREATE TABLE pos_session_terminal_history (...) — session_id, terminal_id, counter_id/counter_name snapshot, started_at, ended_at (nullable while segment is open).
  • CREATE TABLE pos_session_transfer_log (...) — session_id, from_terminal_id, to_terminal_id, initiated_by_user_id, supervisor_authorized boolean, created_at.

All statements idempotent-guarded (to_regclass/IF NOT EXISTS), consistent with the repo's existing migration convention (per CLAUDE.md).

5. Backward Compatibility Considerations

Fully additive — every new column is nullable, every new table is unpopulated at first. No existing query, report, or API response shape changes. ddl-auto=update and Flyway continue to coexist per the existing project convention; this phase adds nothing that conflicts with that.

6. Risks

  • Low. The only real risk is a migration failing to apply cleanly against a tenant database with unexpected existing state (e.g., a column name collision) — mitigated by the idempotent-guard convention already standard in this codebase.
  • Migration runtime on large pos_sessions/pos_cash_movements tables adding nullable columns is a fast metadata-only operation in PostgreSQL (no table rewrite for a nullable column with no default), so no downtime risk.

7. Testing Strategy

  • Migration applies cleanly on a fresh database and on a copy of an existing tenant database (staging).
  • Existing full backend test suite (mvn -o test) passes unchanged — no existing test should reference these new fields, so this is purely a regression check that nothing broke.
  • Manual verification: existing POS flows (open/close session, checkout, X/Z-report) exercised end-to-end on a staging environment post-migration, confirming zero behavioral difference from pre-migration.

8. Rollback Strategy

Drop the new columns/tables via a follow-up migration, or simply leave them in place unused (since nothing reads them yet, leaving them is lower-risk than a reverse migration). Rollback of the *application* deploy (reverting the JPA entity changes) is a standard code rollback with no data implications, since Hibernate will simply stop mapping the new fields.

9. Definition of Done

  • Migration applied successfully to all tenant databases (per the multi-tenant profile list in CLAUDE.md).
  • New entity classes and repositories merged, unused by any service.
  • Full existing test suite green.
  • No change observed in any existing POS screen or report during staging verification.

Phase 2 — Backend Read/Write Plumbing for New Schema

1. Objective

Give the backend the ability to write to the new tables/columns introduced in Phase 1, still without any existing behavior depending on them — this phase proves the plumbing works in isolation before Phase 3's backfill and Phase 4's shadow logic build on top of it.

2. Components Affected

  • Backend: yes — new repository methods, no service-level behavior change.
  • Frontend: not affected.
  • Database: no new migration (reuses Phase 1's schema).
  • APIs: not affected — no new endpoints exposed yet.
  • Services: a small, isolated new internal-only service (or repository-level helper) capable of writing a PosSessionTerminalHistory row and a PosSessionTransferLog row — invoked by nothing in production code yet, exercised only by tests.
  • Reports: not affected.
  • Security: not affected.

3. Files/Modules Likely to Change

  • pos/session/PosSessionTerminalHistoryRepository.java (new), pos/session/PosSessionTransferLogRepository.java (new) — query methods needed later (find open segment for a session, find history for a session).
  • Small internal helper/service class encapsulating "open a new history segment" / "close the current history segment" write operations, unit-tested in isolation.

4. Database Migration Required

None (Phase 1 covered schema).

5. Backward Compatibility Considerations

None — no existing code path is touched.

6. Risks

Minimal — isolated, untriggered code. The only risk is scope creep (accidentally wiring this into a live path early) — explicitly out of scope for this phase.

7. Testing Strategy

  • Unit tests for the new repository methods and helper service, following the existing Mockito-based test convention (@ExtendWith(MockitoExtension.class), builder-method fixtures per CLAUDE.md's testing conventions).
  • No integration/end-to-end testing needed yet, since nothing in the running application calls this code.

8. Rollback Strategy

Trivial — revert the code change; nothing else in the system references it.

9. Definition of Done

  • New repositories and helper service merged with unit test coverage.
  • Code review confirms nothing production-facing invokes these new classes yet.

Phase 3 — Ownership Backfill

1. Objective

Populate pos_sessions.owner_user_id and pos_cash_movements.performed_by_user_id for all historical and ongoing rows, so that by the time Phase 4's resolution logic needs a reliable ownerUserId, it is already populated for every session, not just new ones going forward.

2. Components Affected

  • Backend: yes — a one-time (or idempotent, safely re-runnable) backfill job.
  • Frontend: not affected.
  • Database: data-only change (UPDATE statements via the backfill job), no new schema.
  • APIs: not affected.
  • Services: new backfill job/runner, modeled after the existing PosCounterBackfillRunner (ApplicationRunner) pattern already used in this codebase for an analogous prior backfill.
  • Reports: not affected.
  • Security: not affected.

3. Files/Modules Likely to Change

  • New PosSessionOwnershipBackfillRunner.java (or similar), following the existing pos/counter/PosCounterBackfillRunner.java pattern (idempotent ApplicationRunner, safe to run on every startup, no-ops once complete).
  • Resolves PosSession.openedBy (username string) → users.id via the existing user-lookup mechanism already used by resolveDisplayName in PosSessionService.
  • Same for PosCashMovement.performedBy.

4. Database Migration Required

No schema migration — this is a data backfill executed by application code at startup (matching the existing PosCounterBackfillRunner precedent, not a Flyway UPDATE script), so it can safely handle username-resolution edge cases (renamed/deactivated users) in Java rather than brittle SQL.

5. Backward Compatibility Considerations

Fully additive — openedBy/performedBy string columns are untouched and remain authoritative for any code that still reads them (all existing code, at this point in the rollout). Rows that fail to resolve cleanly (e.g., a username with no matching current user) are left with a null owner_user_id and logged for manual follow-up — never blocking, per the blueprint's explicit risk mitigation (Chapter 15).

6. Risks

  • A username that no longer resolves to exactly one user (renamed, deactivated, or ambiguous) leaves owner_user_id null for that historical session — acceptable and expected, called out explicitly in the blueprint. Mitigation: log every unresolved row for manual/administrative follow-up; do not fail the backfill run over it.
  • Backfill running against a very large pos_sessions table taking longer than expected on first boot. Mitigation: batch the backfill (process in chunks, following the same idempotent-and-resumable pattern as PosCounterBackfillRunner), and make it safe to run across multiple application restarts if it doesn't finish in one.

7. Testing Strategy

  • Unit tests for the username→userId resolution logic, including the ambiguous/unresolvable case.
  • Staging run against a full copy of a real tenant database, verifying resolution rate (expect near-100% for active users, with any gaps manually reviewed before sign-off).
  • Confirm re-running the backfill after it has already completed is a safe no-op (idempotency check).

8. Rollback Strategy

Set owner_user_id/performed_by_user_id back to null (or simply stop running the backfill runner) — since nothing yet depends on these columns being populated, this is a zero-risk rollback.

9. Definition of Done

  • Backfill runner merged and verified idempotent.
  • Staging backfill run completed with resolution rate reviewed and any gaps documented.
  • Full existing test suite green; no behavior change observed anywhere.

Phase 4 — Session Resolution Service (Shadow Mode)

1. Objective

Ship the new user-first Session Resolution Service described in Chapter 12 of the blueprint, but running only in shadow mode — computing its answer on every relevant request and logging it for comparison, without any caller (frontend or backend) acting on its output yet.

2. Components Affected

  • Backend: yes — new service class, invoked internally alongside (not instead of) the existing terminal-first lookup.
  • Frontend: not affected — no frontend change in this phase.
  • Database: no new migration.
  • APIs: no new externally-facing endpoint yet (or, if exposed, explicitly marked internal/unused-by-clients — see Definition of Done).
  • Services: new PosSessionResolutionService (design per blueprint Chapter 12), consuming owner_user_id (Phase 1-3) to answer "does this user have an active session in this branch, and where is it hosted."
  • Reports: not affected.
  • Security: relies on OwnershipContextHolder.currentUserId() (already present and wired app-wide per the architecture audit) — no new security surface introduced, only a new consumer of an existing one.

3. Files/Modules Likely to Change

  • New pos/session/PosSessionResolutionService.java.
  • pos/session/PosSessionRepository.java — new query method(s): find active (OPEN/SUSPENDED) session by ownerUserId + branchId.
  • pos/session/PosSessionController.java — existing GET /sessions/active endpoint internally calls the new service in parallel with the legacy terminal-first lookup (Phase 4's shadow logging only compares results; the endpoint's actual response is still driven by the legacy path this phase).
  • New structured logging/metrics emission comparing legacy vs. new resolution outcomes (Phase 5 consumes this).

4. Database Migration Required

None.

5. Backward Compatibility Considerations

The externally-visible behavior of every existing endpoint is unchanged in this phase — the new service's output is logged, never returned to a caller or acted upon. This is the phase most explicitly designed (per blueprint Chapter 14) to carry zero user-facing risk while still exercising the new logic against real production traffic patterns.

6. Risks

  • Performance: running two resolution paths per request (legacy + shadow) doubles the query load for this one lookup. Mitigation: the shadow call is read-only and can be run asynchronously/best-effort (e.g., logged but not required to complete before the response returns), and this is a low-frequency call (once per POS session-check, not per-request-hot-path) — flagged as low risk but explicitly tested for latency impact.
  • False mismatches between legacy and shadow logic due to genuinely-expected differences (e.g., a session backfilled with a null owner_user_id from Phase 3) rather than real bugs. Mitigation: Phase 5's analysis explicitly accounts for and filters out known-expected gaps before treating a mismatch as a real signal.

7. Testing Strategy

  • Unit tests for PosSessionResolutionService covering every branch of its decision tree (hosted-here, hosted-elsewhere, suspended-unhosted, none) using fixture sessions.
  • Staging: run against synthetic multi-session, multi-terminal scenarios (including sessions with a null owner_user_id, to confirm graceful "no match" behavior rather than an error).
  • Latency/load testing to confirm the shadow call does not measurably slow down the existing GET /sessions/active response time in production-scale traffic.

8. Rollback Strategy

Disable the shadow-call invocation (config flag or simple code removal) — since it is a pure side-effect (logging), removing it has zero data or behavioral consequence.

9. Definition of Done

  • PosSessionResolutionService merged, unit-tested across all decision branches.
  • Shadow logging live in production for at least one full business-day cycle across a representative sample of branches.
  • Latency impact confirmed negligible.
  • No change in any existing endpoint's actual response.

Phase 5 — Shadow-Mode Validation & Metrics

1. Objective

Build confidence, using real production data gathered by Phase 4, that the new user-first resolution logic agrees with the legacy terminal-first logic in every case where they *should* agree (i.e., every session that has never been transferred, which — before Phase 8 ships — is every session). This is the gating checkpoint before Phase 6 introduces any new user-facing capability.

2. Components Affected

  • Backend: yes — a lightweight comparison/metrics job or dashboard query, consuming Phase 4's shadow logs.
  • Frontend: not affected.
  • Database: none, or an optional small metrics/discrepancy table if the team prefers persisted tracking over log-scraping (implementation detail, not architecturally required).
  • APIs: not affected.
  • Services: a comparison utility (could be as simple as a scheduled report over existing logs, or a dedicated small service — sizing left to the implementing team, since the blueprint does not mandate a specific mechanism here).
  • Reports: an internal-only engineering report (discrepancy count/rate), not a customer-facing report.
  • Security: not affected.

3. Files/Modules Likely to Change

  • Depends on chosen mechanism — likely a small analysis script/scheduled job reading Phase 4's structured logs, or a lightweight new repository query if a persisted discrepancy table is used.

4. Database Migration Required

None, unless the team opts for a persisted discrepancy-tracking table (optional, additive if so).

5. Backward Compatibility Considerations

None — this phase is purely observational tooling.

6. Risks

  • The main risk this phase exists to *retire*, not create: if discrepancies are found, this is exactly the safe, low-stakes place to find and fix them, before Phase 6 makes the new logic load-bearing for any real user action.

7. Testing Strategy

  • Review discrepancy reports daily during an initial observation window (team-determined length, e.g., one to two full weeks spanning multiple Day-Close cycles) across all branches.
  • Any discrepancy is root-caused and either (a) confirmed as an expected/explainable gap (e.g., an unresolved backfill row) or (b) fixed in the resolution service before proceeding.

8. Rollback Strategy

Not applicable in the traditional sense — this phase produces no deployable artifact beyond the observation tooling from Phase 4, which is already independently rollback-safe.

9. Definition of Done

  • Zero unexplained discrepancies between legacy and shadow resolution across a full observation window.
  • Explicit written sign-off (even informal — a documented go/no-go decision) that the Session Resolution Service is trusted to become load-bearing in the next phase.

Phase 6 — Terminal LOCKED Status & Lock/Unlock Backend

1. Objective

Introduce the LOCKED terminal status and its supporting lock/unlock backend logic (Chapter 5 and Chapter 10 of the blueprint), reachable only by new, not-yet-wired-in code paths — no existing flow can cause a terminal to become LOCKED yet.

2. Components Affected

  • Backend: yes — status enum extension, new service methods.
  • Frontend: not affected yet (the Locked-screen UI ships in Phase 8).
  • Database: none new (Phase 1 already added the supporting columns).
  • APIs: new endpoint(s) for unlock-acknowledgment and supervisor force-unlock, unused by any client yet.
  • Services: PosTerminalService/a new PosTerminalLockService gains lock/unlock methods; existing status-transition validation (PosTerminalStatus enum handling in PosTerminalService/PosTerminalController) is extended to recognize LOCKED as a valid state.
  • Reports: not affected.
  • Security: new authorization rule — self-service unlock requires the requester to be the same user whose session vacated the terminal; supervisor force-unlock requires the same supervisor-auth mechanism already used for takeover (PosSettingsController.verify-pin/supervisor-auth).

3. Files/Modules Likely to Change

  • pos/terminal/PosTerminalStatus.java — add LOCKED to the existing enum (NEW, PENDING_REGISTRATION, ACTIVE, IDLE, OFFLINE, INACTIVE, MAINTENANCE, BLOCKED, STALE, DECOMMISSIONED, ARCHIVED).
  • pos/terminal/PosTerminalService.java — new lock(terminalId, sessionId, reason) / unlock(terminalId, actingUserId) / forceUnlock(terminalId, supervisorAuth) methods.
  • pos/terminal/PosTerminalController.java — new endpoints, e.g. POST /{terminalId}/acknowledge-lock, POST /{terminalId}/force-unlock.
  • pos/terminal/PosTerminalService.java archive/decommission guards updated per blueprint Chapter 5's table (guard condition extended to also consider LOCKED), but still unreachable via any real flow this phase since nothing produces a LOCKED terminal yet outside of tests.
  • PosTerminalLifecycleService.java — confirm LOCKED terminals are handled sensibly by the existing auto-archive sweep (a LOCKED-but-vacated terminal should likely be eligible for the same staleness consideration as OFFLINE, per the team's judgment — flagged for explicit decision during implementation, not pre-decided by the architecture blueprint).

4. Database Migration Required

None new (columns added in Phase 1; this phase only adds a new permitted value to an existing string/enum-backed status column, which requires no schema change in this codebase's existing PosTerminalStatus implementation pattern — confirm no DB-level CHECK constraint on pos_terminals.status needs updating, since one exists per V28__pos_terminal_status_offline_fix.sql; if so, an additive migration to widen that CHECK constraint is required here).

5. Backward Compatibility Considerations

No existing terminal can transition into LOCKED through any currently-reachable code path in this phase — it is purely new capability, dormant until Phase 8 wires the Transfer Service (Phase 7) into a real user flow. Existing terminal status handling (heartbeat, archive, decommission) continues to behave identically for every terminal that never enters the new state.

6. Risks

  • If a DB-level CHECK constraint on pos_terminals.status exists (per V28) and is not updated, any attempt to persist LOCKED fails at the database layer rather than gracefully — mitigation: explicitly verify and widen this constraint as part of this phase's migration, and cover it with a dedicated test that persists a LOCKED terminal end-to-end.
  • Scope risk: it's tempting to wire the lock trigger in early — explicitly out of scope for this phase, deferred to Phase 7/8, to keep this phase's blast radius to "new dormant capability only."

7. Testing Strategy

  • Unit tests for the new status-transition logic, including the CHECK-constraint-safe persistence test above.
  • Unit tests for the unlock authorization rules (self-service vs. supervisor).
  • Regression: full existing terminal lifecycle test suite (PosSessionServiceTest, terminal-related tests per CLAUDE.md's test conventions) remains green.

8. Rollback Strategy

Revert the enum addition and new endpoints; since no terminal can reach LOCKED yet, there is no data to reconcile — a pure code rollback.

9. Definition of Done

  • LOCKED status persists and round-trips correctly, including through any DB CHECK constraint.
  • Unlock endpoints merged and unit-tested, unused by any client.
  • Full existing test suite green.

Phase 7 — Session Transfer Service (Backend, Feature-Flagged Off)

1. Objective

Ship the complete, atomic Session Transfer Service (Chapter 7 of the blueprint) end-to-end on the backend, gated behind a feature flag defaulting to off across all branches — the capability exists and is fully testable, but cannot be triggered in production yet.

2. Components Affected

  • Backend: yes — this is the single largest backend change in the roadmap.
  • Frontend: not affected yet (Phase 8 ships the UI).
  • Database: no new schema (Phase 1 covered it); this phase is the first to actually write to pos_session_terminal_history and pos_session_transfer_log from a real (flagged) code path.
  • APIs: new endpoint, e.g. POST /sessions/{id}/transfer, flagged off (returns not-yet-available, or is simply unreachable from any client until Phase 8).
  • Services: new PosSessionTransferService, composing the atomic detach/attach/history/audit transaction exactly as specified in the blueprint's sequence diagram.
  • Reports: not affected yet (Phase 12 consumes the new history data).
  • Security: new authorization checks — same-owner transfer requires only normal auth; different-owner transfer requires supervisor authorization, reusing the existing takeover credential-check mechanism (PosSettingsController).

3. Files/Modules Likely to Change

  • New pos/session/PosSessionTransferService.java (or a new pos/transfer/ package) — the atomic transaction described in blueprint Chapter 7: re-verify session state, acquire transfer guard, detach source (lock it via Phase 6's lock method), close/open history segments (Phase 2's plumbing), attach target, refresh session's denormalized terminal/counter fields, write the transfer log row, release the guard.
  • pos/session/PosSessionController.java — new POST /{id}/transfer endpoint, behind a feature flag (e.g., PosSettings-level or a global config flag — team's choice of flag mechanism).
  • pos/session/PosSessionRepository.java — the atomic compare-and-swap query for the transfer guard, modeled directly on the existing setOpenSession/clearOpenSession pattern in PosTerminalRepository.java.
  • pos/terminal/PosTerminalActivityService.java — confirmed (per the dependency audit) to key its six call sites purely on terminalId; no change required here, since once the Transfer Service keeps a session's terminalId field live (this phase), these call sites automatically become correct without modification.

4. Database Migration Required

None new — reuses Phase 1's schema exclusively.

5. Backward Compatibility Considerations

With the feature flag off, this endpoint is entirely inert in production — zero behavioral difference for any existing customer. This is the phase where the architecture's core new capability first becomes real, and the flag is the explicit safety valve the blueprint calls for (Chapter 14, Phase 3).

6. Risks

  • This is the highest-complexity single phase in the roadmap — the atomic transaction has several moving parts (lock, history, audit, denormalized-field refresh) that must all commit or all roll back together. Mitigation: exhaustive unit and integration testing of every failure branch in Chapter 7's "every scenario" list (re-verification failure, concurrent transfer race, mid-flight network drop) before this phase is considered done — even though the flag keeps it off in production, it must be *correct*, not just *dormant*, before Phase 8 turns it on.
  • Race condition between a transfer and a concurrent close/suspend of the same session (explicitly called out in blueprint Chapter 10/15). Mitigation: the re-verification step inside the atomic transaction, tested explicitly with a concurrent-modification integration test.

7. Testing Strategy

  • Unit tests for every branch of the transfer transaction, including forced-failure injection at each step to confirm full rollback.
  • Integration tests simulating concurrent transfer attempts for the same session (two threads/requests racing) to confirm exactly one succeeds and the loser receives a clean, actionable failure.
  • Integration test simulating a transfer racing a concurrent closeSession/suspendSession call, confirming the transfer cleanly fails rather than committing against stale state.
  • Manual QA on a staging environment with the flag enabled for a test branch only, exercising the full transfer flow via direct API calls (Postman/equivalent) since no UI exists yet.

8. Rollback Strategy

The feature flag is the primary rollback mechanism — disabling it immediately returns the system to Phase 6's behavior with zero data-cleanup required, since a disabled flag means the endpoint was never reachable. A full code rollback (reverting the service/endpoint) remains available as a secondary option and is equally safe, since nothing else depends on this service yet.

9. Definition of Done

  • PosSessionTransferService merged with full unit/integration coverage of every scenario in blueprint Chapter 7.
  • Concurrency tests (racing transfers, transfer-vs-close) passing.
  • Manually verified end-to-end via direct API calls against a staging branch with the flag enabled.
  • Flag remains off in every production branch at the close of this phase.

Phase 8 — Transfer UI & Pilot Branch Enablement

1. Objective

Ship the frontend Transfer Confirmation and Locked-screen experiences (blueprint Chapter 13), and enable the feature flag from Phase 7 for a single pilot branch — this is the first phase where any real cashier can experience session roaming.

2. Components Affected

  • Backend: minor — flag enablement configuration for the pilot branch only; the LOCKED-notice field added to the heartbeat response (per blueprint Chapter 13: "the heartbeat response simply gains a 'you are now LOCKED' field").
  • Frontend: yes — the primary work of this phase.
  • Database: none new.
  • APIs: POST /terminals/{terminalId}/heartbeat response shape gains an optional new field (additive, non-breaking for any client not yet reading it); the transfer endpoint from Phase 7 becomes reachable for the pilot branch.
  • Services: none new beyond Phase 6/7.
  • Reports: not affected.
  • Security: the existing supervisor-auth challenge (already implemented) is reused verbatim in the Transfer Confirmation dialog for the supervisor-initiated case — no new security code, only new UI wiring to an existing mechanism.

3. Files/Modules Likely to Change

  • billbull-frontend/src/pages/Sales/POSSales.jsx — new state/handlers for the transfer confirmation flow, following the existing pattern already used for SupervisorTakeoverDialog.
  • New component, e.g. src/components/pos/TransferConfirmationDialog.jsx, modeled on the existing src/components/pos/SupervisorTakeoverDialog.jsx.
  • New component, e.g. src/components/pos/TerminalLockedScreen.jsx.
  • src/hooks/useHeartbeat.js — surfaces the new lock-notice field from the heartbeat response to the calling component.
  • src/api/posApi.js — new function(s) for calling the transfer endpoint and the unlock-acknowledgment endpoint.
  • billbull-backend/.../pos/terminal/PosTerminalController.java — heartbeat endpoint response DTO gains the optional lock-notice field.

4. Database Migration Required

None.

5. Backward Compatibility Considerations

Every branch other than the pilot branch continues to operate exactly as before this phase — the flag remains off for them (Phase 7's control), so their terminals can never enter LOCKED and their frontend never shows the new dialogs (since the resolution flow, still terminal-first for these branches until Phase 9, never surfaces a "hosted elsewhere" case in the first place). The heartbeat response's new field is purely additive and safely ignored by any client not yet updated.

6. Risks

  • UX confusion for pilot-branch cashiers if training doesn't precede rollout. Mitigation: this is explicitly why the blueprint calls for a single pilot branch (Chapter 14/15) rather than a wider rollout — use this phase to gather real usage feedback before Phase 9's full cutover.
  • The pilot branch's cashiers are, at this phase, still using terminal-first *resolution* (Phase 9 hasn't shipped) but now have transfer *capability* — meaning the trigger for showing the Transfer Confirmation dialog must be sourced from somewhere. Mitigation: for the pilot branch specifically, wire the *existing* GET /sessions/active 409 "locked by active cashier" response (already present today) as the trigger for offering a transfer, rather than waiting for Phase 9's full resolution-service cutover — this keeps Phase 8 self-contained without silently depending on Phase 9.

7. Testing Strategy

  • Manual QA walkthrough of every scenario in blueprint Chapter 7's "every scenario" list, performed by hand on the pilot branch in staging, then in production with real (but supervised) pilot usage.
  • Regression testing confirming non-pilot branches show zero change in behavior or UI.
  • Cross-browser/device testing for the new dialogs, consistent with however the existing SupervisorTakeoverDialog was originally validated.

8. Rollback Strategy

Disable the flag for the pilot branch (reverting to Phase 7's dormant state) — any in-flight session at the moment of rollback simply continues on whichever terminal is currently hosting it, since a disabled flag only prevents *new* transfers from being initiated, it does not disrupt an already-completed one. Frontend code rollback (removing the new dialogs) is also available and safe, since nothing else depends on them.

9. Definition of Done

  • Pilot branch running with the flag enabled for a full, uneventful business cycle (minimum one full Day Close, ideally several).
  • Every scenario in blueprint Chapter 7 manually verified working as designed.
  • Documented pilot feedback reviewed and any UX issues resolved before proceeding to Phase 9.
  • Zero behavioral change confirmed on all non-pilot branches.

Phase 9 — Frontend Cutover to User-First Resolution (All Branches)

1. Objective

Switch the primary session-resolution path, for every branch, from the legacy terminal-first flow to the now-proven (Phases 4/5) user-first Session Resolution Service — this is the phase where the architectural cutover described in blueprint Chapter 14's Phase 4 actually happens.

2. Components Affected

  • Backend: yes — GET /sessions/active (and related resolution logic) now returns the Session Resolution Service's answer as its primary/authoritative response, with the legacy terminal-first path retained in code (not deleted) as the rollback target.
  • Frontend: yes — registerTerminalAndResumeSession's logic in POSSales.jsx is restructured so terminal registration and session resolution run as two independent calls (per blueprint Chapter 13), with the full three-way outcome (resumed-here / transfer-prompt / auto-claimed / none) now live for every branch, not just the pilot.
  • Database: none new.
  • APIs: GET /sessions/active's internal resolution logic changes; its request/response contract is unchanged (backward-compatible per blueprint Chapter 12's API philosophy).
  • Services: PosSessionService.getActiveSession is updated to delegate to PosSessionResolutionService as primary, rather than shadow-only.
  • Reports: not affected yet.
  • Security: no new surface — this phase changes *which* existing, already-proven logic is authoritative, not what is being authorized.

3. Files/Modules Likely to Change

  • pos/session/PosSessionService.java — getActiveSession re-keyed to call PosSessionResolutionService as the primary path.
  • pos/session/PosSessionController.java — GET /active endpoint's internal wiring updated; external contract unchanged.
  • billbull-frontend/src/pages/Sales/POSSales.jsx — registerTerminalAndResumeSession (lines ~1806-1862 per the dependency audit) restructured per blueprint Chapter 13's new startup flow; the Transfer Confirmation dialog (Phase 8) now triggers from the new resolution outcome for all branches, not just the pilot's legacy-409 workaround.
  • Feature flag from Phase 7/8 is widened to all branches (or removed entirely in favor of "always on," per team preference, since Phase 8's pilot has already validated the underlying transfer mechanics — this phase is specifically about resolution, which was independently validated in Phases 4/5).

4. Database Migration Required

None.

5. Backward Compatibility Considerations

Any client that has not been updated to the new frontend build continues to function, because the API contract is unchanged — an old frontend build calling GET /sessions/active still receives a response in the shape it expects, now computed via the new logic but indistinguishable in the common case (a session that has never transferred resolves identically under either model, as established in Phase 5's validation). The legacy terminal-first resolution code path is retained, not deleted, specifically to serve as the rollback target for this phase.

6. Risks

  • The primary risk this whole roadmap has been building toward mitigating: a resolution-logic bug surfacing at full production scale that smaller-scale (pilot branch) testing didn't catch. Mitigation: Phases 4/5's shadow-mode validation ran against full production traffic across all branches (not just the pilot) before this phase, specifically to catch exactly this class of risk ahead of time.
  • Frontend startup-flow restructuring (two independent calls instead of one sequential dependency) introduces new timing/race possibilities (e.g., terminal registration failing while session resolution succeeds, or vice versa). Mitigation: explicit test cases for each combination of (terminal registration success/failure) × (session resolution outcome), and a defined UI precedence rule (terminal registration failure still hard-stops the UI regardless of what resolution found, per blueprint Chapter 13).

7. Testing Strategy

  • Full regression of the existing POS startup flow test coverage (if any exists — flagged for the implementing team to confirm/expand, since the dependency audit did not find dedicated frontend tests for this flow).
  • End-to-end staging tests covering every combination in the Chapter 4 state diagram: resumed-here, transfer-prompt, auto-claimed, none, across multiple branches.
  • Gradual production rollout (e.g., branch-by-branch or via a percentage-based flag ramp, if the team's deployment tooling supports it) rather than an instantaneous all-branches flip, even though the phase's *goal* is all-branches — the mechanism of getting there can still be staged for safety without that staging constituting a separate "phase" in this roadmap.
  • Monitoring/alerting on GET /sessions/active error rates and latency during rollout, with a defined threshold that triggers rollback.

8. Rollback Strategy

Revert the frontend build to the pre-cutover version (Phase 8's build, which still uses terminal-first resolution for non-pilot branches) and/or flip PosSessionService.getActiveSession back to calling the legacy path directly instead of the Resolution Service — both are pure code-level reverts with no data cleanup required, since the underlying PosSession/PosTerminal data is valid and correctly interpretable under either resolution logic at this point in the rollout (Phase 10 has not yet shipped the suspend-behavior change that would make this less true — see next phase's note on sequencing).

9. Definition of Done

  • All branches resolving sessions via the new user-first service in production.
  • Rollout monitoring shows no elevated error rate or latency versus the pre-cutover baseline.
  • At least one full Day-Close cycle completed cleanly across all branches post-cutover.
  • Legacy terminal-first resolution code remains in the codebase, unused but intact, as the rollback target.

Phase 10 — Suspend-Releases-Terminal Behavior Change

1. Objective

Ship the one deliberate behavior change called for in blueprint Chapter 4: an idle/hard-timeout auto-suspend (and manual suspend) now releases the session's hosting terminal, rather than leaving it locked as it does today. This is intentionally sequenced *after* Phase 9's cutover, since it only makes sense once user-first resolution is the live path everywhere (per blueprint Chapter 14's own phase ordering).

2. Components Affected

  • Backend: yes — PosSessionScheduler and PosSessionService.suspendSession gain a call to release the hosting terminal (using the same lock-release mechanism proven in Phase 7's Transfer Service, applied here to a suspend rather than a transfer).
  • Frontend: minor — a terminal that just had its session suspended-and-released should now show its normal "no active session, start one" state rather than continuing to imply it's occupied, if the UI doesn't already do this correctly.
  • Database: none new.
  • APIs: no contract change.
  • Services: pos/session/PosSessionScheduler.java and PosSessionService.suspendSession updated.
  • Reports: not affected.
  • Security: not affected.

3. Files/Modules Likely to Change

  • pos/session/PosSessionScheduler.java — suspendIdleSessions now also calls the terminal-release logic after flipping status to SUSPENDED.
  • pos/session/PosSessionService.java — suspendSession (manual suspend path) gains the same release call.
  • pos/terminal/PosTerminalRepository.java — reuse of the existing clearOpenSession-style atomic release (already proven in Phase 7 for transfer; this phase is a second, simpler caller of the same underlying mechanism).

4. Database Migration Required

None.

5. Backward Compatibility Considerations

This is the one phase in the roadmap with a genuine, intentional behavior change visible to end users (a suspended session's terminal becomes usable by someone else sooner than it did before). This is explicitly called for by the approved architecture and is not a compatibility concern to avoid — it is flagged here so that operational/support teams are notified ahead of this phase shipping, consistent with the blueprint's Chapter 15 operational-risk mitigation ("communication risk... include explaining the... change before it ships").

6. Risks

  • Operational surprise if support staff or branch managers aren't informed that a suspended session no longer "reserves" its terminal. Mitigation: explicit advance communication (a support/ops runbook note), not a code mitigation — flagged plainly as the primary risk of this phase.
  • A session auto-suspending mid-transaction on a terminal that a *different* cashier immediately starts using could theoretically create a confusing moment if the original cashier returns expecting their screen to still be there. Mitigation: this is precisely what the Resume-from-anywhere capability (already shipped in Phase 9) is for — the original cashier resumes their session on whatever terminal is free next, losing no data; this should be part of the same communication/training materials as the risk above.

7. Testing Strategy

  • Unit tests confirming both the scheduled auto-suspend and manual suspend paths release the terminal correctly.
  • Integration test confirming a released terminal is immediately available to host a *different* user's new or resumed session.
  • Staging soak test across a full idle-timeout cycle to observe the end-to-end behavior under realistic timing.

8. Rollback Strategy

Revert the two call sites (scheduler and manual suspend) to their pre-Phase-10 behavior (suspend without releasing) — a pure code rollback; no data cleanup needed, since a terminal's hostedSessionId/lock state is always internally consistent regardless of which suspend behavior is active at any given moment.

9. Definition of Done

  • Both suspend paths (scheduled and manual) confirmed releasing the terminal in staging and production.
  • Support/ops teams have received and acknowledged the behavior-change communication.
  • No increase in support tickets related to "my terminal was taken" beyond an agreed monitoring window.

Phase 11 — Z-Report Eligibility Redefinition

1. Objective

Redefine Z-Report/Day-Close eligibility from "every terminal has produced an X-Report" to "every active/closed session for the branch+date has produced an X-Report" (blueprint Chapter 8, Rule 14, and Chapter 9), reflecting that a terminal may now legitimately host zero, one, or several sessions across a single business day.

2. Components Affected

  • Backend: yes.
  • Frontend: minor — the Z-Report screen's "pending terminals" messaging becomes "pending sessions" messaging.
  • Database: none new.
  • APIs: GET /sessions/z-report response shape's pendingTerminals field is renamed/reshaped to a session-based equivalent — this is the one place in the roadmap where an existing response field's meaning changes, so it is called out explicitly as a compatibility consideration below.
  • Services: PosSessionService.generateDynamicZReport eligibility-gate logic.
  • Reports: yes — this phase's core deliverable.
  • Security: not affected.

3. Files/Modules Likely to Change

  • pos/session/PosSessionService.java — generateDynamicZReport/getZReport eligibility computation re-keyed from a terminal-completeness check to a session-completeness check.
  • billbull-frontend/src/pages/Sales/POSSales.jsx — renderZReport()/loadZReport messaging updated to reflect pending *sessions* rather than pending *terminals*.

4. Database Migration Required

None.

5. Backward Compatibility Considerations

For any branch where no session has ever transferred (i.e., every branch not yet using roaming in practice, or any day with zero transfers), "every terminal reported" and "every session reported" are mathematically equivalent — so this phase produces zero observable difference for the overwhelming majority of days, and only changes behavior (correctly) on days where roaming actually happened. The response field shape change is additive-safe if implemented as "add a new session-based field, keep the old terminal-based field computed for one more phase as a soft-deprecated alias" — recommended explicitly here to avoid a hard breaking change to any dashboard or integration reading the old field name.

6. Risks

  • Any external tool, saved report, or dashboard that specifically parses the old pendingTerminals field name would break if that field is removed outright. Mitigation: the additive/aliased approach above avoids this entirely; a hard removal of the old field should be deferred to Phase 13 (cleanup) at the earliest, not bundled into this phase.
  • Finance/ops staff noticing the Z-Report screen's wording change without warning. Mitigation: same communication approach as Phase 10.

7. Testing Strategy

  • Unit tests confirming eligibility computation is identical to the legacy logic for every non-roaming scenario (regression safety), and correctly reflects reality for scenarios involving a transferred session.
  • Staging verification against both a normal (no-transfer) day and a synthetic roaming day.

8. Rollback Strategy

Revert the eligibility computation to its legacy terminal-based logic — safe, since (per the compatibility note above) the two are equivalent for any day without an actual transfer, meaning a rollback loses no information for the vast majority of historical data; only days that genuinely involved a transfer would show different (and, under rollback, slightly less accurate) eligibility framing, which is an acceptable, well-understood rollback trade-off.

9. Definition of Done

  • Eligibility logic verified equivalent to legacy behavior on all non-roaming days (regression-safe).
  • Correct, verified behavior on at least one real or synthetic roaming day.
  • Z-Report UI messaging updated and reviewed.

Phase 12 — Terminal/Counter Summary Rebuild

1. Objective

Rebuild Terminal Summary and Counter Summary reporting on top of per-transaction location data (each invoice's and cash movement's own point-in-time terminal/counter stamp) rather than "sessions opened on this terminal" — the second half of blueprint Chapter 9's reporting alignment.

2. Components Affected

  • Backend: yes.
  • Frontend: minor — report screens consuming the new data shape.
  • Database: none new (uses data already being written since Phase 1/7 — the Session-Terminal-History table — plus data invoices already write today, per the dependency audit's finding that checkout already self-stamps terminal/counter).
  • APIs: any existing Terminal/Counter Summary endpoint's underlying query changes; response shape kept compatible where feasible.
  • Services: reporting query logic in PosSessionService/pos/reports/PosReportsController.java's supporting services.
  • Reports: yes — this phase's core deliverable.
  • Security: not affected.

3. Files/Modules Likely to Change

  • Reporting query logic under pos/reports/ and/or the relevant private helper methods in PosSessionService.java (e.g., alongside buildCashierWiseSummary, buildTopSellingItems) — a new buildTerminalWiseSummary/buildCounterWiseSummary built from invoice/cash-movement stamps rather than session-terminal fixed assignment.
  • Frontend report rendering components consuming these summaries.

4. Database Migration Required

None new.

5. Backward Compatibility Considerations

For any historical day with no transfers, the new per-transaction-based Terminal Summary produces numbers identical to the old session-based one (since, absent a transfer, every transaction a session recorded happened on the one terminal it was ever hosted on). This phase is therefore safe to ship without any special historical-data handling — the new logic is simply more correct going forward and equally correct looking backward.

6. Risks

  • Query performance: aggregating per-transaction rather than per-session could be more expensive depending on data volume and existing indexing. Mitigation: profile the new query against a realistic-sized dataset in staging before shipping; add indexes if needed (an additive, low-risk migration if so).
  • Numbers moving slightly for any historical day that *did* involve a transfer (correctly, per the redesign) could surprise a report viewer comparing against a previously-cached/exported figure. Mitigation: same communication approach as prior reporting-change phases.

7. Testing Strategy

  • Unit tests comparing old vs. new Terminal/Counter Summary output on non-roaming fixture data (must match exactly).
  • Unit tests validating correct attribution on synthetic roaming fixture data.
  • Performance testing against a production-scale dataset copy.

8. Rollback Strategy

Revert the reporting query logic to its prior session-based computation — safe for the same reason as Phase 11's rollback (equivalent results on the vast majority of non-roaming historical data).

9. Definition of Done

  • New summary logic verified matching legacy output exactly on all non-roaming data.
  • Verified correct on roaming scenarios.
  • Performance confirmed acceptable at production scale.

Phase 13 — Legacy Field Demotion & Index Retirement (Optional, Deferred)

1. Objective

The blueprint's explicitly optional cleanup phase (Chapter 11/14): demote openedBy/performedBy string fields to pure display-only status (never read for logic, since owner_user_id/performed_by_user_id have been authoritative since Phase 9), and optionally retire the older of the two redundant DB-level terminal-lock unique indexes. This phase has no fixed deadline and is only undertaken after a sustained, uneventful production period.

2. Components Affected

  • Backend: yes — removal of any remaining code paths that read the string fields for logic rather than display.
  • Frontend: none expected.
  • Database: optional — retiring uq_pos_session_terminal_open (the string-terminal_id-keyed index from V13), leaving uix_one_open_session_per_terminal (the numeric-terminal_pk-keyed one) as sole enforcement.
  • APIs: no contract change.
  • Services: cleanup-only changes to PosSessionService/PosCashMovementService removing any lingering string-based comparison logic.
  • Reports: not affected (Phase 12 already moved reporting off any dependency on this).
  • Security: not affected — ownership validation has used the numeric FK since Phase 9's cutover made the Resolution Service authoritative; this phase only removes now-dead string-comparison code.

3. Files/Modules Likely to Change

  • pos/session/PosSessionService.java, PosCashMovementService.java — remove any remaining openedBy/performedBy string-equality checks used for authorization (superseded by owner_user_id/performed_by_user_id since Phase 9).
  • A new Flyway migration to drop uq_pos_session_terminal_open, if the team elects to proceed with that specific cleanup step.

4. Database Migration Required

Only if the index-retirement half of this phase is undertaken — a single DROP INDEX IF EXISTS uq_pos_session_terminal_open (or equivalent), guarded and reversible.

5. Backward Compatibility Considerations

This phase is explicitly optional and time-unbounded per the blueprint — the system is fully correct and fully supported indefinitely without ever executing it. It should only be scheduled after a documented, sustained period (the blueprint suggests several full Day-Close cycles at minimum) with zero rollback events across every prior phase.

6. Risks

  • Removing the redundant index prematurely, before full confidence in the numeric-FK-keyed index's correctness under all edge cases. Mitigation: this is precisely why the blueprint frames this as strictly last and optional — no other phase depends on it happening at all.
  • Any lingering, undiscovered code path still reading the string fields for logic (rather than display) that this phase's audit misses. Mitigation: a dedicated code-search pass (grep for every read of openedBy/performedBy) before removing any of it, treating this phase with the same "exhaustive dependency sweep" rigor as the original architecture audits.

7. Testing Strategy

  • Full regression suite plus a dedicated search-and-verify pass confirming no remaining logic-path dependency on the string fields before removing any authorization use of them.
  • If retiring the index: verify the remaining index alone still fully enforces the one-session-per-terminal-hosting invariant under the same concurrency tests used in Phase 7.

8. Rollback Strategy

Code-level revert for the string-field cleanup; re-create the dropped index via a follow-up migration if the index-retirement half is rolled back (the index's absence has no data-loss implication, since it is a constraint, not stored data — re-adding it is always safe as long as no invariant violation occurred in the interim, which the remaining index would have already prevented).

9. Definition of Done

  • Documented sustained-stability period elapsed with zero rollbacks across all prior phases.
  • String fields confirmed display-only (no remaining logic dependency) via a dedicated code audit.
  • If undertaken, index retirement verified not to weaken the one-session-per-terminal-hosting guarantee.
  • This phase may be formally deferred indefinitely without blocking anything else — its absence from a given release is itself an acceptable Definition of Done for "not doing it yet."
