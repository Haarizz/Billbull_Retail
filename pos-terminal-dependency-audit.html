POS Terminal-Centric Dependency Audit — Final Pre-Migration Sweep

Purpose: exhaustive inventory of every component (frontend, backend, database, jobs, security, storage) that directly or indirectly depends on the Terminal-Centric session model, ahead of a User-Centric ("session roaming") redesign. No code changed, no solutions proposed. Builds on the two prior audit documents (pos-architecture-analysis.html, pos-session-user-centric-audit.html); this pass goes one level deeper and exhaustively line-cites.

Pattern: Terminal is the primary key for terminal-lifecycle and hardware-binding endpoints (as expected). Session is the primary key for session-lifecycle, cash-movement, held-sales, and per-session reporting endpoints. Branch is the primary key for nearly everything list/aggregate-shaped. User is never an explicit path/query key anywhere — it is always implicit via JWT, confirmed across every controller reviewed. This last point is the clearest structural signal: today's API surface has no "give me resources for user X" shape at all, which a user-centric session model would need to introduce as a new, first-class query pattern.

16. Final Summary

1. Which modules are completely unaffected? PosSessionScheduler (idle/timeout auto-suspend — purely session-keyed already); PosLayawayExpiryReleaseJob; Day-Close reconciliation arithmetic; ZatcaQrGenerator (fully identity-agnostic); PosTerminalScheduler offline detection (orthogonal, stays terminal/branch-based regardless of session model); Device Dashboard's branch-level aggregation query shape; sessionStorage auth keys (token/role/user/fullName/activeBranchId); the device_fingerprint localStorage key; customer/product/quantity selection UI state.

2. Which modules require minor changes? Cash movement core logic (session-scoped already; only the performedBy string field and the terminal-activity side-effect touch terminal identity); Held Sales/Layaway recall filtering (already session-first, just needs the terminal-metadata field to stop being load-bearing); Session History filtering (additive userId filter alongside existing branch/terminal/date/status filters); X-Report generation (already session-first).

3. Which modules require major redesign? Session open/resume duplicate-check and locking (PosSessionService.openSession/getActiveSession, plus the two DB partial unique indexes and the current_open_session_id CAS mechanism); Hardware Profile assignment (HardwareProfileAssignmentEngine, structurally terminal-bound); Printer resolution (resolvePrinterForContext, no session/user parameter exists); Z-Report eligibility gating (currently framed as "pending terminals," a concept that needs redefinition); checkout/reprint's three uncorrelated identity fields (sessionId/terminalId/branchId) which need either validation or a decision about which one is authoritative under roaming.

4. Which modules are tightly coupled to Terminal ownership? Everything in the hardware layer without exception (PosPrinter, PosCashDrawer, PosScanner, PosHardwareProfile/PosHardwareProfileDevice, HardwareProfileAssignmentEngine); PosTerminalActivityService and its six call sites; the frontend's registerTerminalAndResumeSession startup flow and its localStorage terminal-id cache; both DB-level partial unique indexes on pos_sessions; the pos_terminals.current_open_session_id lock column itself.

5. Which modules are already User-centric? OwnershipContextHolder (a real, JWT-derived, numeric userId context — exists app-wide, currently unused by any POS code); PosSessionScheduler; PosSessionService.buildCashierWiseSummary (already groups reporting by cashier); the openedBy-reassignment mechanisms (reassignSessionOwner, supervisorTakeover — prove the domain already tolerates "owner ≠ opener," just not "across terminals"); sessionStorage's JWT/user/role/fullName keys.

6. Which modules can remain exactly as they are? PosLayawayExpiryReleaseJob, PosTerminalScheduler, ZatcaQrGenerator, Day-Close reconciliation math, the device_fingerprint localStorage mechanism, sessionStorage auth keys, customer/product selection UI state, and — contingent entirely on the redesign's policy decision about whether hardware should roam with the user or stay with the physical terminal — potentially the entire hardware layer (§6/§17 of this document deliberately leaves that policy question open, since resolving it is redesign work, not audit work).
