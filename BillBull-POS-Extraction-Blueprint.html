Implementation Blueprint · Sequel to the POS Separation Audit

Extracting BillBull POS into a standalone application

A phased plan to lift the point-of-sale experience out of the Retail SPA and stand it up as a second browser client of the same BillBull API and the same tenant database — without a second backend, a second database, or a rewrite of POS business logic.

The finding that shapes everything

Tenant identity is not a frontend concern today. One build is deployed to /var/www/billbull and served by every client vhost; nginx maps the hostname to a per-tenant Spring Boot instance on its own port (8080, 8081, 8082…), and that instance owns the tenant database. The browser bundle is tenant-agnostic apart from cosmetic overrides in config/clientConfig.js. A standalone POS therefore inherits correct tenant routing for free — provided it is served from the tenant's own origin.

The finding that constrains everything

POSSales.jsx holds 481 useState declarations, 50 useEffect blocks and roughly 5,800 lines of JSX in a single function component. Its already-extracted children (POSConsole 3,518 lines, POSTouchScreen 1,996, CustomerView 1,417) are driven by enormous prop bags rather than owned state. Nothing about creating apps/pos is hard; making this component portable is the entire project.

Why billbull-frontend/ does not move on day one

Every deployment runbook, the eight-client update script and the k8s manifests hard-code the path billbull-frontend/. npm workspaces let a package live at any path, so apps/pos and packages/shared can exist alongside it immediately while Retail keeps its current location and build command. Renaming it to apps/retail is a cosmetic git mv plus a documentation sweep — schedule it in Phase 8, after POS is live, so a path rename never shares a release with a behavioural change.

POSSales.jsx imports pages/Sales/SalesReturn/SalesReturnScreen.jsx (542 lines, backed by useSalesReturn.js at 643 lines and eleven components — 3,861 lines total) and distinguishes the two callers with an ENTRY_POINT constant. This is the one large Retail page POS genuinely reuses.

The boundary that is easiest to get wrong

POS administration is Retail's. A cashier's terminal must not be able to rename terminals, reassign counters, approve corrections or adjust denomination records — those screens carry maker-checker weight and belong in the back office behind the existing RBAC gates. The till consumes terminal and counter records; it does not manage them. The single exception already in the code is self-registration (POST /api/pos/terminals/register), which is how a till claims an identity on first boot, and it stays.

05Shared package — and how to keep it honest

The audit named duplicated financial arithmetic as the highest-severity risk of this split. The counter-risk is a shared package that absorbs everything and re-couples the two apps by the back door. Both are prevented by rules, not by intentions.

Admission rules

  1. Two real callers. A module enters packages/shared only when both billbull-frontend and apps/pos import it. "POS will probably need it" is not a caller.
  2. No app-shell code. Nothing that knows about routes, sidebars, page layout or navigation. The Sales Return module is the one carved exception and it is a self-contained feature, not a page in a router.
  3. No cross-app state. Shared contexts hold server-derived data (company profile, branch list, permission set). They never hold "the other app's" UI state.
  4. Every money module ships with tests. vatMath, salesPricing, unitPricing, cashDenominations and posReportViewModel must have Vitest coverage in packages/shared before either app is allowed to import them from there.
  5. Explicit exports map. package.json lists every public subpath. Anything not listed is unreachable, so growth is a deliberate edit rather than a side effect.
  6. An ESLint boundary rule. A no-restricted-imports rule forbids apps/pos from importing any path containing billbull-frontend, and forbids packages/shared from importing either app. This is the mechanism that makes "no Retail↔POS frontend dependency" checkable in CI rather than aspirational.

Subpath layout

@billbull/shared ├── /api/client axios instance + interceptors ├── /api/<feature> auth, branch, company, pos, products, customers, sales, print-template… ├── /context CompanyProvider, BranchProvider, PermissionProvider ├── /money vatMath, salesPricing, unitPricing tests required ├── /pos cashDenominations, posReportViewModel, posSessionBusinessDay tests required ├── /print escPosReceipt, printGenerator, documentTemplateRenderer, templates, fonts ├── /device localPrintAgent, zebraZpl ├── /ui Radix primitives, AedSymbolRenderer, AsyncSearchableDropdown ├── /hooks useHeartbeat, useIdleTimeout, usePermission, useShortcuts ├── /features/sales-return the one shared feature module └── /utils logging, dates, names, exports, numbering

Migration mechanics for a shared module

Move the file with git mv so history follows it. In its old location leave nothing — no re-export shim. Update Retail's imports in the same commit. A shim would let the two copies drift silently, which is the exact failure this package exists to prevent. Each module moves in its own small PR, and Retail's test suite plus a build is the gate.

07Decomposing POSSales.jsx

The rule that governs this section

Decomposition happens in place, in billbull-frontend, against the live /sales/pos route, before apps/pos exists. Every extraction is behaviour-preserving and is proven by the existing route continuing to work. Only once the component is a thin shell over ~15 hooks does anything move. Moving 15,818 lines first and refactoring in the new home would leave both copies unverifiable at once.

Why state-first, not JSX-first

The instinct is to cut the 5,800 lines of JSX (lines 9,998–15,818) into components. That is the wrong first cut: the JSX is already partly extracted, and the child components are only unwieldy because they receive prop bags sourced from 481 useState declarations in the parent. Extract the state into hooks, expose it through one PosWorkspaceContext, and the prop bags collapse on their own — POSConsole's 3,518 lines and POSTouchScreen's 1,996 shrink without either file being restructured.

Rules for every extraction PR

  • One hook per PR. Never two.
  • No behaviour change, no API change, no rename of a value the UI displays. If a bug is found, log it and fix it in a separate PR after the extraction lands.
  • The hook's test lands in the same PR. For hooks 7, 10, 12 and 13 the test is a snapshot of computed output against fixtures captured in Phase 0.
  • Line count of POSSales.jsx is recorded in the PR description. It is the project's progress metric, and it only goes down.
  • /sales/pos is exercised manually on the PR branch before merge — open a session, sell an item, take cash, print, close.

Structured for a desktop wrapper, without building one

  • Every asset path is relative to a single configurable base — a wrapper serving from file:// or a local server needs one build-time change, not a restructure.

15Security for an independent client

POS becoming a separate client changes the threat surface only where the origin, the token lifetime or the permission gate changes. Everything else is the existing, unchanged security model.

Must fix before standalone POS

Minimum viable fix: for POS only, persist the token in localStorage scoped to the POS path, paired with the idle lock screen from §11 so an unattended till is protected by a PIN rather than by token volatility. Can be improved later

  • Refresh tokens with rotation. The right fix for shift-length sessions; a self-contained backend project, not a precondition for the split.
  • Device-bound terminal tokens. The fingerprint is a localStorage string a determined user can copy. Binding a terminal to a server-issued device credential is a real hardening step, and it is orthogonal to extraction.
  • Content-Security-Policy on the POS origin. Worth adding once the bundle's external dependencies are known and stable.
  • Narrowing Access-Control-Allow-Headers: *. Pre-existing, unrelated to this project.
  • Per-cashier PIN as a first-class credential. Supervisor PIN verification exists; extending it to cashier sign-in would improve till ergonomics but changes the auth model.
Not a security rewrite

Five items block the split, and four of them are configuration or a header. The one substantive change — token persistence for a till — is scoped deliberately narrowly, because the alternative (a refresh-token subsystem) would put a backend security project on the critical path of a frontend extraction.

19Rollback strategy

Why rollback is cheap here

Both clients write the same rows to the same database through the same API. There is no data migration, no dual-write, no reconciliation. Rolling back is therefore always "stop using one client and use the other" — never "undo the data". This is the strongest practical argument for the shared-backend architecture over a separate POS service.

20The first coding task

First task

Write the cart-and-checkout characterization suite against the current embedded POS, in billbull-frontend, changing no source file.

Concretely: fixtures for a representative matrix of carts — mixed tax rates, inclusive and exclusive pricing, line and order discounts, zero-rated and exempt lines, multi-unit items, a returned line — driven through the current totals code path, with committed snapshots of both the computed totals and the exact posCheckout request body each cart produces. Then the same treatment for the X and Z report view-models from a fixed session fixture, and a SHA-256 snapshot of the ESC/POS bytes for one receipt of each type.

Why this and not something else

  • Every later step is unsafe without it. Phase 1 moves vatMath and salesPricing into a shared package; Phase 3 pulls apart the component that calls them. Both are refactors of money code, and a refactor without a characterization test is a rewrite with extra steps.
  • It is the only task with zero production risk. No source file changes. It cannot break a till.
  • It pays off even if the split is cancelled. The current POS has fourteen test files and none of them covers the cart, the totals or the checkout payload — the three things that decide whether a customer is charged correctly. This suite is worth writing regardless of what happens to apps/pos.
  • It answers a question the plan cannot. Writing the fixtures forces someone to read the totals code closely enough to enumerate its branches. If there are surprises in there — and in 15,818 lines there usually are — the project should discover them now, not during Phase 3.
  • It sets the standard. Every extraction PR from then on has an obvious, non-negotiable definition of "still correct".

The alternatives were considered and rejected: creating the workspace first produces churn across Retail with nothing verifying it; decomposing first is the refactor-without-a-net case above; and creating apps/pos first means the standalone app is built on a component that is about to change underneath it.
