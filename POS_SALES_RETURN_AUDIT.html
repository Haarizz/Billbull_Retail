POS Sales Return — Implementation Audit

BillBull Retail / ERP · branch feature/posclient · 1 October 2026 · read-only audit

A BillBull sales return is five loosely-coupled effects, not one transaction: it creates its own sales_returns document, posts inbound stock movements, posts a GL journal, and settles the customer only for two of the five refund methods. It never touches the original invoice, the invoice balance that is the customer's outstanding, or the customer statement. No code, schema, migration or data was changed.

1. Executive Summary

A sales return in BillBull is a separate document (sales_returns), never an edit to the original invoice and never a negative invoice. Nothing happens until the return is moved to APPROVED; at that moment SalesReturnService.updateStatus runs five side effects in one database transaction, in this fixed order: batch restock, non-batch restock, GL journal, serial status flip, cash refund, credit-voucher issue.

What a return reliably does today

  1. Creates sales_returns + sales_return_items (+ sales_return_item_batches) rows.
  2. Posts positive stock_movements rows (source_type = SALES_RETURN) for lines marked condition GOOD, raising on-hand quantity.
  3. Posts a GL journal: Dr Sales Revenue (or Deferred Revenue) + Dr VAT Output / Cr Accounts Receivable, plus a second self-balancing Dr Inventory / Cr COGS entry when goods are restocked.
  4. For CASH_REFUND only: books a POS_CASH_MOVEMENT DROP_OUT on the POS session, which reduces expected drawer cash in the X-Report, Z-Report and day close.
  5. For CREDIT_VOUCHER only: issues a credit_vouchers row with its own Dr AR / Cr Credit Vouchers Issued journal.

What a return does not do

  1. It never changes the original invoice. sales_invoices.invoice_total, amount_paid, balance and status are untouched. The invoice is read and row-locked, never written.
  2. It never changes customer outstanding. Outstanding is defined as SUM(sales_invoices.balance) (CustomerService, SalesInvoiceRepository.sumOutstandingBalanceByCustomerCode). No code path reduces it on a return — including the CUSTOMER_CREDIT refund method, which has no implementation beyond the GL line.
  3. It never appears on the customer statement. StatementService reads sales invoices, receipt vouchers, advance applications, opening invoices, purchase invoices and payment vouchers. It does not inject SalesReturnRepository at all; its PRI_RETURN_CREDIT sort constant is declared and never used.
  4. It creates no refund record for card or bank. CARD_REFUND and BANK_TRANSFER are selectable, validated and stored, but settle nothing — no payments row, no reversal, no cash movement. The GL credit to AR is left unsettled.

The single most important structural fact: the return's journal always credits Accounts Receivable, because it is modelled as a credit note against AR. Only CASH_REFUND (via the seeded SALES_RETURN_REFUND cash-movement category, mapped to AR) and CREDIT_VOUCHER post the matching debit that clears it. For the other three methods the AR control account carries a permanent credit that the AR sub-ledger (invoice balances) never mirrors.

What the client computes (useSalesReturn.summary)

ratio = returnQty / soldQty
  • gross = Σ unitPrice × returnQty
  • discountReversal = Σ lineDiscount × ratio
  • vatReversal = Σ lineVat × ratio
  • netOfDiscount = gross − discountReversal
  • totalRefund = taxInclusive ? netOfDiscount : netOfDiscount + vatReversal, floored at 0, rounded to 2dp

unitPrice, lineDiscount, lineVat and taxRate all come from the eligibility payload, i.e. from the original invoice line — never from the product master and never recomputed from a current tax rate.

Payload shape (buildPayload)

subTotal = gross, taxAmount = vatReversal, totalAmount = totalRefund, refundAmount = totalRefund, returnAction = refundMethod === 'CREDIT_VOUCHER' ? 'Credit Note' : 'Refund'. Each item carries price, discountAmount, taxAmount, total = unitPrice × qty − lineDiscount × ratio, condition, returnReason, returnReasonNotes, itemStatus ('Good' when the condition is restockable, else 'Damaged') and its batches.

Confirm is two calls, not one

handleConfirm does saveSalesReturn (creates the DRAFT) and then approveDraft. If the save succeeds and the approve fails for any reason other than 401/403, the user is told explicitly: "saved as a draft but could not be posted … No stock or refund has been processed." A 401/403 opens the supervisor dialog and re-approves the same draft, so no duplicate is created.

6. Stock Handling

Stock is increased by a new inbound movement. The original sale's outbound movement is never deleted or reversed in place — consistent with stock_movements being an append-only ledger.

The decision tree per return line, at approval:

  1. Does the line carry batch selections? If yes → applyBatchReturns. If no → applyNonBatchStockReturns. The two are mutually exclusive, so a line cannot be restocked twice.
  2. Is itemStatus == "Good"? (derived from condition: only GOOD maps to "Good"; DAMAGED, OPENED, DEFECTIVE, EXPIRED all map to "Damaged".) If not → no stock movement at all. For a batch line the allocation is still flipped to RETURNED for traceability; BatchMaster.status is left untouched.
  3. Can a warehouse be resolved? If not → log a warning and skip, leaving inventory and GL to disagree.

Batch-controlled lines (applyBatchReturns)

  • Validates Σ batch.quantity == returnQty (HTTP 400 otherwise).
  • batchAllocationRepository.findByIdForUpdate(parentId) — pessimistic lock per allocation.
  • Validates the selected batchNumber matches the parent allocation's, and that the parent's productCode matches the line's itemCode.
  • Validates retQty ≤ parentQty − sumAlreadyReturned(parentId).
  • Warehouse comes from parent.getBatchMaster().getWarehouseId(); bin from parent.getBinId(). Batch number and expiry are carried onto the movement, so batch identity is preserved.
  • If BatchMaster.warehouseId is null, the restock is skipped with a warning.

Non-batch lines (applyNonBatchStockReturns)

  • Warehouse comes from resolveReturnWarehouseId: the linked invoice's first delivery note's warehouse. Order is: linked invoice → linkedDeliveryNote (comma-split) → first DN with a warehouse → otherwise null.
  • null means no stock movement is posted, with this log line: "could not resolve a source warehouse … Inventory and GL will mismatch until a manual adjustment is made."
  • No bin, no batch, no expiry on the movement.

There is no reference to the invoice, the invoice item, the POS session or the user on the stock movement. Tracing a movement back to its sale requires two hops: movement → source_id → sales_returns.linked_invoice.

Serials (applySerialReturns) — builds itemCode → serialNumber from the original invoice, locks the serial row, and flips SOLD → RETURNED. Note it keys on item code, so a line with several serialized units of the same product only ever flips the one serial recorded on the invoice line. It also runs regardless of condition, so a scrapped unit's serial is still marked RETURNED rather than quarantined.

Reserved stock is not touched — there is no reservation concept on this path.

No double-stock risk from events — there is no listener, no event publisher and no invoice reversal in the return path. The only route to a duplicate movement is a second approval of the same return, which the row lock and the APPROVED guard prevent. Note that the unique index ux_sm_outbound_source_identity (StockMovementIdentityConstraintConfig) is WHERE quantity < 0, so inbound return movements have no database-level dedup.

7. Amount Calculation

Every figure is prorated from the original invoice line. Not the current product price, not the current customer price, not a manually entered return price, not a weighted average. The source is SalesReturnEligibilityService.getEligibility, which copies SalesInvoiceItem.price, .taxAmount, .netAmount, .taxRate onto each ReturnEligibilityLine.

The formulas

lineDiscount = price × soldQty × (discount% / 100) + footerShare
returnedDiscount = lineDiscount × (returnQty / soldQty) vat         = lineVat × (returnQty / soldQty)
totalRefund = gross − returnedDiscount (VAT inclusive) totalRefund = gross − returnedDiscount + returnedVat (VAT exclusive)

VAT mode detection

res.taxInclusive = Boolean.TRUE.equals(inv.getTaxInclusive()) || inv.getVatMode() == VatMode.INCLUSIVE. The second clause exists because back-office invoices recorded inclusive pricing in vatMode only, leaving taxInclusive false — which made refunds add VAT on top of an already-inclusive price.

What is stored on the header

subTotal = gross (pre-discount, and in inclusive mode that gross contains VAT), taxAmount = returnedVat, totalAmount = totalRefund. There is no header discount column on sales_returns, so the discount is recoverable only as the residual subTotal + taxAmount − totalAmount — which is exactly what PostingEngineService does.

Backend proration is effectively dormant for UI returns

SalesReturnService.prorateDiscountFromInvoice skips any line where discountAmount != null, and buildPayload always sends a discountAmount (even 0). It therefore only fires for API callers that omit the field.

Free items, promotions, overrides

A zero-price or promotional line reverses at whatever the invoice line recorded. There is no special handling and no link to any promotion record. Price overrides made at POS are already baked into SalesInvoiceItem.price, so they reverse correctly.

Does the return exactly reverse the sale?

For a full return, yes to the cent in exclusive mode. Two caveats: (a) per-line rounding at 2dp happens twice — once on the invoice, once on the prorated return — so a partial return of an odd fraction can differ by ±0.01 per line from the invoice's own line split; (b) soldQty is taken from the first invoice line matching an item code (invoiceItemByCode.putIfAbsent), so an invoice that lists the same product on two lines at different prices will prorate against only one of them.

8. Customer Outstanding

A sales return does nothing to the customer's outstanding balance. This is derived, not asserted.

Outstanding is defined in exactly one way across the system:

outstanding(customer) = Σ sales_invoices.balance + Σ opening_invoices.outstanding
  • CustomerService.getAllCustomers → salesInvoiceRepo.sumOutstandingBalanceByCustomerCode()
  • CustomerService detail view → sumOutstandingBalanceForCustomerCode(code) + openingInvoiceRepository.sumOutstandingForCustomer(code)
  • Credit-limit checks → CustomerCreditService.assertWithinLimit → invoiceRepo.findOutstandingBalanceByCustomerCode
  • AR aging → FinancialReportService.generateARAgingReport, which iterates salesInvoiceRepository.findAll() and buckets inv.getBalance()
  • AR sub-ledger reconciliation → SalesInvoiceRepository.sumGlobalOutstandingBalance()

SalesInvoice.balance is maintained only by SalesInvoiceService.recordPayment and the invoice's own status transitions. No return code path writes it. SalesReturnService reads the invoice twice (findByInvoiceNumber, findByInvoiceNumberForUpdate) and never calls save on it.

So the formula the business probably expects:

Original Customer Outstanding = X
Sales Return                  = Y
New Outstanding               = X - Y        <-- NOT what happens

What actually happens:

Original Customer Outstanding = X
Sales Return                  = Y
New Outstanding               = X            <-- unchanged, for every refund method

Including CUSTOMER_CREDIT. The enum documents it as "Credits the customer's account via the existing customer-credit mechanism", and SalesReturnCustomerAccountResolver goes to real trouble to block it for walk-ins on the grounds that "the method posts to the customer's ledger". But no code posts it. Searching the backend for writers of customer credit turns up only CustomerCreditService, which is a read-only credit-limit guard — it has no mutator at all. A CUSTOMER_CREDIT return therefore stores refund_method = CUSTOMER_CREDIT on the row, posts Cr AR in the GL, and leaves the customer's receivable exactly as it was. There is no credit balance, no refund payable, and no adjustment record.

The one place the customer is genuinely credited is CREDIT_VOUCHER: a credit_vouchers row with remaining_amount, redeemable at a later checkout through the VOUCHER payment allocation in PosCheckoutController.redeemVoucherAllocation. That is store credit held outside the AR sub-ledger, not a reduction of outstanding.

9. Customer Statement

A sales return does not appear on the customer statement of account.

financials/statement/StatementService.java is the only producer of the customer SoA (StatementController → getCustomerStatement). Its injected sources are:

SalesReturnRepository is not injected. The class declares private static final int PRI_RETURN_CREDIT = 6; // Row 7 — sales return / credit note and that constant is never referenced anywhere in the file — the slot was reserved and never filled. (PRI_REFUND is used once, at line 288, for refund receipt vouchers.)

Consequences:

  • Transaction type: none emitted for a return.
  • Debit / credit direction: n/a.
  • Running balance effect: none. The SoA closing balance after a return equals the balance before it.
  • Reference document, date, branch, POS session, description: none.

Is the statement consistent with outstanding? Yes — both ignore returns, so they agree with each other. Both disagree with the general ledger, which has been credited. The customer's SoA and the AR control account diverge by the return total until some other transaction happens to close the gap (a cash payout or a voucher issue does close the GL side, but the SoA still never shows the return).

A CREDIT_VOUCHER return does eventually surface on the statement, but indirectly and later: when the voucher is redeemed, the sale it settles is a normal invoice and the voucher leg reduces that invoice's balance. The return itself is still invisible.

SalesReturnService.updateStatus calls exactly two settlement collaborators: cashRefundService.recordCashRefund(saved) — which returns null immediately unless refundMethod.isCashDrawerAffecting(), true only for CASH_REFUND — and issueCreditVoucherIfRequired(saved), which returns immediately unless the method is CREDIT_VOUCHER. There is no third branch.

Cash sale → return

The original POS cash sale produced: invoice PAID with balance = 0, a payments row, a receipt_vouchers row, and session tender counters via recordInvoiceOnSession.

On return with CASH_REFUND: physical cash leaves the drawer and is recorded as a DROP_OUT on pos_session_id, with reference = returnNumber, business_date = session.sessionDate, category SALES_RETURN_REFUND (GL override → Accounts Receivable). Expected drawer cash falls by the refund. The original payments row and receipt_vouchers row are not reversed, voided or linked — the refund is a fresh drawer movement with no pointer to the original tender.

Two hard gates: posSessionId must be non-null (HTTP 400: "Cash Refund requires an open POS session"), and the amount must not exceed availableCashInDrawer(session), i.e. the same expected-cash figure the X-Report shows (HTTP 400 otherwise). So a large refund against a card-heavy session is refused.

Card payment → return

Nothing is recorded. No refund transaction, no reversal of the original payments row, no card-settlement entry in financials/settlement. CARD_REFUND is documented in the enum as "Reversal against the original card payment, via the existing payment architecture", but no code implements it. The return posts Cr AR and stops.

Credit sale → return

The original credit checkout recorded nothing (PosCheckoutController: "CREDIT allocations intentionally record nothing: the amount stays outstanding on the customer's A/R ledger"), so the invoice keeps a positive balance. On return, the customer's outstanding does not reduce — see §8. The invoice balance is untouched whichever refund method is chosen.

Partial payment

Paid        =  6,000      customer outstanding = 4,000

Current behaviour: sales_returns.total_amount = 2,000; stock for the returned lines comes back; GL posts Dr Revenue 2,000-net + Dr VAT / Cr AR 2,000. invoice.balance stays 4,000, customer outstanding stays 4,000. If the method is CASH_REFUND, 2,000 physically leaves the drawer in addition to the 4,000 still owed — nothing allocates the credit against the unpaid portion first. There is no allocation logic of any kind between a return and an invoice's open balance.

11. Tax / VAT

VAT is reversed as a debit to VAT Output (2102) inside the return's own journal — a real reversal in the general ledger, not a negative tax transaction and not an edit to the original invoice's tax.

Dr VAT Output (2102)   taxAmount        (only when taxAmount > 0)

Returned tax = Σ (invoice line taxAmount × returnQty / soldQty), rounded 2dp per line. It is taken from the invoice line's recorded tax money, so a line that was zero-rated or exempt on the sale reverses zero tax, and a rate that has since changed in the product master is irrelevant.

Exclusive sale

Sale:    price 100, VAT 5% = 5, line total 105
Return:  subTotal 100, taxAmount 5, totalAmount 105
Journal: discount = 100 + 5 - 105 = 0
         Dr Sales Revenue 100 / Dr VAT Output 5 / Cr AR 105

Correct and exact.

Inclusive sale

Also correct — but by arithmetic coincidence rather than by design. The posting engine labels the residual discountAmount, and in inclusive mode that "discount" is actually the contained VAT. The entry balances and the revenue split is right; only the name of the intermediate figure is misleading. With a real discount on an inclusive line the same identity still holds (gross 105, discount 10, VAT portion 4.52, total 95 → residual 14.52, net revenue 90.48 → 90.48 + 4.52 = 95).

Tax reporting

No tax-specific table is written. financials/tax (TaxService, TaxConfiguration, TaxFiling) does not reference SalesReturn at all. VAT reporting reaches returns only through the ledger: FinancialReportService.getTaxReconciliation / getTaxDashboard call collectVatLines(fetchEntries(...)), which reads ledger_entries by account role. Because the return debits 2102, output VAT in those reports is correctly net of returns.

Rounding

Two roundings compound: the invoice line's own tax was rounded when the sale was posted, and the prorated share is rounded again (round2 on the client, HALF_UP scale 2 server-side). A partial return of an odd quantity can therefore differ by up to ±0.01 per line from a hand-computed share. The GL entry always balances regardless, because the AR leg is totalAmount and the revenue leg is derived as a residual from it.

12. COGS / Inventory Valuation

COGS is reversed, and inventory is debited — in the GL. The inventory sub-ledger valuation is a different story.

SalesReturnService.resolveActualCogs resolves a per-line cost through three tiers, first hit wins:

TierSourceFormula
1DeliveryNoteBatchConsumption rows for the invoice's first linked DNunitCost = sumTotalCostByDnAndItem(dnId, itemCode) / deliveredQty, then × min(returnQty, deliveredQty)

Tier 1 is the exact batch/WAC cost at the moment of the original sale, which is what stops a later WAC movement from distorting the reversal. Tier 2 survives the product master's cost being changed or cleared afterwards. Tier 3 is the legacy fallback and logs a warning.

Scrap lines are excluded. Any line whose itemStatus != "Good" is skipped with "status='…' (scrap); excluded from COGS reversal" — no stock comes back, so the cost correctly stays on the books as a loss.

Missing cost is a hard stop, not a silent zero. If total COGS resolves to zero and at least one item had no resolvable cost, approval fails with HTTP 422 naming the items: "no Cost Price is set for … Set the Cost Price under Inventory → Products → Pricing". An explicit 0.00 in ProductPricing.cost counts as missing, deliberately. A pure scrap return legitimately resolves to zero COGS and is allowed: PostingEngineService checks restocksInventory first and skips the inventory entry entirely when no line is resaleable.

The inventory entry

Dr Inventory (1120)  costOfGoodsReturned
Cr COGS      (5101)  costOfGoodsReturned

Posted as its own journal with reference <returnNumber>-INV, separate from and independent of the revenue entry.

Average cost / WAC is deliberately not moved

reverseOutboundStock leaves stock_movements.unit_cost null. The WAC query (StockMovementRepository.getWeightedAverageCost) filters unitCost IS NOT NULL AND unitCost > 0, so a return never shifts the weighted-average cost. For FIFO/FEFO, the restocked batch keeps its original batch number and expiry, so DeliveryNoteService's batch picking sees it as the same lot it sold.

But the inventory sub-ledger value does not rise with the GL

Idempotency at the posting layer

Every journal method starts with findDuplicate(ref) and returns the existing entry if the reference was already posted. Because the reference is the return number (and -INV), a replayed approval cannot double-post the GL even if the status guard were bypassed.

14. POS Session / X-Report / Z-Report

A return is treated as a post-sale transaction scoped to branch + date, not to a session. sales_returns carries pos_session_id, but no report filters on it.

X-Report (PosSessionService.getXReport) — buildSessionReturnsSummary(session.branchId, session.sessionDate, invoices) loads every approved return for that branch+date and then keeps only those whose linkedInvoice is in this session's own invoice numbers. 15. Day Close Impact

Cash reconciliation — yes, correctly. Expected cash is opening + tender + dropIn − dropOut, computed once in PosCashReconciliationService.reconcile and reused by closeSession(), getXReport() and day close. A CASH_REFUND return's DROP_OUT therefore reduces expected drawer cash everywhere, automatically, with no report-specific code. This is the one place a return is fully wired into POS reconciliation.

Payment reconciliation — no. There is no per-tender reconciliation of refunds. A card refund produces no record, so card settlement (financials/settlement.CardSettlement) never sees it.

Net sales — not netted. PosDayClose.netSales is set from summary["netSalesExTax"], which PosSessionService computes as totalSales − totalTax over the day's invoices. Returns are published as separate keys (salesReturnTotal) and are not subtracted from gross or net sales. Only netQuantitySold nets returns, and only in quantity.

A second mismatch inside the same summary: salesReturnTotal is the return's totalAmount, i.e. VAT-inclusive, while netSalesExTax is ex-tax. A consumer that subtracts one from the other over-deducts by the VAT.

Consolidated cash position — deliberately excludes refunds. The comment at PosSessionService is explicit: "Cash Refunds/Returns are deliberately NOT included: SalesReturn has no payment-mode field today, so a 'cash refund' total cannot be computed without misclassifying every refund (cash+card+other) as cash. cashRefundsSupported=false flags this to the caller/frontend rather than silently reporting a wrong number."

That comment is now stale: V78 added refund_method, so a cash-only refund total is computable today. The flag still reports false.

Day-close gating. A return cannot be approved with a CASH_REFUND once closure has begun or the session has rolled to a new business day — addCashMovement runs businessDayContinuationGate.assertMayContinue and closureWorkflowGate.assertMayOperate, and rejects a closed session outright. Because the cash payout is the last step inside the approval transaction, that rejection rolls the entire return back: no stock, no journal, no document. Non-cash methods are unaffected and can be approved against a closed or stale session.

17. Transaction Boundaries

SalesReturnService.updateStatus is annotated @Transactional. Every side effect it invokes propagates REQUIRED and therefore joins that one transaction. The SalesReturnCashRefundService javadoc states the intent explicitly: "a return is never reported as refunded without the matching drawer movement, and never reported as settled by voucher without the voucher actually existing."

Inside the approval transaction — all-or-nothing:

OperationRolls back together?
sales_returns.status = APPROVEDYes
batch_allocations splits/flipsYes

serial_masters flipsYes
journal_entries / journal_lines / ledger_entriesYes
pos_cash_movements DROP_OUTYes

So the stated failure scenarios resolve cleanly:

  • Return invoice saved + stock update fails → the approval rolls back entirely. The return remains a DRAFT (the DRAFT row was committed by the earlier, separate POST call) and the frontend says so explicitly.
  • Stock updated + customer transaction fails → there is no customer transaction to fail, but the analogous case (stock updated, then the cash payout refused because the drawer is short or the session closed) rolls the stock movements back too.

Outside the transaction — the three real boundary breaks:

  1. The document and its approval are two HTTP calls. POST /api/sales/returns commits the DRAFT in its own transaction; PUT /{id}/status is a separate one. A failure between them leaves an unposted draft — benign and surfaced to the user, but it means the returns register can accumulate drafts that look like returns and are not.
  2. InventoryBalanceService.refresh is REQUIRES_NEW. It is called synchronously from reverseOutboundStock, inside the approval transaction, and suspends it. The new transaction therefore cannot see the stock movement that was just inserted but not yet committed, so inventory_balances is re-derived from the pre-return ledger. The row is written (and survives even if the approval rolls back), but with a stale on-hand quantity. The class comment describes the intent as "consistent with the stock movement already being visible", which holds for callers that commit before refreshing — not for this one. Exceptions are swallowed and logged, never propagated.
  3. Async POS audit. PosAuditService methods are @Async + REQUIRES_NEW. Irrelevant here only because the return path never calls them (see §18).

Lock ordering. Return row → invoice row → batch allocation rows → serial rows. Taken in that fixed order every time, which avoids deadlock between two concurrent returns. The invoice row lock is also what serialises two returns against the same sale.

18. Idempotency / Duplicate Protection

The primary guard is the row lock plus the terminal APPROVED state.

salesReturnRepository.findByIdForUpdate(id)   // PESSIMISTIC_WRITE, before status is read
...
if (salesReturn.getStatus() == SalesReturnStatus.APPROVED)
    throw new ResponseStatusException(BAD_REQUEST, "Approved returns cannot be modified.");

A double-clicked or retried approval blocks on the lock, then sees APPROVED and is rejected. findByIdForUpdate deliberately omits JOIN FETCH (some databases refuse FOR UPDATE alongside an outer join) and the full graph is re-read via findByIdWithItems inside the same transaction, returning the same managed instance.

Layered guards behind it

Stock movements have no idempotency key of their own. No duplicate check, and the unique index on stock_movements covers only quantity < 0. They rely entirely on the status guard.

Gaps

  1. POST /api/sales/returns accepts a caller-supplied status. saveReturn only defaults status to DRAFT when it is null. A client (or a retried/replayed request) that posts {"status":"APPROVED", ...} creates a row that reads as a fully approved return while no stock moved, no journal posted, no refund was paid, and no authorization was checked. The UI never does this, but the endpoint permits it, and such a row then counts against returnable quantity in assertReturnableQuantitiesStillAvailable and shows in every report as an approved return.
  2. The frontend's save is not idempotent. handleConfirm has no request key; the guard against a duplicate draft is sr.submitting and the disabled Confirm button. A dropped-response retry at the network layer would create a second DRAFT. Approving both is then blocked by the quantity revalidation — so the money is safe, but an orphan draft is possible.
  3. No POS audit trail. PosAuditAction declares RETURN_INITIATED, RETURN_APPROVED and RETURN_CANCELLED; PosAuditService.logReturnInitiated exists and has no callers; the other two actions are never used. SalesReturnController autowires AuditLogService and never calls it. So an ordinary return that needed no supervisor sign-off leaves no entry in any of the three audit subsystems — only the GL journal and the return row itself record that it happened.

22. Possible Inconsistencies / Risks

Ranked by business impact. "Alternate" describes what a conventional retail ERP would typically do — not a claim that the current behaviour is a defect.

R1 — Customer receivable never reduces High confidence

  • Observed: a return credits the AR control account in the GL but leaves sales_invoices.balance, customer outstanding, AR aging and the statement of account untouched, for every refund method.
  • Alternate: the credit is allocated against the original invoice's open balance, or held as a customer credit the next invoice can draw on.
  • Why they differ: no code was ever written to settle the AR credit outside the cash and voucher paths. CUSTOMER_CREDIT is documented and validated but unimplemented.
  • Code path: SalesReturnService.updateStatus (no AR settlement branch); CustomerService / sumOutstandingBalanceByCustomerCode as the outstanding definition.
  • Impact: a credit customer who returns goods is still chased for the full amount; the AR sub-ledger and the AR control account diverge permanently; reconcileAR reports a growing difference.

R2 — Card and bank refunds record nothing High confidence

  • Observed: CARD_REFUND and BANK_TRANSFER are selectable and stored, and settle nothing: no payment reversal, no refund record, no cash movement, no settlement entry.
  • Alternate: a negative payment / refund record linked to the original tender, visible to card settlement reconciliation.
  • Why: the enum documents the intent ("via the existing payment architecture"); the implementation branches only on isCashDrawerAffecting() and CREDIT_VOUCHER.
  • Impact: the business has no system record that a refund is owed or was paid; the GL credit to AR is never cleared.

R3 — Return absent from the customer statement High confidence

  • Observed: no SoA row. StatementService.PRI_RETURN_CREDIT is declared and unused — the slot was designed and never implemented.
  • Impact: the customer-facing statement cannot be used to explain a return; disputes have no document trail on the SoA.

R4 — Non-batch stock silently not restocked when no DN exists High / Medium

  • Observed: resolveReturnWarehouseId returns null unless the invoice has a linkedDeliveryNote with a warehouse, and the line is then skipped with a warning while the GL still debits Inventory.
  • Impact: physical goods come back, on-hand quantity does not rise, GL inventory does. The code's own log admits the mismatch.
  • Note: exposure depends on whether POS checkout always auto-generates a DN. PosCheckoutController comments say the DRAFT → PAID transition fires "auto-DN generation, stock deduction", so for POS sales a DN usually exists — but back-office invoices that deducted stock by another route, and any invoice whose DN lacks a warehouse, fall through.
  • Confidence: High that the branch exists and skips; Medium on how often it is reached in production.

R5 — Inventory GL vs inventory valuation diverge on every return High confidence

  • Observed: the return's inbound stock_movements row has unit_cost = null, so sumGlobalInventoryValue() ignores it, while the GL debits Inventory by costOfGoodsReturned.
  • Alternate: stamp the resolved COGS unit cost on the movement.
  • Impact: reconcileInventory drifts by the COGS of every restocked return (tolerance is AED 1.00). Note the null is also what protects WAC from distortion, so this is a genuine trade-off, not an oversight.

R6 — Cross-branch return splits financial and inventory effect High / Medium

  • Observed: the return is stamped with the current user's branch while stock returns to the invoice's warehouse. An ADMIN with global scope can do this; a BRANCH_ADMIN is stopped at eligibility.
  • Impact: branch P&L and branch Z-Report attribute the reversal to the wrong branch; branch stock levels move in the right one.
  • Confidence: High on the mechanism; Medium on whether cross-branch returns are intended to be possible at all.

R7 — POST accepts status: APPROVED High code / Low exposure

  • Observed: saveReturn defaults status only when null, so a direct API call can create an already-approved return with no stock, GL, refund or authorization.
  • Impact: a phantom approved return that consumes returnable quantity and appears in every report. Requires API access with create permission, so the practical risk is a buggy or replayed integration rather than the UI.

R8 — Day-boundary split between the return and its cash payout High / Medium

  • Observed: the return and its GL journal are dated return_date (the browser's calendar date); the drawer movement and its journal are dated session.sessionDate.
  • Impact: at a day boundary one cash refund lands in two different business days across the Z-Report and the GL. Period-close reconciliation will show an unexplained cash difference.

R9 — netSales in POS reports is not net of returns, and bases are mixed High confidence

  • Observed: netSalesExTax excludes returns entirely; salesReturnTotal is VAT-inclusive while netSalesExTax is ex-tax.
  • Impact: any consumer that nets the two over-deducts by the VAT. "Net sales" on the Z-Report and day close is really gross sales.

R10 — Refund buckets in X/Z misclassify High confidence

  • Observed: bucketing keys off the free-text returnAction, which the UI sets to "Refund" for cash, card, bank and customer credit alike. "Replacement" is never produced, so exchange buckets are dead. refund_method exists on the row and is not used by the reports.
  • Impact: refundTotal overstates refunds actually paid out; the stale cashRefundsSupported=false flag also suppresses a now-computable cash-refund figure.

R11 — No audit record for an ordinary return High confidence

  • Observed: PosAuditService.logReturnInitiated has no callers; RETURN_APPROVED / RETURN_CANCELLED are unused; SalesReturnController autowires AuditLogService without calling it. Only supervisor-gated approvals are audited.
  • Impact: a return that needed no sign-off — the common case, since both thresholds default to 0/disabled — leaves no audit entry in any of the three audit subsystems.

R12 — inventory_balances refresh cannot see its own movement Medium-high

  • Observed: InventoryBalanceService.refresh is REQUIRES_NEW and is called from inside the approval transaction, so it recomputes from a ledger that does not yet contain the just-inserted movement.
  • Impact: the pre-aggregated balance lags by one return until the next movement for that product/warehouse refreshes it. Reports that read inventory_balances rather than the ledger show the stale number. Exceptions are swallowed.
  • Confidence: the propagation and call site are unambiguous; the exact visibility depends on the transaction isolation level in effect, which was not verified against a live database.

R13 — Proration keys on item code, first line wins Medium

  • Observed: invoiceItemByCode.putIfAbsent and soldByCode.merge mean an invoice with the same product on two lines at different prices prorates against the first line's price while the quantity ceiling sums both.
  • Impact: refund value can be wrong for mixed-price repeat lines. Depends on whether POS ever writes two lines for one product (it merges by default, but a price override can split them).

R14 — Serial handling is per item code and ignores condition Medium

  • Observed: one serial per item code from the invoice; the flip to RETURNED happens even for a scrapped unit.
  • Impact: multi-unit serialized returns under-record; scrapped serials look resaleable.

23. Open Questions

These need a business or accounting decision; the code cannot answer them.

  1. Should a return reduce the customer's outstanding balance? If yes, by what mechanism — allocate against the original invoice's open balance, or create a standalone customer credit the next invoice draws on? The two give different aging behaviour.
  2. Is CUSTOMER_CREDIT meant to exist? It is documented, validated and unimplemented. Either it needs an implementation or it should be removed from the vocabulary so cashiers cannot choose it.
  3. What is supposed to happen on a card refund? A record of an obligation, an actual reversal through the card terminal, or an out-of-band process the system just notes? This determines whether CARD_REFUND needs a payment record, a settlement entry, or both.
  4. Should the return appear on the customer statement of account? And if so, as a credit row dated on return_date, with what description and reference?
  5. Should a return against an unpaid or partly-paid invoice be allowed to pay out cash at all, or must the credit first be applied to the open balance?
  6. Are cross-branch returns permitted? Today a global admin can raise one, with the financial effect landing in their own branch and the stock in the invoice's. If permitted, which branch should own the reversal?
  7. Which business day owns a return? return_date (calendar), trading_date (session), or the original sale's date? The answer should be the same for the document, its GL journal, its stock movement and its drawer payout — currently all four can differ.
  8. Should "net sales" on the Z-Report and day close be net of returns? If yes, on which base (ex-tax vs inclusive) — the two figures currently published are on different bases.
  9. Should a return without a linked invoice be possible? The code tolerates it and skips the quantity guard entirely. If unlinked returns are a real business case, they need their own rules; if not, they should be rejected.
  10. Should "exchange" / Replacement exist? The X/Z reports have buckets for it and the UI never produces it. Is an exchange meant to be a return plus a new sale, or its own document?
  11. Should scrapped returns be routed anywhere? Today a DAMAGED / DEFECTIVE / EXPIRED line restocks nothing, keeps the cost on the books, and leaves no quarantine or supplier-claim record. The condition is captured but not acted on beyond the restock decision.
  12. What should the inbound stock movement's unit cost be? Stamping the resolved COGS would reconcile inventory with the GL but reintroduces WAC movement on returns. Which matters more here?
  13. Is sales_returns intentionally outside the BaseEntity / soft-delete convention? It is one of the few entities with an IDENTITY id, no isActive flag and a physical deleteById. Deliberate for an immutable financial document, or an oversight?
  14. Which AR account code is live — 1110 or 1100? The javadocs disagree while the constant is shared. Worth confirming against the seeded chart of accounts per tenant.
