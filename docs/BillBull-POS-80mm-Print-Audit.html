The 80 mm Roll

Every receipt, slip, voucher and report the POS can push to an 80 mm thermal printer — reconstructed from the code that actually builds the bytes, not from the screens or the settings copy. Nineteen live print paths, thirteen documented gaps, and twenty-eight defects between what the paper says and what the ledger holds.

How this was determined

Every claim below was traced to a builder function, its call sites, and the option bag actually passed at those call sites. Where a value is a default that a call site never overrides, that default is what prints — and it is reported as what prints.

Four builders produce essentially all 80 mm output. buildEscPosReceipt (Template 1) emits ESC/POS text with rastered logo and native QR. renderBilingualReceiptCanvas (Template 2) paints the whole receipt to a canvas and ships it as one raster. buildEscPosDocument wraps a plain-text body in a shared branded header and is used by every voucher, statement, layaway, return and report. buildThermalReceiptText is the text/GDI fallback — and, as shown in F6, it is a materially different document from the ESC/POS one it substitutes for.

Physical geometry is fixed in escPosReceipt.js: 80 mm paper is 576 dots / 48 Font-A columns, with a one-column software gutter each side, so every body is built to 46 usable columns. There is no GS L/GS W hardware margin — it was deliberately removed after a POS-80C leaked the width payload as a stray glyph. The mockups below are rendered at that exact 46-column width; the ruler above each one marks columns 1, 10, 20, 30, 40, 46.

Sample values in the mockups are illustrative. They demonstrate the layout the code produces — field order, labels, alignment, separators, what is present and what is absent. They are not observed output and are not evidence of any figure being correct.

F

Findings

Twenty-eight defects, ordered by what they cost. Each was traced to the code that produces it; nothing here is inferred from a screenshot or a settings label.

Critical — compliance, money, or a document that cannot do its job

F1Refund receipts and credit vouchers print with no company header at allMISSING

The Sales Return screen calls the print helpers without a header object. It defaults to {}, so the shared branded header receives empty strings for company name, address, phone, TRN and document title, and a null logo — and emits nothing but its closing divider.

Both documents affected are exactly the ones that must carry issuer identity: a refund receipt is a credit-note-class document, and a credit voucher is a bearer instrument redeemable for money. Neither names the business that issued it.

SalesReturnScreen.jsx:265,279 → salesReturnPrint.js:253,281 → escPosReceipt.js emitEscPosBrandedHeader

F2The printed QR is not a ZATCA code — and the real one is generated then discardedINCORRECT

The receipt QR payload is buildQrContent output: a multi-line human-readable text blob listing type, doc number, date, company, customer, every line item, and totals. It carries no cryptographic or structural verification of any kind, and the caption printed under it reads “Scan to verify”.

Meanwhile PosCheckoutController builds a correct UAE FTA Phase-1 TLV via ZatcaQrGenerator on every checkout, and no print path consumes it. A frontend twin, buildZatcaTlvBase64, is imported into the POS screen and never called.

POSSales.jsx:166 (dead import), :4996 → printGenerator.js:79 · PosCheckoutController.java:388,583,632 · posPrintUtils.js:242

F3Receipts can print a dummy company identityINCORRECT

Company name, address and phone come only from PosSettings.printTemplateConfig. When a tenant has never saved a print template, the React state defaults stand and every sale receipt prints “BillBull Trading LLC”, “Shop 12, Dubai Mall, Downtown Dubai”, “+971 4 123 4567”.

TRN, by contrast, correctly chains to the branch record and then the company profile — and the Customer View screen’s own branding does fall back to the company profile. So one terminal can print a Payment Receipt with the real company name and a Sale Receipt with the sample one.

POSSales.jsx:1203-1208 (defaults), :2295-2303 (only override) vs :1217 (TRN chain) and CustomerView.jsx:43-52

F4The Delivery Order slip contains no delivery informationINCORRECT

Out-for-Delivery prints an ordinary sale receipt titled TAX INVOICE with the credit block forced off. Delivery address, driver, delivery date, time slot and special instructions are collected in the modal and concatenated into the invoice notes field — which no thermal builder reads. There is no recipient signature line and no delivery-order document number distinct from the invoice.

POSSales.jsx:4240-4295; escPosReceipt.js buildEscPosReceipt has no notes or delivery section

F5Delivery Settlement prints “Cash Received” for card paymentsINCORRECT

The settlement passes the settled amount as cashGiven and supplies no payment block. The builder’s fallback branch is reached and prints the row hardcoded as Cash Received regardless of the tender the cashier actually selected in the settlement dialog.

POSSales.jsx:15417 → escPosReceipt.js:1052

F6The text/GDI fallback is a different document, and it is also the audit payloadDIVERGENT

buildThermalReceiptText substitutes for the ESC/POS receipt whenever a v4/WSD-class driver refuses raw output. It is built to 42 columns instead of 46, and drops the logo, the QR, the stamp, the CREDIT ACCOUNT block, all payment-allocation rows, and per-line VAT. It puts the customer block above the items where the ESC/POS version puts it below the payment block. It has no isReprint parameter at all, so a reprint that falls back loses its COPY marking.

This same text is passed as receiptText on every ESC/POS print and stored as the PosPrintJob payload — so the print-job audit trail records a document that in most cases was never the one printed.

posPrintUtils.js:723-891 · localPrintAgent.js sendEscPosReceiptToConfiguredPrinter (payload + fallback)

The Reprint panel passes no payment block, no cash given and no change, so the reprint shows only a single “Payment Mode” row — the tender breakdown of the original sale is gone. The Last Receipt dialog reprints the same invoice and does pass cash given, change and the credit-account figures from in-memory checkout state.

Two reprints of one sale therefore differ in their payment section and in whether a CREDIT ACCOUNT block appears. Neither is wrong about the totals; they simply are not the same document.

F8The cash drawer never opensMISSING

openCashDrawer dispatches a pos:open-cash-drawer DOM event. No listener for that event exists anywhere in the codebase, no ESC/POS drawer-kick pulse (ESC p) is emitted by any builder, and the print agent has no drawer endpoint. Every drawer trigger — receipt print, manual open, cash movement — is a no-op.

The agent’s own printer-probe notes identify tall rasters as the discriminating failure case on clone controllers. Template 2 caps logo height at 180 dots; Template 1 does not.

The QR content includes one line per basket item. The emitter shrinks module size until the symbol fits the paper, with a floor of 2 dots per module. A large basket therefore prints a high-version symbol at 2–3 dots per module on a 203 dpi head with error correction M — marginal for a phone camera on thermal paper, and the failure is silent.

Recommended standard 80 mm layout

One skeleton for every document, with a single shared header emitter that cannot be called with an empty bag. Nine bands; which are mandatory depends on the document class, not on the call site that happened to build it.

BandContentsRule
1 · HeaderLogo (height-capped, never upscaled) · company name · branch · address · telephone · TRNMANDATORY on every document — the header builder should reject an empty company name rather than emit a bare divider.
2 · Document identityBold document title · document number · business date · time · terminal · counter · cashier · COPY/REPRINT marker with sequence numberMANDATORY — every document, including vouchers, statements and reports. Reprint marking must survive the text/GDI fallback.
3 · Counterparty / orderCustomer name, code, mobile, TRN, address · for delivery: address, driver, date, time slot, instructionsDOCUMENT-SPECIFIC — mandatory on any credit, delivery or settlement document; optional on a walk-in cash sale.
4 · Detail linesItem block, ledger entries, denomination rows or report sections, depending on classDOCUMENT-SPECIFIC — must be wrappable, never column-collapsed and truncated.
5 · Financial summarySubtotal · discount · taxable · VAT · charges · voided disclosure · TOTAL at double heightMANDATORY on any document carrying an amount. Every figure sourced from the persisted record, never re-derived.
6 · Payment / settlementOne row per tender, from the persisted allocations · change · rounding · deposit · balance due · credit account movementMANDATORY where money moved — and must be reconstructible on reprint, not dependent on in-memory checkout state.
7 · Audit informationSession number · approver for overridden actions · print sequence · generated-at, labelled as a print stamp not as contentMANDATORY on financial documents, optional on a plain cash sale.
8 · Machine-readableZATCA TLV QR for tax invoices · Code 39/128 barcode of the document number · both, not one instead of the otherMANDATORY on tax invoices; barcode recommended on every document a cashier may need to recall.
9 · FooterThank-you · return policy · configured footer text · stamp or signature line · feed-then-cut with head-to-cutter clearanceMANDATORY — stamp should accompany the QR, not replace it, and the cut must always clear the blade.

The three structural changes that close most of the findings

  • Make the branded header non-optional. A single required company-profile argument, resolved once from branch → company with no sample defaults, would close F1, F3 and half of F25 at once.
  • Persist the print payload, not the screen state. Payment allocations, credit-account figures and delivery details should be reconstructible from the record so a reprint is byte-identical apart from its COPY marker — closing F4, F5, F7 and the reprint half of F26.
  • Give the text/GDI fallback the same body. One builder emitting either ESC/POS bytes or plain text from a single layout description, at one width, would close F6 and remove the audit-payload mismatch behind it.
