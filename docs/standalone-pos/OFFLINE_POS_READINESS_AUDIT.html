Offline POS Readiness Audit

How the current standalone till works, what stops it working without Internet, and the safest way to add offline selling without a second copy of POS business logic. Read-only audit: no files, migrations, configuration or services were changed.

SUMMARYWhat we found

01

CONFIRMED The standalone POS is a thin shell (apps/pos, ~1,950 lines) around the same shared workspace as /sales/pos (POSSales.jsx, 11,037 lines, in @billbull/shared). It is a browser SPA served at /pos/ on each tenant's existing HTTPS origin, talking same-origin to the tenant's Spring Boot backend. The Electron app tools/pos-desktop loads that same remote page. Nothing is installed locally except the print agent.

02

MISSING There is no offline capability at all today. No service worker, no web manifest, no IndexedDB, no online/offline detection. Every boot needs the server (login, permissions, terminal register, session, settings). Every new scan calls GET /api/pos/resolve. Settlement is refused unless GET /api/pos/checkout/capabilities answers. The JWT lives in sessionStorage, so a closed tab cannot be reopened offline. When the server is unreachable, Electron replaces the till with an offline page.

03

PARTIAL Checkout already has an idempotency key (checkoutKey, unique partial index uq_si_pos_checkout_key from V13), and the client treats timeouts as "unconfirmed". This is the best foundation for sync. But the key lives only in a React ref, so a refresh loses it. And the checkout is not atomic despite its Javadoc: invoice save, status/stock/GL posting, and each payment leg commit in separate transactions, with a compensating delete. If a payment leg fails after posting, a retry with the same key gets back the posted invoice as if it were a success. This must be fixed before any offline replay depends on the key.

04

DECISION Invoice numbers come from one tenant-wide counter per document type, locked FOR UPDATE at save time (SalesDocumentNumberingService). There is no per-branch or per-terminal series. An offline receipt therefore cannot carry its final tax invoice number unless number blocks are leased per terminal. This needs a tax/compliance decision.

05

CONFIRMED Stock is checked at posting time under row locks, governed by the global SalesSettings.stockCheckRequired. When it is on, a shortfall refuses the sale. When it is off, the movement goes negative with negativeOverride set. An offline sale has already taken the customer's money, so at sync it must never be refused for stock. It must post with the override and be flagged for review.

06

PROPOSED Recommendation: browser POS + terminal-local durable outbox (IndexedDB) + cloud, with offline sales replayed through the same checkout pipeline via a new batch-ingest endpoint. Offline selling is restricted: cash (and optionally card on an external terminal), untracked or auto-FEFO products, inside a session that was already open, under a server-issued offline lease. A Store Node is deferred to an optional later phase, as a relay and cache only, never as a second ledger. The first phase (Phase 0) changes no offline behaviour. It fixes checkout atomicity detection and persists the in-flight checkout key.

Request lifecycle: opening the till to a completed sale

  1. Load. nginx serves /pos/index.html (no-store) and hashed /pos/assets/* (immutable). The Inter font comes from Google Fonts without blocking render.
  2. Sign in. PosLogin calls POST /api/auth/login, or the PIN path with the device token from localStorage billbull:pos:pin_device. persistLoginSession writes token, user and role to sessionStorage.
  3. Gates. RequireAuth (once), then PermissionProvider fetches permissions, then SessionLock, then RequirePosAccess (sales.pos + sales.invoice), then PosBootGate (one branch via switchBranch).
  4. Terminal. usePosSession reads or creates the fingerprint and calls POST /api/pos/terminals/register. A 403 means archived, blocked or at the limit, and shows TerminalUnavailableOverlay. Heartbeat runs every heartbeatIntervalSeconds.
  5. Session & day. GET /api/pos/sessions/active?terminalId and /day-status. If no session is open, the cashier runs Start Session (POST /sessions/open, with the opening count defaulting to the last close). Overlays handle a previous business day still open, closure required, and so on.
  6. Settings. POS settings, tax config, layout (Classic, Compact or Cart Focus) and print templates load into POSSales state.
  7. Scan. The in-memory cache is checked first, then GET /api/pos/resolve?q=. The line is added client-side; totals use vatMath. Price levels and customer prices are re-resolved via the pricing hooks.
  8. Pay. GET /checkout/capabilities must say "supported", or Settle is disabled. Payment lines are reconciled client-side. When the template shows a credit block, GET /api/pos/credit-balance runs first.
  9. Settle. POST /api/pos/checkout with a checkoutKey tied to a fingerprint of the payload. The server steps are listed below.
  10. Done. The success screen shows and the cart clears. In the background: drawer pulses, receipt (agent ESC/POS, backend socket for network printers, or browser print), layaway conversion, PosPrintJob bookkeeping.

What POST /api/pos/checkout does on the server

From PosCheckoutController.checkout (lines 228–549). Each TX marks a separately committed transaction. The controller itself is not @Transactional.

  1. Till permission, then idempotent replay: findByPosCheckoutKey. If found, the existing invoice is returned, even after the business day has closed.
  2. Session gates: previous-business-day continuation, then close-workflow gate. Then the business-day checkout gate (423, unless a supervisor authorizes this one sale).
  3. Validate before writing: allocation structure, price level, salesperson/target readiness, mandatory customer, Sales Order take-up.
  4. buildInvoice: invoice date = session business date, terminal/session/counter stamped, minimum-price gate (with supervisor PIN, negotiated-price allowance and bill-discount share).
  5. invoiceService.save: number from the locked tenant-wide counter, pricing record (client-charged prices are kept), warehouse defaulting. TX 1
  6. Resolve the payment plan. On failure the controller calls deleteQuietly.
  7. updateStatus(PAID | PARTIALLY_PAID | CONFIRMED): FEFO/batch reservation, auto Delivery Note, stock movements, GL invoice journal, credit-limit policy. TX 2. On failure: deleteQuietly.
  8. For each allocation: voucher redeem (row lock) and recordPayment, giving a Payment row, a Receipt Voucher and GL. TX 3…n. No compensation if one of these fails.
  9. recordInvoiceOnSession (session tender counters, authoritative close-workflow re-check). TX
  10. Best effort: Sales Order conversion, serials marked sold, ZATCA QR archived, sale stats, audit, terminal activity.

Why this matters for offline. A sync engine retries. With the current shape, a retry after a failure in step 8 or 9 returns HTTP 200 with an invoice whose payments are missing or partial. The sync would record that as "acknowledged". Phase 0 must make an incomplete checkout detectable before replays rely on checkoutKey.

Limitations caused by the deployment

  • The UI is always fetched from the server. Neither the browser nor Electron can start the till without the origin, because nothing is cached.
  • A tenant is identified by its hostname. An offline-capable till is bound to one tenant origin, which is fine. A Store Node on the LAN would need its own origin, and that changes the service worker, storage and token scope (see §7).
  • Network printers depend on the cloud backend opening a socket to the printer's LAN IP from the VPS. Treat this path as unavailable offline. Only agent-driven printers keep working.
  • Google Fonts is external. The fallback font is acceptable offline. The font could also be precached or self-hosted.

Other technical limitations found

  • Business date comes from the server. posBusinessDate(sessionId) stamps the invoice with the session's business date. This helps: a replayed sale keeps the date of the session it was rung in. But the business-day checkout gate uses the server's clock now, so a sale replayed after the window closed would get a 423 today.
  • Session sync poll. Failures are swallowed, so offline does not lock the till. When the network returns, a session closed remotely by an admin in the meantime invalidates the till and resets the cart. Pending outbox records must survive that reset.
  • POSSales.jsx is line-pinned. Characterization tests pin source lines (for example the PromotionsDialog pins). Offline logic should live in new hooks and modules, with the smallest possible edits in POSSales.jsx.
  • Two places for "held sale". The till's Hold uses layaways, while pos_held_sales and PosHeldSaleController also exist. Offline parking should be local and separate from both.

REPORT §7Store Node recommendation

Do not build a Store Node for the first offline release. Revisit it after Phase 2 telemetry shows how often and for how long branches with three or more terminals are offline, and how often they oversell.

If one is built later, its role should be kept narrow:

  • It does: mirror the branch catalog snapshot (fewer cloud downloads), receive copies of each till's signed offline records and forward them, keep per-SKU "sold offline" counters so tills can warn on likely oversell, and report device health.
  • It does not: number invoices, post GL, deduct stock, or accept a sale the till has not already stored in its own outbox. The terminal outbox stays the source of truth until the cloud acknowledges.
  • Packaging: the same tech as the print agent (Node, packaged as a Windows service), with SQLite. No Postgres at the store.
  • Origin problem: the till must keep loading from the tenant origin. The node would be a second, LAN-only API (for example https://storenode.local:19800) called by an explicit client, with its own pairing just like the print agent. It must not become the page origin.
  • Authentication: node enrolled by an admin, holding a device key; tills authenticate to it with their terminal key; mTLS or signed requests on the LAN.

Survival

  • Refresh / browser closed / PC restart: IndexedDB survives. The service worker serves the shell. The outbox resumes. The working draft is restored.
  • Cleared site data or a new browser profile: pending records are lost. Mitigations: the Electron shell (its profile is not cleared by users), a "pending sales" warning before sign-out, and an optional backup copy (to the print agent or, later, a Store Node). The server detects the loss as a sequence gap.
  • Store Node restart: not applicable in the recommended phases. Later, the terminal outbox remains authoritative.

  REJECTED --> REVIEW

The offline sale record

{
  offlineSaleId:   UUIDv7      // also sent as checkoutKey, so an earlier "unconfirmed" online attempt dedupes
  terminalId, branchId, sessionId, businessDate,   // businessDate from the session open at capture
  localSeq:        n           // per terminal, gap-free, from the IndexedDB counter in the same tx
  capturedAt:      device time + serverOffset at last sync
  cashierUserId, leaseId, catalogVersion,
  request:         PosCheckoutRequest   // the exact body the online path sends; no new shape
  prevHash, hash:  SHA-256 chain over (prevHash, canonical record)
  signature:       HMAC-SHA256(terminalKey, hash)
}

How it fits the current checkout

  1. One pipeline. Move the body of PosCheckoutController.checkout into PosCheckoutService.checkout(request, CheckoutContext). The online endpoint calls it with CheckoutContext.ONLINE, with no behaviour change. The new PosOfflineSaleIngestService calls it with OFFLINE_REPLAY(record).
  2. What replay changes, explicitly. The business-day checkout gate is evaluated against the captured session and business date, not the server's current time. Stock shortfall becomes a negative override with a review flag. A price below minimum is refused (the client should never send one). The voucher, credit, advance and online allocation types are refused.
  3. Dedupe, in layers. (1) Unique pos_offline_sales(offline_sale_id). (2) Unique (terminal_id, local_seq). (3) The existing unique sales_invoices.pos_checkout_key. (4) The Phase 0 completion marker, so an incomplete earlier attempt is never reported as success.
  4. Ordering. Send in localSeq order, batches of up to 20. The server processes them sequentially per terminal and records highWaterSeq. A gap stops acceptance past it and raises a review item.
  5. Retry. Exponential backoff with jitter (2 s doubling up to 5 min). Retry immediately on an online event or a successful heartbeat. 4xx results are final per record, not retried; 5xx and network errors are retried.
  6. Acknowledgement. Each record returns ACCEPTED | DUPLICATE | REVIEW | REJECTED, plus invoiceId, invoiceNumber and a reason code. The till stores it and can then offer reprint or email of the final tax invoice.
  7. Reconciliation. Heartbeat carries {pendingCount, highWaterSeq, oldestPendingAt}. The server compares this with the ingested high-water mark and shows mismatches in POS Administration. Session close and Day Close use it as a gate.

PART 7 · REPORT §11Inventory and financial restrictions

Multiple terminals selling the same stock while disconnected

Each till sees only its cached snapshot. Two tills can each sell the last unit. At sync, the first replay deducts normally and the second either fails (when stockCheckRequired is on) or goes negative (when it is off). Because the customer has already paid and left, replay must never refuse for stock. It posts with StockMovement.negativeOverride (an existing flag that bin reports already surface) and creates a review item. This is acceptable for untracked goods. It is not acceptable for unique units (serials, per-unit batch numbers), so those are blocked.

REPORT §16Testing strategy

  • Unit (frontend): offline policy matrix, outbox state machine, hash chain and signature, sequence allocation under concurrent tabs. Use fake-indexeddb with Vitest.
  • Unit (backend): PosCheckoutService extraction run against the existing checkout tests unchanged; replay context rules (business-day gate, negative override, refused tenders); completion-marker detection; ingestion dedupe across all four layers; signature, lease and gap handling.
  • DB-backed: concurrent duplicate submissions (two threads, same key), named *Test (a *IT class never runs). Run against a clone of testdb on a disposable 8081 backend, never testdb itself.
  • End to end: extend tools/pos-parity with Chrome DevTools offline emulation: ring N sales offline on two tabs as two terminals, restore the network, then diff invoices, stock movements, GL and session totals against the same sales rung online.
  • Chaos: kill the tab mid-sync; restart the PC (Electron); skew the clock backwards and forwards; expire the lease mid-outage; revoke the terminal; force-close the session from back office while records are pending.
  • Hardware: the HARDWARE_CHECKLIST.md runs (agent printer and drawer offline). Network printers are expected to fail.
  • Pilot: one branch, cash only, offline mode enabled per branch, with a daily reconciliation report.

RECOMMENDATIONRecommended architecture and the first phase

Architecture: keep the standalone till as the browser or Electron app on the tenant origin. Add a terminal-local, signed, append-only outbox in IndexedDB and a cached catalog. Replay offline sales into the cloud through a refactored PosCheckoutService, so there is one copy of the checkout logic, with an explicit replay context. Offline selling is a narrow, server-leased privilege of enrolled terminals: cash first, untracked or auto-FEFO goods, within a session already open. Everything with a server-side balance, lock or number (credit, vouchers, returns, layaways, X/Z, Day Close) stays online-only. No Store Node until the data says it is needed.

Phase 0, the first implementation phase

  1. Detect incomplete checkouts. Add pos_checkout_completed_at, written as the final step of PosCheckoutController.checkout. When a checkoutKey replay finds an invoice without it (and created after the migration), return 409 CHECKOUT_INCOMPLETE with the invoice id, log a POS audit event, and show "needs supervisor check" instead of a false success.
    DECISION Alternative: wrap the steps in one transaction. This is cleaner, but it would hold the tenant-wide invoice-number row lock for the whole checkout, through stock, GL and payments, and serialize every sale on the tenant. A marker is recommended for now.
  2. Persist the in-flight attempt. In useCheckout.js, write {checkoutKey, fingerprint, payload, startedAt} to IndexedDB before posCheckout, and clear it on a definite answer. On boot, if one exists, show "Checking the last sale…" and re-send the same key before allowing a new sale.
  3. Persist the working cart per terminal, so a refresh restores it.
  4. Tag network errors in axiosConfig.js and show a read-only connectivity badge on the till rail.
  5. Tests: backend marker and replay tests (including a negative control), frontend refresh-mid-checkout tests, and a parity run on a disposable clone.

Dependencies: Dexie (or raw IndexedDB) in @billbull/shared; one Flyway migration. Risk: low. Rollback: revert the commits; the new column is nullable and unused by everything else.

Decisions needed before Phase 2: offline invoice numbering (provisional vs leased blocks); whether card on an external terminal is allowed; auto-FEFO for expiry goods; the offline unlock rule for cashiers; the lease limits per branch.
