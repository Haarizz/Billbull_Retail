V1Terminal cryptography

Defect The server cannot verify an HMAC-SHA256 signature if it stores only a hash of the terminal key.

To verify HMAC(K, m), the server has to compute the same value, and that needs K itself. SHA-256(K) does not let anyone compute HMAC(K, m). The proposal copied the pattern from PIN devices: PosPinLoginService stores sha256(token) (pos/pinlogin/PosPinLoginService.java:94) and verifies by hashing the token the client sends (:224, findByTokenHashAndRevokedAtIsNull(sha256(...))). That works for a bearer token because the client sends the secret on every request. An offline signature never sends the key, so the pattern does not carry over. If the server used the stored hash as the HMAC key instead, the hash would become the secret, and "store only the hash" would no longer mean anything.

What "non-extractable" protects. It stops page script, including injected script, from exporting the key. It does not stop injected script from using the key while it runs. It also does not stop someone who copies the whole browser profile from disk. A valid signature proves "made by whoever holds this terminal's browser profile", not "made by an honest cashier". The lease limits and server-side reconciliation stay the real financial controls.

Recommended design: option B, ECDSA P-256

  1. Enrollment (online, admin-approved). In POS Administration, an admin creates an offline enrollment for terminal T. The server returns a short-lived single-use code and stores only its SHA-256 (the PIN-device pattern is correct for this bearer code). The till generates a non-extractable P-256 pair and posts {terminalId, spkiPublicKey, code}. The server checks the code, binds the key to the terminal's primary key and branch, assigns a keyId, and returns keyId plus the tenant's lease-signing public key. The till stores the private CryptoKey, the keyId and the pinned server public key in IndexedDB.
  2. Signing offline records. Canonicalize each record with RFC 8785 (JSON Canonicalization Scheme), including prevHash, keyId, leaseId and localSeq. Hash it with SHA-256 and sign with {name:'ECDSA', hash:'SHA-256'}. Store the signature as base64url P1363. Shared test vectors must prove that JavaScript and Java canonicalize byte-identically.
  3. Server signs leases. Use a per-tenant P-256 lease-signing key held server-side, outside the tenant database (keystore file or secret store), so a leaked database cannot mint leases. Issue the lease as an ES256 compact JWS. jjwt 0.11.5 is already a dependency and supports ES256. Claims: leaseId, terminalPk, keyId, branchId, sessionId, tradingDate, iat (server clock), notAfter (server clock), maxSales, maxCashMinor, seqStart, tenders, productClasses, catalogVersion, policyVersion. The server also stores the lease row (pos_offline_leases), which is the authority.
  4. Browser verifies leases. ES256 JWS signatures are raw r‖s, so crypto.subtle.verify({name:'ECDSA', hash:'SHA-256'}, pinnedServerKey, sig, signingInput) works directly. This check only catches local corruption or casual edits. At ingest the server never trusts the till's copy: it loads the lease by id.
  5. Revocation and rotation work as in the table. Keys are never deleted. Records arriving under a revoked key are stored and routed by the rule in V4, never rejected unseen.

V2Outbox and printing

Defect In the proposed state machine, CAPTURED → PENDING happens only after "receipt printed / drawer opened". A durable sale can therefore get stuck in all four cases asked about.

CaseUnder the proposed machine
Printer disconnectedThe record stays CAPTURED and never syncs. The server never learns about cash it is owed.
Print agent unavailableSame. USB, Bluetooth and Windows-queue printers all go through the agent.
Drawer failsOffline, this happens on every sale (see below), so no offline sale would ever sync.
Crash after the IndexedDB commit, before printingOn restart nothing says whether the receipt was printed, and no transition moves the record on.

New BillBull cannot open a cash drawer offline today. openCashDrawer only dispatches a pos:open-cash-drawer window event (packages/shared/src/pages/Sales/POS/device/cashDrawer/useCashDrawer.js:28-33). No listener for it exists in packages/shared, apps/pos, the Retail src or tools/pos-desktop. The print agent refuses ESC p drawer pulses (tools/pos-print-agent/lib/escposPolicy.js:84). The only drawer pulse BillBull can deliver goes through a server-relayed network printer print, which PosPrinterService:164 checks against PosDrawerKickAuthorizer, and that requires an OPEN session verified on the server. None of this works offline. The drawer would have to open through the Windows printer driver's "open drawer on print" setting or the drawer's manual key. verify on pilot hardware

The online path already uses the right order. useCheckout.js shows success only after posCheckout resolves (:317-331), then prints and opens the drawer in a fire-and-forget block whose failures only warn (:416-470). The offline design should keep that order, with the IndexedDB commit taking the place of the server's confirmation.

Corrected model: three independent tracks

Sync state, print state and drawer state are separate fields on the stored record. Only the sync track decides whether the server learns about the sale.

stateDiagram-v2
  direction LR
  [*] --> COMMITTED: Settle, one IndexedDB tx (durability strict) writes record, localSeq, lease counters, chain head
  COMMITTED --> SENDING: online, worker holds Web Lock
  SENDING --> COMMITTED: transport error or retryable code (backoff)
  SENDING --> RECEIVED: server stored the signed record (its own commit)
  RECEIVED --> [*]: purge after retention (e.g. 30 days)

Print track (never gates sync)

NOT_REQUESTED → QUEUED → PRINTING → PRINTED
                                ↘ FAILED → QUEUED (reprint)

The receipt is always rendered from the stored record, never from React state, so the paper matches what syncs. On boot, any record in QUEUED or PRINTING raises a "receipt not printed for OFF-…" prompt.

Drawer track (log only)

REQUESTED → OPENED | FAILED | MANUAL_KEY

An audit log of drawer events for the session's cash review. It never changes the sale's state.

Rules

  • A sale is complete when the IndexedDB transaction's complete event fires, not when put() returns. Open that transaction with {durability: 'strict'} explicitly. Chromium's default has changed between versions and should not be relied on. verify on pilot hardware
  • Success screen, print and drawer request all happen after that commit and only after it.
  • If the till crashes before the commit, no record and no receipt exist. The draft cart is restored, and the cashier sees that the sale was not recorded.
  • If it crashes after the commit, the record syncs normally. The print track shows the receipt as unprinted, and the cashier reprints from the stored record.
  • On the server, receiving a record (RECEIVED) is a separate step from posting it. Posting has its own state machine (R5), so a record that needs review never keeps the till waiting.

Can retrying payment allocations duplicate financial entries?

Yes Every call to recordPayment creates a new Payment row, payment number, Receipt Voucher and GL posting (SalesInvoiceService.createSalesPaymentForInvoice → PaymentService.savePayment:240-345). No key per leg exists. splitGroupId is random on each attempt (PosCheckoutController:429) and null for single-leg sales. Matching by amount and mode is ambiguous, for example two Visa legs of 50.00. Only the VOUCHER leg is idempotent. Automatic resume of payments is therefore not safe today, and Phase 0 must not attempt it.

What Phase 0 must implement

  1. Pre-write session check. Before TX1, refuse with 409 SESSION_NOT_OPEN or SESSION_MISMATCH unless the session exists, is OPEN, belongs to the request's terminal, and belongs to the branch the server resolves for this user. This removes the most likely cause of P2 and P3. Today a checkout against a CLOSED or SUSPENDED session passes every gate: BusinessDayContinuationGate.evaluate ignores CLOSED, and PosSessionClosureWorkflowGate.isInClosureWorkflow is false for CLOSED.
  2. Checkout attempt journal (pos_checkout_attempts, migration V138). Written in its own short transaction before TX1: key (unique), request hash (canonical body without supervisor credentials), the resolved payment plan with each leg's type, amount, reference and allocationKey = key#index, session, terminal, branch, user, started_at, status IN_PROGRESS. Each step records its own completion flag in a REQUIRES_NEW transaction: INVOICE_SAVED(id, number), POSTED, LEG_n_RECORDED(paymentId), SESSION_RECORDED, SERIALS_MARKED, then COMPLETED last. Cosmetic steps (QR, stats) are logged but do not decide completeness.
  3. Key per payment leg: a nullable sales_payments.pos_allocation_key column with a partial unique index, written for every new POS leg. This does not enable automatic resume. It makes a duplicate leg impossible, both now and when a supervisor records a missing leg.
  4. Replay outcomes instead of blanket 200: see the matrix in R6. A different request hash under the same key is never answered with the earlier sale.
  5. Telling running from dead. A sweep job, modelled on PosPrintJobTimeoutSweepJob, marks IN_PROGRESS attempts older than a configurable timeout as INCOMPLETE. Until then, a replay gets CHECKOUT_IN_PROGRESS with Retry-After.
  6. Failures after money is committed. Guard markSerialsSold and recordActivity, and catch the TX4 closure-race 409. Each marks the attempt INCOMPLETE with the failed step. The till gets a structured "sale recorded, needs a supervisor check, do not ring again" answer, never a plain refusal.
  7. Investigation and manual resolution (back office, read-only first). For each incomplete attempt, show: intended plan against recorded legs, the invoice and its status history, Delivery Note and stock movements, journal entries, receipt vouchers, voucher transactions, session totals against sales_payments, and the POS audit trail. Resolution actions use only existing audited operations:
    • Record missing leg: a supervisor confirms the money was actually collected (counted cash or card slip). The system calls recordPayment for exactly that leg, and the allocation key blocks any second attempt.
    • Confirm as credit: only when the customer really owes the amount.
    • Mark serials sold.
    • Cancel sale: through the existing cancellation path (updateStatus(CANCELLED) cancels the DN and reverses the journal). Only when no payment is recorded and the goods are confirmed returned, with a reason and a second approver.
    No step deletes or reverses anything automatically.
  8. Legacy suspects report (read-only, run per tenant before rollout). POS_SALE invoices with status PAID and a balance above 0.005. POS_SALE DRAFTs holding a checkout key that are older than one hour. Invoices whose amount paid differs from their recorded payments. Pre-Phase-0 rows have no stored intended plan, so each one is triaged by hand.

On the single-transaction alternative. The previous audit is right that wrapping everything in one transaction would hold the tenant-wide invoice-number lock (findLockedByDocumentType, PESSIMISTIC_WRITE) for the whole checkout and serialize every till on the tenant. The journal approach is the right choice for Phase 0. A later option is to take the number in its own short transaction, which gives no worse gaps than deleteQuietly already causes, and then run the rest atomically. That needs its own design review.

Clocks and restarts

  • Trustworthy: server timestamps (iat, notAfter, arrival), the server-stored lease, record signatures (they show who holds the key), and per-key sequence order and gaps.
  • Not trustworthy: capturedAt, the device clock, and any order inferred from device time across restarts.
  • performance.now() only runs forward within one page lifetime. A restart resets it. After a restart the till knows only a stored floor, lastTrustedTime = max(server time at last sync + elapsed, last capturedAt). It should refuse to sell when the wall clock is below that floor (minus a small tolerance), or beyond notAfter. This catches honest mistakes and a clock that jumps forward. It cannot catch a deliberate rollback that stays above the floor.
  • Conclusion: expiry and the business-day end are honest-mode controls. The sale count and cash caps are the controls the server can actually check, so keep leases short and the caps tight.

"Records created after revokedAt can be identified by sequence"

Not sufficient A sequence number gives order within one key. It says nothing about time.

At the moment of revocation, the server knows only the highest sequence it has seen: the highest one ingested, or the last one a heartbeat reported. Call it seqAtRevocation. Records at or below it were certainly made before revocation. Records above it may have been rung legitimately before revocation by a till that was offline, or after it. They cannot be told apart, because the only timestamp they carry comes from the till's own clock. Only a server-issued token for each sale could prove timing, and that cannot exist offline.

Rule for previously issued leases after revocation

  1. Revocation sets the key to REVOKED. Every ACTIVE lease for that key becomes REVOKED in the same transaction, with seqAtRevocation recorded.
  2. Records at or below seqAtRevocation post normally.
  3. Records above it but inside the revoked lease's sequence window and caps are stored and handled per decision D6: post with a flag (routine decommission) or hold for review (suspected theft or compromise).
  4. Records outside every lease window are held. They never post automatically.
  5. On its next contact, the till learns of the revocation, deletes its lease and any offline PIN verifier, and keeps sending its outbox.
  6. Exposure is limited to the unused caps of the leases still outstanding. Allow at most one active lease per terminal, and issue the next only when the previous one has been closed (V8).

V5Inventory safety

How stock is posted today

  • The negative-stock override is global only. In DeliveryNoteService.markDelivered, allowNegative = !stockCheckRequired (:510), and the setting is read straight from salesSettingsService.getSettings() at :390, :480 and :622. SalesInvoiceService.enforceStockCheck refuses a shortfall when the setting is on (~:1928, with the comment "No product-level negative-stock override; governed globally"). No per-call parameter exists.
  • Batch products can never go negative. When product.isBatch() (isBatchControlled, :1519), the deduction goes through postAllocatedBatchDeliveryDeduction (:653-685). That requires batch allocations that exactly match the quantity, whatever the global setting. In Fast Sale, ensureDirectInvoiceBatchSelections (SalesInvoiceService:2145-2181) auto-reserves FEFO through BatchSelectionService.autoReserveFefoForSalesInvoiceLine (:183) and throws "Insufficient Batch Stock" on a shortfall.
  • FEFO eligibility uses the server's date at the moment of posting (LocalDate.now() at BatchSelectionService:703, :748, :895), not the date of the sale.
  • Non-batch goods are deducted across the warehouse's active bins in order, with any shortfall placed on the line's bin when the override applies (postBatchAwareDeliveryDeduction:591-651).
  • Serials are marked sold after the payments, outside any transaction shared with the sale (PosCheckoutController.markSerialsSold:1348).
  • Warehouse: save() fills in the branch warehouse from the branch resolved for the current user (resolveBranchForSave:2658-2672). A replay must set that branch from the lease, not from a request header.

Can auto-FEFO at sync guarantee the physically sold batch?

No FEFO at sync records the batch the server would pick at sync time. That matches the batch that left the shelf only if the cashier always picked in expiry order and no other till or document used that batch in the meantime. Neither can be known. Two further problems:

  • A batch that expired between the sale and the sync is not eligible at sync. FEFO then records a different batch, or the sale fails.
  • When two tills oversell a batch product, the second replay fails outright: no override path exists for batch products. That contradicts the previous audit's "Batch / expiry products, auto FEFO: default ALLOW … flags but does not block" and its Phase 3 scope.

  5. The tenant's SalesSettings.stockCheckRequired is never modified. A test proves that an online sale made at the same moment is still refused.

V6Sync failure and sequence recovery

Defect The previous rule "a gap stops acceptance past it" would hold back every later valid sale for as long as one record is missing, possibly forever. Defect "4xx final, 5xx retried" cannot work: a 401 (sign in again), 403 (wrong branch), 409 (closure in progress) or 423 (Business Day closed) can each become postable later, while a 500 caused by a bad payload never will.

Two stages on the server

  1. Receive. For each record: verify the signature and the keyId, insert into pos_offline_sales in its own transaction (unique offline_sale_id, unique (key_id, local_seq)), store the raw payload and its hash, and answer RECEIVED. From here on the server owns the record, and the till's job is done.
  2. Post. A worker posts each terminal's records in sequence order through the shared checkout service with the replay context. Posting results are visible to the till by polling, but the till never retries them.

The questions answered

QuestionAnswer
One sequence is rejectedIts posting failure sends it to review with a reason code. Sales do not depend on each other financially, so later records keep posting. The exceptions are a bad signature or a chain conflict, which suggest tampering: the server still receives and stores later records but stops auto-posting for that key until an admin releases it.
Can later valid records sync?Yes. Each record is signed on its own, so record n+1 verifies even when n is missing. It is posted with a GAP_BEFORE flag.
How is a lost record found?A gap in local_seq for a key, or record n+1's prevHash not matching the stored hash of n. Further evidence: heartbeat {highWaterSeq, chainHead}, and the signed lease-close summary {lastSeq, count, cashTotal, chainHead}.
Admin resolution of a missing sequenceGAP_SUSPECTED → (the till is asked; it may still be sending) → GAP_CONFIRMED when the till reports it no longer has n, or its lease-close summary skips it. The admin then either (a) recovers the record from a backup copy and ingests it normally, or (b) declares it lost. In that case an incident is opened with the paper-receipt evidence, the sale is entered through the normal back-office invoice path linked to the incident, or booked as a cash variance on the session. Nothing is ever invented. Every step is audited.
Duplicate after a partial commitPosting uses offlineSaleId as the checkout key, and the Phase 0 attempt journal records how far it got. An INCOMPLETE attempt is never posted again automatically; it goes to review with its step evidence. A resend after a lost RECEIVED answer gets DUPLICATE_SAME, which the till treats as done.

On every launch

  1. Open IndexedDB and check storage.persisted() and storage.estimate().
  2. Verify the hash chain from the last acknowledged record to the head, and check the counters against the lease.
  3. Show the pending count and any unprinted receipts. Restore the draft cart. Resolve any pending online checkout attempt (Phase 0).
  4. Online: sign in, sync the outbox, then close the old lease before a new one can be issued or the session closed.
  5. Offline: keep selling only if the lease is valid, the clock is above its stored floor, and storage readiness still holds.

Minimum conditions before offline cash is enabled

  1. Secure context. IndexedDB opens, and a write-then-read probe with durability: 'strict' succeeds.
  2. Persistent storage granted, or an equivalent verified on Electron.
  3. Free quota at or above an agreed minimum (for example 200 MB), and usage below 80%.
  4. Signing key present and enrolled. Server lease key pinned. Lease valid and its signature verified.
  5. Outbox integrity check passed, and no unresolved chain conflict.
  6. Device clock within the agreed tolerance of server time at the last sync.
  7. Catalog snapshot and tax configuration younger than the agreed age.
  8. Pilot: Electron shell, one Windows user per till, server-address change blocked while records are pending, and the backup copy active if D11 chooses one.

V8Session, Day Close and financial reconciliation

The gates as they exist in code

  • Day Close (PosSessionService.closeDay, from :2435) refuses OPEN or SUSPENDED sessions on that date (~:2452-2461), POS DRAFT invoices (~:2489-2496) and pending or failed payments (~:2498-2505). It then checks the sales identity, in which an unpaid balance counts as creditSales.
  • Session close (closeSession, :877) accepts OPEN or SUSPENDED sessions, locks the row and needs admin approval. There is no special "force close" endpoint: a supervisor or admin can close any session in scope from any device. Expected cash comes from sales_payments by collection session, so cash from offline sales not yet synced shows up as an overage at the count.
  • New The idle and hard-limit scheduler (PosSessionScheduler.suspendIdleSessions:34-63, every minute) suspends OPEN sessions when sessionIdleTimeoutMinutes (default 0, meaning off) or sessionMaxDurationHours is set. An offline till cannot report activity, so its session can be suspended while it keeps selling.
  • Closed business day: SalesInvoiceService.save refuses invoices for a business day that has been closed (:374-380). Nothing is written.
  • Period lock: database triggers on journal_entries and ledger_entries (PeriodLockTriggerInstaller) make TX2 roll back.

A pending count reported by the till is not proof. The till may be offline, may have lost its data, or may be modified. The server-side source of truth is the lease register. Each lease holds a range of sequence numbers and a cash cap, and closes only on a signed summary that matches what the server received. Heartbeat counts are a helpful early warning, nothing more.

Safe administrative resolution path

  1. One "Offline records" review queue per branch, showing the record, its signature and lease status, the posting attempt evidence, and the affected session and day.
  2. Allowed actions, each needing a supervisor role, a reason and an audit entry:
    • Retry posting, after the blocking condition is fixed.
    • Post into a reconciliation session that a supervisor opened to receive this cash, referencing the original session and its close variance (per D4).
    • Record as lost or cash variance.
    • Mark as duplicate.
  3. Nothing is deleted or reversed automatically. Every posting uses the existing audited operations.

R5Corrected architecture and state machine

Till (Electron, pilot)

  • IndexedDB stores: outbox, printJobs, drawerLog, lease, keys, meta (lastSeq, chain head, clock floor), pendingCheckout (Phase 0), drafts, catalog snapshot.
  • Non-extractable ECDSA P-256 signing key, plus the pinned server lease key.
  • An offline policy module: lease valid, clock sane, storage ready, tender and product class allowed.
  • A sync worker under a Web Lock, active only while the page is open.

Server

  • pos_terminal_offline_keys: public keys, keyId, status ACTIVE, RETIRED or REVOKED.
  • pos_offline_leases: the authority. Sequence window, caps, status ACTIVE, CLOSED, REVOKED, ABANDONED or OUTSTANDING_AT_CLOSE.
  • pos_offline_sales: raw signed records, receive state and post state.
  • pos_checkout_attempts (Phase 0): the step journal for every checkout, online or replayed.
  • PosCheckoutService, extracted, with a CheckoutContext (online, or offline replay with the stock policy and gate rules).
  • Review queues: incomplete checkouts (Phase 0) and offline records (Phase 2).
