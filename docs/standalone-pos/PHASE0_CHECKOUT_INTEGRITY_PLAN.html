Phase 0 Checkout Integrity Plan

An implementation plan for making the online POS checkout safe against partial financial commits, recoverable after a crash or lost response, and reviewable by supervisors. Shared by /sales/pos and /pos/. This is a plan only: no files, migrations, properties, databases or services were changed.

M0 correction, added 12 Nov 2026 after this document was written. A database-backed reproduction (PosCheckoutClosedSessionDefectTest, run twice on the disposable clone billbull_m0_checkout_20261112, HEAD be9be921) did not reproduce the predicted partial commit for a checkout naming a CLOSED or SUSPENDED session.

Observed:

  • HTTP 200, invoice PAID with zero balance.
  • Delivery Note, stock movement, invoice journal and receipt journal written.
  • Payment and Receipt Voucher written, with the Payment attributed to the closed or suspended session.
  • The session's totals stayed at 0.
  • The closed session's live X-Report expected cash rose after it had been closed.
  • The same-key retry returned 200 with the same, fully paid invoice.

Cause: SalesInvoiceService.createSalesPaymentForInvoice calls the one-argument PaymentService.savePayment(p) (SalesInvoiceService.java:1948), so PosDrawerSessionValidator.requireOpenDrawerSession never runs on the till path. PosSessionRepository.incrementSessionTotals updates OPEN sessions only.

What this changes: statements in this document that describe "invoice posted, then payment refused", an unpaid invoice returned on retry, or Day Close counting it as a credit sale are not correct for this scenario. They are kept and marked rather than removed. The real defect is silent acceptance and misattribution of cash to a session that is already closed or suspended.

Still open:

  • Other partial-commit paths in this document, such as a payment leg failing for a different reason after posting, were not tested by M0. They remain plausible but unverified.
  • Day Close behaviour with such a sale remains unverified: closeDay was not run.
  • M1 adds a pre-write session guard that refuses these checkouts with 409 before any write. It is not concurrency-safe; the session-row lock and attempt claim remain M2.

1Executive summary

  • Confirmed The defect described in the brief is still present at be9be921, by static trace. A checkout naming a CLOSED or SUSPENDED session passes every gate, saves the invoice, posts stock, the Delivery Note and the invoice GL, and only then fails at the first payment leg. Corrected by M0 Not reproduced: the checkout fully succeeded. See the M0 correction. The original text is kept below. Reproduce The committed database effects still need to be shown by a database-backed test. That is milestone M0.
  • Confirmed Closing a session races with a checkout in progress. Only closeSession locks the session row. beginClosure, generateXReport, suspendSession, resumeSession, transferSession and the idle scheduler all read, modify and save without a lock. No entity uses @Version.
  • Proposed The fix has five parts:
    • A session claim. A short transaction, before any invoice write, locks the session row, validates it and records an IN_PROGRESS attempt. Every session transition takes the same lock and refuses while an attempt is in progress.
    • A fenced attempt journal, with a child table for payment legs.
    • Allocation keys on sales_payments.
    • Explicit replay outcomes.
    • A supervisor resolution queue, built on the existing POS Administration correction framework.
  • Proposed Decision Strongly recommended: wrap invoice posting, all payment legs, the session totals and serial marking in one transaction. PosDeliverySettlementService (:108) already does this for delivery settlement. It removes most partial states instead of only detecting them, and it does not hold the invoice-number lock, because the invoice is saved in its own earlier transaction.
  • The session-status refusal ships with no flag that can switch it off. Terminal and branch matching starts log-only, because of session transfer and takeover.
  • Recommendation: Phase 0 can begin, starting with M0 (reproduce the defect and run the read-only legacy report), then M1 (the session guard).

3Verified critical checkout defect

Corrected by M0 M0 did not reproduce steps 5 to 7 below. The payment was recorded against the closed or suspended session, and the sale was not left half-posted. See the M0 correction. The original text is kept below.

Confirmed by static trace at be9be921. Reproduce for the committed rows (M0).

  1. PosCheckoutController.checkout (:228) loads the session (:262) and runs BusinessDayContinuationGate.assertMayContinue, which returns empty for a CLOSED session (evaluate: only OPEN or SUSPENDED are checked). It then runs PosSessionClosureWorkflowGate.assertMayOperate, where isInClosureWorkflow is false for CLOSED, and for SUSPENDED unless closure has started. No status check runs.
  2. businessDayCheckoutGate.assertCheckoutAllowed(request.getBranchId()) (:277) checks the branch window only.
  3. TX1: invoiceService.save (:343) commits the invoice, its items and a number from the counter.
  4. TX2: invoiceService.updateStatus (:414) commits stock, the auto Delivery Note, the batch consumption and the invoice journal, with the status set to PAID.
  5. TX3: invoiceService.recordPayment (:452) → PaymentService.savePayment (:272-276) → PosDrawerSessionValidator.requireOpenDrawerSession throws 400 because the status is not OPEN. No compensation runs.
  6. The client keeps checkoutAttemptRef on error (useCheckout.js:161-171; it is cleared only on success, :331), so the retry sends the same key. :240-247 returns 200 with the posted, unpaid invoice, and the till treats that as success and prints.
  7. Day Close (PosSessionService.closeDay): once the session is CLOSED, the OPEN and SUSPENDED blockers pass. The invoice is not a DRAFT, and it has no pending or failed payment. Its balance falls into creditSales, so the identity balances and the damage is invisible.

Related variants in current code

  • Confirmed A credit-only checkout on a CLOSED session records no payment, so it succeeds. recordInvoiceOnSession (:1791-1855) then increments the totals of a closed session.
  • Confirmed A CASH, CARD or ONLINE checkout on a SUSPENDED session follows the same path as CLOSED.
  • Confirmed Race: the session is OPEN at :262 but is closed before TX3. This is possible because closeSession locks the row (:888) while checkout never does.
  • Confirmed No terminal check runs at checkout. request.terminalId, sessionId and branchId are not checked against each other, and a BLOCKED, ARCHIVED or DECOMMISSIONED terminal is not refused (PosTerminalService.heartbeat, around :183-185, refuses those, but checkout does not call it).
  • Realistic triggers: a supervisor closes a session from another device while a cashier still has a cart open; the idle or hard-limit scheduler suspends it (PosSessionScheduler:34-63); or an X-Report or close lands in the same second.

Indexes

  • A partial index on (session_id) WHERE status = 'IN_PROGRESS', for session transitions and the scheduler.
  • (branch_id, status, started_at), for the queue and Day Close.

Other properties

  • Tenant isolation: each tenant has its own database, so there is no tenant column.
  • Historical rows: none are created. Invoices made before the change have no attempt and follow the legacy rule (§10). All existing payments keep a NULL key.
  • Rollback: the project has no down migrations. Reverting the code leaves the tables and the column unused, and the nullable column is harmless to old code. Never drop them on a tenant that ran with them, because they are evidence.
  • Multi-tenant rollout: the migration applies on the next boot of each tenant (the profile per client). Run it first on a testdb clone with -Dspring.flyway.locations=filesystem:src/main/resources/db/migration, to avoid the stale target/classes copy problem.

Telling a running request from a dead one

  1. Each step is bounded. Every new transactional service method carries @Transactional(timeout = stepTimeoutSeconds) (proposed default 30 s). Nothing bounds it today, because no statement timeout is configured.
  2. Lease. claimStep sets lease_expires_at = now + stepTimeout + margin (proposed 45 s) before every financial step. An expired lease therefore means the owner is dead, or that its next claimStep will be fenced. A step that started before expiry cannot still be running after it, because its own transaction timeout is shorter than the lease.
  3. Fencing. claimStep and recordStep are conditional on owner_token and IN_PROGRESS. The sweep changes owner_token when it marks an attempt, so a slow original thread cannot start another financial step.
  4. Same JVM. If owner_instance is this JVM and ActiveCheckoutRegistry still holds the attempt, it is alive: log CHECKOUT_SLOW and do not mark it. A different owner_instance together with an expired lease means a previous process crashed.
  5. Classify from evidence, not flags.
    • No invoice with the key and no payment with any of its allocation keys: ABANDONED, retry allowed.
    • A DRAFT invoice only: INCOMPLETE(INVOICE_DRAFT).
    • Posted invoice with legs missing (judged by allocation keys present on sales_payments): INCOMPLETE(PAYMENT).
    • Every leg present: COMPLETED (a lost response), but only if session_recorded_at is set. Session totals are counters with no per-invoice row, so otherwise INCOMPLETE(SESSION).
  6. Client timeouts are not server events. The attempt stays IN_PROGRESS and the replay answers CHECKOUT_IN_PROGRESS.

Reproduce Whether a transaction timeout reliably interrupts a pessimistic-lock wait on PostgreSQL with Hibernate is unproven (T19). If it does not, set jakarta.persistence.lock.timeout on the lock queries too.

11Payment-leg idempotency design

  • Key: allocationKey = checkoutKey + "#" + legIndex, where legIndex is the position in PosPaymentPlan.getAllocations(), counting legs trimmed to zero (:436), so the index is stable for a given request hash. CREDIT legs get a key in the journal but write no Payment.
  • Write path: the new SalesInvoiceService.recordPayment(id, amount, mode, ref, date, bank, cheque, splitGroupId, combinedMode, posSessionId, posAllocationKey) calls createSalesPaymentForInvoice, which sets Payment.posAllocationKey, then PaymentService.savePayment.
  • Idempotent check in savePayment, before numbering: findByPosAllocationKey(key).
    • Found with the same linked invoice and amount: return the existing Payment. No new number, receipt voucher or GL entry.
    • Found with a different invoice or amount: 409 ALLOCATION_KEY_CONFLICT.
    • Not found: proceed. The unique index catches a concurrent insert (mapped in B9).
  • Splits: splitGroupId stays random per execution (:429). For traceability the plan stores it in resolved_plan. A supervisor recording a missing leg reuses the stored splitGroupId.
  • Vouchers: unchanged. CreditVoucherService.redeem stays idempotent on the invoice number and voucher id (:301-314). The voucher's Payment leg also carries an allocation key.
  • Compatibility: back-office PaymentController (:166), receipt-voucher-first flows, PosDeliverySettlementService and all historical rows keep a NULL key, and the partial index ignores them. The JSON field is READ_ONLY, so a client cannot set it. An edit (savePayment on an existing id) keeps the original key.
  • No automatic continuation: no code path resumes the missing legs of an INCOMPLETE attempt. Only the supervisor action in §12 calls recordPayment with the stored key, after confirming the money was collected.

13Session closure and Day Close coordination

  • One lock, one rule. Checkout's begin and every session transition take pos_sessions … FOR UPDATE on the same row. Either the transition sees the IN_PROGRESS attempt and refuses, or the checkout sees the new status and refuses. Once an attempt is IN_PROGRESS, the session cannot leave OPEN, so requireOpenDrawerSession and the :1807 closure re-check pass for the rest of the checkout.
  • No deadlock by construction. The session lock is taken and released inside begin's own short transaction, which commits before TX1 takes the tenant invoice-number lock. No transaction holds both. Transitions hold only the session lock, and they read attempts without locking. Reproduce T05 and T06 under concurrency.
  • Throughput: the lock is per session, not per tenant. Two checkouts on the same session (one terminal) serialize only for the milliseconds begin takes.
  • X-Report: generateXReport and beginClosure refuse while IN_PROGRESS, and allow INCOMPLETE but list it on the report.
  • Session close: refused while IN_PROGRESS. INCOMPLETE is allowed only with an acknowledgement that records the attempt ids in the close audit (B5).
  • Z-Report and Day Close: closeDay refuses while any IN_PROGRESS or INCOMPLETE attempt exists. Override with the existing close-day admin approval plus a reason; the override reference is written onto each attempt. assertZReportPrintable is unchanged, and the Z-Report shows a "checkouts unresolved at close" section.
  • "Force close": no separate endpoint exists. A back-office close goes through closeSession and gets the same check.
  • Idle and hard-limit suspension: the conditional update (B13) skips sessions with an attempt in progress. begin also refreshes lastActivityAt.
  • Stuck IN_PROGRESS blocks transitions only until its lease expires (at most about 45 s), after which the sweep classifies it. The UI shows the attempt and a countdown.
  • A pending count reported by the client is never used. Only server attempt rows count.

Contract for external API clients (M2.2.1). An older client that omits the key is not compatible: every checkout it sends is refused, and nothing is recorded.

  • Create the key before the first request for a sale. Any unique string works; the till uses a UUID.
  • Send the same key on every retry of that sale, including after a network error, a timeout, a 5xx, a 408, or a 409 CHECKOUT_IN_PROGRESS, CHECKOUT_STALLED or CHECKOUT_ATTEMPT_SUPERSEDED. Never create a new key after an uncertain response. The server answers with the sale it already recorded.
  • A new key means a new sale. A changed request under a used key gets 409 CHECKOUT_KEY_REUSED; that key is spent.
  • Treat the key as resolved only after a 2xx, a CHECKOUT_KEY_REUSED, or another definite 4xx refusal.

Known limitation (M2.2.1). The till keeps the pending key in memory (features/checkout/checkoutKey.js). It also does not persist the cart. For a PI-Flow delivery order, the duplicate this can cause is a second draft Pro-forma Invoice with its own stock reservation. Whether a serial the first PI already marked sold would be refused on the second was not tested. Neither PI posts GL, stock movement or payment. Durable pending-checkout persistence (for example in sessionStorage) should be decided for all checkouts together. It is not specific to PI delivery.

16Performance impact

  • Added work per checkout:
    • begin: one row lock plus one insert, in its own transaction.
    • About 6 to 10 small conditional updates (a claim and a record for each step, fewer if claim and record are merged).
    • One indexed lookup per payment leg.
    Estimated at 1 to 3 ms each on a local Postgres. Not verified
  • Target: added p95 latency of 25 ms or less for a 3-line, 2-tender checkout. Hard ceiling 50 ms.
  • Measurement: on a testdb clone with a disposable 8081 backend, run 200 scripted checkouts each in record mode and with the journal code reverted, same cart and tenders, through the parity harness. Compare the pos.checkout.duration histograms. Repeat with M5 on: its effect on lock hold time is that the payment-number lock is held from the first leg until commit.
  • Contention: the new lock is per session, so there is no new tenant-wide serialization. The invoice-number lock is unchanged (TX1 only).

17Security and audit implications

  • Server-resolved identity: branch from BranchScope / BranchAccessService.getRequiredCurrentUserBranch, user from the JWT, terminal from PosTerminalRepository.findByTerminalId. Request fields are only compared against these, never trusted.
  • The status endpoint requires till permission and the same branch. It reveals only the outcome and the invoice reference. Keys are random UUIDs.
  • PII is kept to a minimum. No full request body is stored: only the hash, amounts and masked references (last 4 characters). No supervisor PIN or password ever reaches the journal, logs or IndexedDB.
  • New PosAuditAction values:
    • CHECKOUT_SESSION_REFUSED
    • CHECKOUT_REPLAY_REFUSED
    • CHECKOUT_INCOMPLETE
    • CHECKOUT_FENCED
    • SESSION_TRANSITION_BLOCKED
    • DAY_CLOSE_UNRESOLVED_OVERRIDE
    • CHECKOUT_RESOLUTION_REQUESTED/APPLIED
    Resolution writes also go to FinancialAuditService, as the correction framework already does.
  • Permissions are registered in RolePermissionInitializer, never as runtime data: pos.admin.checkout.view and pos.admin.checkout.resolve, with cancellation through correction approval.
  • Retention: attempts are financial evidence and are never purged by AuditLogRetentionJob (B11).

20Final Phase 0 acceptance checklist

  1. A checkout on a missing, CLOSED or SUSPENDED session writes no invoice, item, DN, stock movement, journal entry, payment, receipt voucher or session-total change. No flag can disable this.
  2. No session transition (close, begin-closure, X-Report, suspend, transfer, scheduler) can happen while a checkout on that session is IN_PROGRESS.
  3. Every checkout has exactly one attempt row, written before the invoice transaction, with the request hash and, after resolution, the plan and allocation keys.
  4. Replay never returns 200 for a DRAFT, partial, running or different-payload sale.
  5. Simultaneous duplicates produce one invoice and a specific outcome code, never the generic 409.
  6. No payment leg can be recorded twice. Historical and back-office payments still work.
  7. Stale attempts are classified from evidence and fenced. A live request is never marked dead.
  8. A sale whose money is committed is never shown to the cashier as an ordinary failure.
  9. Supervisors can see every INCOMPLETE attempt with its evidence and resolve it only through audited actions, with maker-checker for cancellation. Nothing is automatic.
  10. Day Close is blocked by unresolved attempts unless an audited override is given.
  11. The till persists its in-flight attempt and draft cart, recovers after a refresh by asking the server, and never mints a new key while an attempt is unresolved.
  12. Network errors are tagged. The standalone rail shows read-only connectivity. The embedded POS shows no badge.
  13. All existing unit and characterization tests pass, except reviewed updates. Parity shows no difference in success paths. p95 overhead is 25 ms or less.
  14. The legacy-suspects report has run on every tenant, and finance has triaged it.
  15. No Phase 1+ code exists: no service worker, outbox, catalog, lease, enrollment or signing.
