Architecture Decision · BillBull Retail ERP

Where a printer belongs

Barcode Print & Design is an Inventory module resolving printers through a POS terminal. This audit establishes what the codebase actually models, and decides the ownership scope for every printer role.

Branch feature/posclient Scope pos.printer · pos.device · Inventory/Barcode · print-agent Code changed none — audit only
Decision Branch-scoped printer registry with an optional terminal override — one PosPrinter table, role says what, scope says where.

This is not a new architecture. It is the architecture BillBull already implements in the entity, the service validator, the resolver and the config UI. Barcode printing fails because of four call-site defects in one function, not because Inventory is modelled wrongly.

01 Executive summary

The reported symptom — “No barcode printer is configured for this terminal.” — reads like an architectural mismatch: an Inventory screen demanding a POS terminal. It is not.

Reading the actual implementation, PosPrinter.terminal_id is nullable, PosPrinterService validates printer defaults separately for “branch” scope and “terminal” scope, the frontend resolver already ranks branch-scoped printers as a fallback when no terminal matches, and the POS device UI already labels an unassigned printer · Branch default. A label printer registered to a branch with no terminal is a first-class, fully supported configuration today.

What is broken is handlePrintZebra() in BarcodePrinter.jsx:1100. It asks for printers using a branch id that does not exist on the object it reads it from, reads the terminal id from a localStorage key nothing ever writes, and calls the print-agent helper with the wrong argument shape. Any one of those three is sufficient to produce the failure. The alert text then misattributes the cause to the terminal.

So the recommendation is deliberately unexciting: fix the four call-site defects, tighten one ranking rule in the shared resolver, and change nothing in the schema. The ERP-level printer-management layer is a real future need, but it is a Phase 3 concern gated on a second non-POS consumer appearing — not a prerequisite for printing a barcode label.

02 Current architecture, as implemented

The two-table device model

pos_devices (PosDevice.java) is the generic parent row for any piece of hardware. Type-specific configuration lives in the feature package — pos_printers, pos_scanners, pos_cash_drawers — linked back via device_id. Discovery, Health, Hardware Profiles and the Device Dashboard all address the parent row and never need to know the concrete type.

pos_devices                    pos_printers
  device_code   UNIQUE   ◄──────  device_id       (FK, backfilled by V22)
  branch_id     NULL-able         device_code     UNIQUE
  terminal_id   NULL-able         branch_id       NOT NULL
  counter_name  NULL-able         terminal_id     NULL-able  ← the scope switch
  device_type   PRINTER|…         counter_name    NULL-able
  runtime_health                  device_type     RECEIPT|KITCHEN|LABEL
  last_heartbeat                  connection_type USB|BLUETOOTH|WINDOWS_QUEUE|
                                                  NETWORK_IP|ZEBRA_BROWSER_PRINT
                                  system_printer_name
                                  ip_address / port_number
                                  is_default_printer

Note the asymmetry that answers the whole question: branch_id is NOT NULL, terminal_id is nullable. Branch is the mandatory owner. Terminal is an optional narrowing.

The scope rule is enforced server-side

PosPrinterService.java:216 makes the two-tier model explicit — it permits one default per scope, and names the scopes in the error text:

private boolean sameDefaultScope(String existingTerminalId, String requestedTerminalId) {
    return Objects.equals(blankToNull(existingTerminalId), blankToNull(requestedTerminalId));
}
…
String scope = isBlank(req.terminalId()) ? "branch" : "terminal";
throw new ResponseStatusException(CONFLICT,
        "A default " + labelFor(req.deviceType()) + " is already configured for this " + scope + ".");

A branch may hold one default LABEL_PRINTER with terminal_id = NULL and one default LABEL_PRINTER per terminal, simultaneously. requiresUniqueDefault() covers RECEIPT_PRINTER and LABEL_PRINTER — label printers were deliberately given the same default-uniqueness discipline as receipt printers.

The resolver already falls back to branch

localPrintAgent.js:453, resolvePrinterForContext(), computes two flags per candidate — exactTerminal and branchScope (= !printerTerminal) — and ranks: exact-terminal default → exact-terminal → branch-scope default → any default → name. Passing terminalId: undefined is already a legitimate call: every terminal-scoped printer simply loses its ranking boost and the branch default wins.

The config UI already exposes the choice

POSConsole.jsx:485 writes terminalId: printerForm.assignToCurrentTerminal ? currentTerminal.terminalId : null from an explicit checkbox, and line 1406 renders printer.terminalId ? "· Terminal: …" : "· Branch default". The two-tier model is already a user-facing concept with a visible label.

Transport

Routing is a clean binary, decided by connectionType: NETWORK_IP goes through the backend socket relay (PosPrinterService.printEscPos, reachable from any device); everything else goes through the local agent on 127.0.0.1:19777. sendEscPosReceiptToConfiguredPrinter() implements this fork correctly. handlePrintZebra() does not implement it at all — it calls the agent unconditionally, so a LAN Zebra could never work from the barcode screen.

03 The root problem

Barcode Print & Design is not incorrectly coupled to the POS terminal/counter model at the architecture level. It is incorrectly coupled at the call site. Four defects, all inside one function:

Root cause Branch id read from an object that has no branch id BarcodePrinter.jsx:1107, 1115

getPosPrinters({ branchId: company?.branchId }). CompanyContext stores the company profile — companyName, logoUrl, currency — and never sets branchId. So branchId is undefined, and PosPrinterService.list() opens with if (branchId == null) return List.of();. The screen receives an empty printer list every single time, in every tenant, regardless of configuration. This alone produces the reported alert.

Defect Print-agent helper called with the wrong argument shape BarcodePrinter.jsx:1186

printEscPosThroughAgent(resolvedPrinter, { dataBase64: base64Zpl }) — but the helper takes a single options object: ({ printerName, dataBase64, connectionType, ipAddress, portNumber, title }). The printer object is destructured as if it were that options bag, yielding printerName: undefined and dataBase64: undefined; the second argument is discarded. The agent answers 400 "printerName is required for workstation printers." Even with a correctly resolved printer, no ZPL is ever transmitted.

Defect Terminal id read from a key nothing writes BarcodePrinter.jsx:1112

localStorage.getItem('terminalId'). The registration flow in POSSales.jsx:2096 writes billbull:pos:terminal_id:${activeBranchId}. The plain terminalId key is never written anywhere in the codebase, so this is always null. Benign today because the resolver falls back to branch — but it is dead code that looks like terminal coupling, and it is the reason the failure was diagnosed as architectural.

Defect Network label printers unreachable from this screen BarcodePrinter.jsx:1186

No connectionType === "NETWORK_IP" branch, so a LAN Zebra is never routed to printPosPrinterEscPos(). It also bypasses PosPrintJob tracking entirely, so label prints leave no audit row while every receipt print does.

Latent Resolver can select a printer wired to a different PC localPrintAgent.js:483–490

The fourth tie-break ranks on printer.defaultPrinter alone, without re-checking terminal match. A LABEL_PRINTER scoped to Terminal 2 with defaultPrinter = true therefore outranks a branch-scoped non-default printer. For POS this rarely bites — a terminal id is always supplied and defaults are unique per scope. For Inventory, where terminalId is legitimately null, every terminal-scoped printer becomes an eligible candidate, and jobs can silently spool to a USB printer plugged into a till on the other side of the shop.

Not a defect Branch-scoped label printers entity · service · resolver · UI

Nothing in the schema, service, resolver or config screen requires a label printer to have a terminal. The capability is present and enforced end-to-end. It has simply never been exercised, because the barcode screen could not get past its own branch-id bug to reach it.

The alert text — “No barcode printer is configured for this terminal” — is itself a misstatement. The lookup is branch-scoped. The message invented the architectural problem being audited.

05 Ownership models — which one is BillBull?

Against the five candidate models: BillBull implements Model E, a mixed architecture — but not in the loose sense of “different types behave differently by accident”. It implements a specific, disciplined variant:

Branch  ──(mandatory owner, branch_id NOT NULL)──►  Printer
   │                                                  ├─ role  = device_type
   └──(optional narrowing, terminal_id NULL-able)─►    ├─ scope = branch | terminal
       Terminal                                      └─ transport = connection_type

Every printer role uses the same two-tier scope. What differs is the convention each role follows in practice, and that is a configuration habit rather than a schema constraint:

RoleNatural scopeWhySchema support
RECEIPT_PRINTERTerminalPhysically at a till; a receipt must emerge where the customer is standing.Present
KITCHEN_PRINTERBranchOne kitchen serves every till. Notably it is excluded from requiresUniqueDefault — multiple kitchen stations per branch are anticipated.Present
LABEL_PRINTERBranch, terminal as overrideLabels are produced by Inventory from wherever stock is handled; a till-bound label printer is the exception, not the rule.Present

The correct reading of the current system is therefore: BillBull is a Branch-owned printer registry that permits terminal narrowing. It is not, and has never been, Model A.

Scenario E is the only real limitation — and it is narrower than it looks

It requires all of: two or more Inventory workstations in one branch, each with its own directly-attached USB label printer, both needing to print concurrently. A LAN Zebra dissolves it (Scenario D). A single shared Zebra dissolves it (Scenario G). Registering the Inventory PCs as terminals dissolves it, at the cost of the coupling this audit exists to avoid.

The honest resolution for Scenario E, when a client actually hits it, is a per-workstation printer preference stored locally — a localStorage override naming which of the branch's label printers this PC should use, falling back to the branch default. That is a browser-local UI preference, not an ownership model: it needs no table, no server round-trip, and no new identity concept. It is Phase 2, and only on demand.

07 Is “workstation” already a first-class concept?

The audit brief correctly flags that the POS UI says “printers installed on this specific PC” and that the agent runs per-machine. Two candidates were examined.

Candidate 1 — PosTerminal.device_fingerprint

This is a genuine persistent workstation identity. POSSales.jsx:2091 mints a crypto.randomUUID() into billbull:pos:device_fingerprint and it is unique per (fingerprint, branch_id) at the DB level (V47__pos_terminal_device_branch_composite_unique.sql). A PosTerminal is, structurally, a registered workstation.

But it is unusable for Inventory as it stands. It is a browser-profile identity, not a machine identity — a different browser or profile on the same PC is a different terminal, while the print agent is genuinely per-machine, so the two disagree about what a workstation is. Registration only occurs on the POSSales mount, behind terminal approval and POS permissions. Reaching it from Inventory would mean registering warehouse PCs as POS terminals — tightening the coupling this audit exists to remove.

Candidate 2 — the print agent

It has no identity whatsoever. GET /health returns exactly { ok, service, version } (server.js:667). No hostname, no machine id, no agent id, no persisted config. os is imported solely for tmpdir() and homedir(). The agent is a stateless byte pipe that knows about Windows queue names and nothing else.

if (req.method === "GET" && req.url === "/health") {
  sendJson(res, 200, { ok: true, service: "billbull-pos-print-agent", version: VERSION });
}

Conclusion: BillBull has no usable workstation identity for non-POS contexts. Creating one means a new agent capability, a new registration flow reachable outside POS, a new table, and a migration across fourteen tenant databases — to solve Scenario E, which a LAN printer or a localStorage preference solves for free. Do not introduce a workstation entity.

09 Connection types

The right abstraction is not the physical bus but who can reach the printer. That binary is already what the code branches on:

BACKEND-REACHABLE   NETWORK_IP        → PosPrinterService.printEscPos (raw socket)
                                       works from any device: phone, tablet, any PC

AGENT-REACHABLE     USB
                     BLUETOOTH         → agent POST /print/escpos (Windows RAW spooler)
                     WINDOWS_QUEUE        only the machine physically holding the printer

DEPRECATED          ZEBRA_BROWSER_PRINT  → already throws a migration message at test time

No new connection type is needed. WINDOWS_QUEUE already covers a shared Windows queue (\\SERVER\Zebra) — the agent passes the name straight to PowerShell.

ZEBRA_BROWSER_PRINT

Deprecate it as a choice, retain it as a value. testConfiguredPrinter() already refuses it with a migration instruction, and the device-type change handler already rewrites it to WINDOWS_QUEUE. The remaining step is removing it from the connectionTypeOptions picker at POSConsole.jsx:174, so no new row can be created with it. Do not remove the enum constant — existing client rows still carry it, and Hibernate's EnumType.STRING mapping would fail to read them. It retires by attrition.

10 Role versus scope

Yes — this distinction is correct, and the encouraging finding is that BillBull already separates the two cleanly on separate columns. The vocabulary just needs stating plainly:

AxisAnswersColumnValues
RoleWhat is it for?device_typeRECEIPT_PRINTER · KITCHEN_PRINTER · LABEL_PRINTER
ScopeWho may claim it?branch_id + terminal_idbranch (terminal NULL) · terminal (terminal set)
TransportHow do bytes reach it?connection_typeagent-reachable · backend-reachable
PreferenceWhich one wins?is_default_printerone per (role, scope)

LABEL_PRINTER is a role. It carries no implication about POS. Scope is expressed entirely by the nullability of terminal_id. No schema change is required to make role and scope orthogonal — they already are. What is missing is only that the barcode screen never exercised the branch-scope half.

11 Should PosPrinter remain the model?

Yes. Option 1 — keep PosPrinter as-is. Do not rename.

The name is mildly misleading and that is a real cost. It is far outweighed by what a rename touches: the pos_printers table across fourteen tenant databases; the device_id FK from pos_devices and the V22 backfill that established it; HardwareProfileAssignmentEngine's reverse lookup findByDeviceId; PosPrinterDeviceBackfillSeeder; the /api/pos/printers contract consumed by seven frontend call sites; PosPrintJob's printer references. That is a multi-day, multi-tenant migration whose entire benefit is a better identifier.

Option 3 — keeping PosPrinter as persistence and layering an ERP abstraction over it — is the right eventual shape, and the cheap version of it costs nothing today: a thin, well-named frontend module (src/api/printerRegistry.js or similar) that both POS and Inventory call, delegating to /api/pos/printers. That gives non-POS callers a non-POS-sounding entry point without touching the database. Even that is Phase 3, not now.

15 Resolution hierarchy

Existing behaviour, with the terminal-leak fixed:

resolvePrinter({ branchId (required), terminalId?, role })

  1  branchId missing               → hard error, never guess a branch
  2  filter: isActive · status=ACTIVE · device_type = role · branch matches
  3  drop candidates scoped to a DIFFERENT terminal than the one supplied
     — and, when no terminalId is supplied, drop ALL terminal-scoped rows   ← the fix
  4  rank:
       a. terminal match  AND  is_default_printer
       b. terminal match
       c. terminal IS NULL  AND  is_default_printer      ← branch default
       d. terminal IS NULL
       e. name, ascending                                 (deterministic tie-break)
  5  none → actionable error naming the branch and the role

Step 3 is the substantive change and it is strictly narrowing — it can only remove candidates that were never physically reachable from the calling context. It cannot alter POS behaviour, where a terminal id is always supplied and per-scope default uniqueness already guarantees the winner is at rank (a) or (c).

The optional Phase-2 escape hatch inserts one step ahead of ranking: if this browser holds a local preferred-printer id for this branch and role, and that printer is still in the candidate set, take it. It never widens the set, so it cannot reach another branch's hardware.

17 Multi-branch behaviour

Option A, with a specific correction: printing requires a resolved branch, and “All Branches” must block rather than guess.

Option C — resolve from the document's branch — does not apply here. Labels are printed for products, from a cart the operator assembles; there is no document carrying a branch. Option B needs a workstation identity that does not exist.

The branch source must be BranchContext.activeBranchId, not company?.branchId. When isAllBranches is true (admins default to 'ALL' per BranchContext.jsx:263), the barcode screen must ask the operator to pick a branch before printing. Silently taking the first branch would spool a job to hardware in a different building — a failure mode with no error message and no recovery.

This matches the pattern POS already uses: registerTerminalAndResumeSession() reads activeBranchId and treats 'ALL' as a distinct case rather than resolving it to a branch.

The migration converted implicit workstation-local discovery into explicit branch-scoped configuration. That is the trade the new architecture makes, and it is the right one: it is what makes a shared LAN Zebra, a phone-initiated print, and a per-branch default possible at all. The cost is a one-time configuration step per branch — register the label printer once in POS → Devices — which is precisely the step that had never been performed, and which the branch-id bug would have made invisible even if it had.

What the old model got right and must not be lost: the operator never had to think about which printer. The branch default preserves that. Where a branch genuinely has two USB Zebras, the local preference of §06 restores it.

20 Roadmap

Phase 1 · now

Fix the call site

The five edits above. Restores label printing on the existing model. No schema, no migration, no new concept.

Phase 2 · on demand

Local printer preference

Only when a client actually presents Scenario E. A localStorage preferred-printer id per (branch, role), applied as a filter over the branch's candidates. Client-side only — no table, no endpoint, no ownership change.

Phase 3 · when justified

ERP-wide printer management

Triggered by a second non-POS print consumer — warehouse pick lists, GRN labels, shelf-edge tickets. Move the device-config component under Settings → Devices & Printers with its own permission and route, keeping /api/pos/printers and the table untouched. Introduce a neutrally-named frontend registry module. Optionally give the agent a stable agentId — for diagnostics and health attribution, not for ownership.

Phase 4 · future

Label platform

Label template versioning, ZPL preview, a designer surface, per-template printer binding. Builds on the same registry and the same resolver. Labelary is explicitly out of scope and not implemented now.

22 The twelve questions

01

Should Barcode Print & Design use terminalId?

No. Pass no terminal at all. The resolver treats its absence as “branch scope”, which is exactly right for Inventory.

02

Should LABEL_PRINTER belong to a POS terminal?

No. Its default scope is branch. Terminal remains available as an optional override for a genuinely till-bound label printer.

03

Should Inventory barcode printing use workstation context?

No. BillBull has no usable workstation identity, and creating one costs a new agent capability, a registration flow, a table and a 14-tenant migration to solve one scenario a LAN printer solves for free.

04

Should branch-level defaults be supported?

Yes — they already are, in the entity, the validator, the resolver and the UI. This is the primary scope, not a fallback.

05

Should a printer be assignable to both POS and Inventory?

Not as one row. A dual-purpose device is two rows sharing a system_printer_name — already legal, since device_code is unique and the queue name is not. Do not add multi-role.

06

Should PosPrinter be reused?

Yes, unchanged and unrenamed. The name is imperfect; the migration cost across fourteen tenant databases is not worth a better identifier.

07

Should resolvePrinterForContext() be generalized?

Its usage, yes — it is already role- and scope-aware and is not POS-specific. Its logic needs one narrowing fix (§15 step 3), not a rewrite.

08

Should POS → Devices remain the configuration centre?

Yes for now. It is the only screen able to enumerate local Windows queues through the agent. Relocating it is Phase 3.

09

Should there be an ERP-wide printer management layer?

Eventually — Phase 3, gated on a second non-POS consumer. As a relocated UI and a neutrally-named frontend module over the same API, never as a second data model.

10

What is the minimum change now?

Five edits across two frontend files (§19). Zero backend changes, zero schema changes.

11

What should BillBull evolve toward?

A branch-owned, role-typed, transport-typed printer registry with optional terminal narrowing and an optional client-side workstation preference — surfaced through an ERP-wide device screen. Which is the current model, better placed.

What should not change now?

The pos_printers schema and name. The terminal/counter model. Hardware Profiles. Receipt and kitchen flows. The print-job spine. The agent. The ZEBRA_BROWSER_PRINT enum constant. The POS Devices UI layout.

→ Architecture decision

Branch-scoped printer registry with an optional terminal override. One PosPrinter table. Role (device_type) says what a printer is for; scope (branch_id + nullable terminal_id) says who may claim it; connection type says how bytes reach it. Inventory resolves with terminalId = null and lands on the branch default. POS resolves with its registered terminal and lands on the till's printer. No new entity, no new table, no rename.

Why this fits BillBull

  • branch_id is NOT NULL and terminal_id is nullable — the schema already declares branch the owner and terminal the narrowing.
  • PosPrinterService.sameDefaultScope() already validates defaults separately for "branch" and "terminal" scope, and names both in its error text.
  • resolvePrinterForContext() already computes a branchScope flag and ranks branch-scoped printers as the fallback tier.
  • POSConsole already offers “assign to this terminal” as an explicit checkbox and renders · Branch default when it is off.
  • KITCHEN_PRINTER is deliberately excluded from per-scope default uniqueness — evidence that non-terminal printer scoping was designed in, not an afterthought.
  • The one alternative that would improve on it — workstation ownership — has no foundation to build on: the print agent's /health returns { ok, service, version } and nothing else, and PosTerminal.device_fingerprint is a browser-profile identity gated behind POS registration.

Implement now

  • Source the branch from BranchContext.activeBranchId; block on “All Branches”.
  • Drop the terminalId read; resolve with role + branch only.
  • Fix the transport call shape and add the NETWORK_IP fork.
  • Rewrite the error message to name the branch and the fix.
  • Narrow the resolver so non-matching terminal-scoped printers cannot be selected.
  • Register one branch-scoped default LABEL_PRINTER per branch — configuration, not code.

Do not implement now

  • No workstation table, entity, or agent identity.
  • No rename of PosPrinter / pos_printers / /api/pos/printers.
  • No Flyway migration and no schema change of any kind.
  • No removal of the ZEBRA_BROWSER_PRINT enum constant (picker only).
  • No new Settings → Printers screen.
  • No multi-role printers, no printer groups, no Labelary, no label-template platform.
  • No change to receipt, kitchen, Hardware Profile, or print-job behaviour.
