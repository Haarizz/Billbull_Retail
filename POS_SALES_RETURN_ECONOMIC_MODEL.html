Business rules & target economic model

Sales Return: the Correct Economic Model

BillBull Retail / ERP · branch feature/posclient · 1 October 2026 · design only, no code changed

The brief asks whether returnAmount = unpaidPortion + paidPortion is the right model for BillBull, and warns against assuming it. It is the right model — and the reason is stronger than "it is good accounting": BillBull already implements this exact pattern for customer advances, and the Sales Return module already carries the field that holds the split. Adopting it needs one new allocation table, one new term in a balance recompute, and the deletion of a derived subtraction. It needs no change to the return journal at all.

Current post-fix state — only what is implemented

Taken from the post-fix audit and re-verified against source. Four facts matter for the decisions below; the rest of the module's shape is unchanged from that baseline.

The approval chain

A return is a standalone sales_returns document. Nothing happens until APPROVED, at which point every effect runs synchronously in one transaction in SalesReturnService.updateStatus (line 386), under a pessimistic lock on the return row and a second lock on the linked invoice row.

The five-row settlement table

Every refund method posts the identical return journal. The method changes only which account faces AR afterwards. This is the module's best property, and the whole target model below is built to preserve it.

All four settlement paths already read SalesReturn.refundAmount, falling back to totalAmount. The column's own javadoc says "Cash/card/voucher value actually refunded. Equals totalAmount unless partially settled." It exists, V78 backfilled it to total_amount, and the authorization policy already thresholds cash approvals on it — but nothing ever sets it to anything other than the full total, because the frontend sends refundAmount: summary.totalRefund and applyEntryPointDefaults only fills it when null.

The field that holds the paid portion is already in the schema, already read by every settlement path, and currently always carries the full return value. That single fact is why the target model is a small change rather than a redesign.

What the fixes achieved, and what they left

  • Card and bank refunds post Dr 1100 / Cr 1013|1010, so AR control and the customer sub-ledger agree for the first time.
  • Returns appear on the Statement of Account: a RETURN_CREDIT row always, plus an offsetting RETURN_REFUND debit when settlesOutsideReceivable().
  • Customer outstanding nets return credits — on the Customer List, the customer detail card, and the statement opening balance. sumLedgerCredit* has exactly three callers.
  • sales_invoices.balance is read and row-locked on every return path, and written on none of them.

Three corrections to the post-fix audit

trading_date is not unread Correction

The audit records sales_returns.trading_date as "written and read by no Java code". It is read, in exactly one place: SalesReturnRepository.findDayReturnSnapshot matches on COALESCE(r.tradingDate, r.returnDate) and drives the POS card's Returns badge. And it is written for every POS return — useSalesReturn.buildPayload sets payload.tradingDate = posContext.tradingDate from the open session.

That is worse than being unread, not better. The POS badge counts a past-midnight return on the trading day; the X-Report, Z-Report and day close count the same return on the calendar day. Two reporting surfaces on the same screen disagree by construction. It also means the field §16 needs is already populated with the right value in live data.

Card refunds cannot "enter card settlement", because nothing does Correction

The audit frames the missing CardSettlement linkage as the gap. There is no linkage to be missing: CardSettlement is a manually-keyed batch document — settlementDate, processorName, gross / fee / net, DRAFT→POSTED — with no per-transaction reference to anything at all. Card sales do not enter it either; CardSettlementService.createSettlement saves what the operator typed.

So the real requirement is narrower and much cheaper than the audit implies: the operator building the batch needs a card-refund figure to net off the day's gross. That is the §H bucketing fix, not a new subsystem. What card refunds genuinely lack is a transaction-level record outside the GL, which §F resolves with a refund Payment row.

Customer Advance posts to 2060, not 2104 Correction

AdvanceApplicationService.apply's javadoc says "Dr Customer Advance (2104) / Cr Accounts Receivable (1110)". The constants are ACC_CUSTOMER_ADVANCE = "2060" and ACC_ACCOUNTS_RECEIVABLE = "1100". Same class of stale comment as the return journal's javadoc, which names 4101 / 2102 / 1110 / 1120 / 5101 against real constants 4001 / 2100 / 1100 / 1200 / 5001. Harmless to execution, actively misleading when designing against it — which is what this document does, so it is worth stating before the account numbers below are read.

01

The two facts that decide the model

The brief's §6 asks us to choose between modifying sales_invoices.balance (Option A), keeping it immutable and building a separate credit ledger (Option B), or centralising the current derived subtraction (Option C). Two facts about the existing code collapse that choice.

Fact 1 — invoice.balance is already a derived projection, not a stored truth

It is recomputed from allocation ledgers in two places:

SalesInvoiceService.finalizeInvoiceTotals (line 870, every invoice save) balance = invoiceTotal − amountPaid ReceiptVoucherService.syncLinkedInvoice (line 474, every receipt change) totalPaid = Σ ReceiptVoucher(status completed, salesInvoiceId = inv) + Σ AdvanceApplication(status APPLIED, invoiceNumber = inv) balance = max(0, invoiceTotal − totalPaid)

Two consequences, both decisive:

  • Option B is already false as stated. The invoice balance is not immutable and never has been. Describing the target as "keep the invoice immutable" would be describing a property the system does not have.
  • Option A as literally stated is a bug. If a return writes balance directly, the next receipt against that invoice — or any edit to the invoice — recomputes it from receipts and advances alone and silently erases the return's effect. The allocation would survive until the customer next paid something, which is precisely when it matters.

What the code actually supports is a third thing the brief's options do not name: add a term to that recompute. AdvanceApplication is already exactly this — a separate, immutable allocation ledger whose sum is folded into the invoice's balance by the one method that owns it. A return credit is the same kind of object.

Fact 2 — BillBull already has the instrument the brief's §5 is asking for

Customer Advance is a complete, working, auditable customer-credit instrument. Every property §5 demands of Customer Credit already exists for it:

§5 requirementHow Customer Advance does it
credit balanceReceiptVoucher.amount − Σ applications, exposed by findOpenAdvances
credit creationreceiveAdvance → ReceiptVoucher(purpose = ADVANCE_RECEIVED), dated to the session business day
credit consumptionapply(receiptId, invoiceNumber, amount, date)
credit allocation recordadvance_applications — one immutable row per allocation, with appliedDate
credit reversal / refundrefund(...) → status REFUNDED row + drawer DROP_OUT + GL

GL representationLiability 2060 while unapplied; Dr 2060 / Cr 1100 on application

That last row is the one that matters most. Because advance applications land in invoice.balance, the credit-limit check, AR aging, reconcileAR and every AR report are already correct about advances — with no special-case subtraction anywhere. The seven-surface divergence the post-fix audit found for return credits does not exist for advances, and the reason is structural, not diligence.

What this settles

§6 — the answer is Option B's data model reached through Option A's surface. The return document stays the source of record and is never rewritten. A new allocation ledger records which return credit was applied to which invoice and when. That ledger's sum becomes a third term in the one recompute that owns invoice.balance.

§5 — Customer Credit becomes a real instrument (option A), built as a credit applied to AR through allocation rows (option B), by copying the Customer Advance pattern. It is not removed in favour of CREDIT_VOUCHER (option D) and the derived subtraction (option C) is deleted.

§7 — one formula, and it is shorter than today's. See §D.

C

Economic model

A sales return reverses part of a sale. The sale created a receivable; cash, card or bank receipts then settled some or all of it. Reversing the sale means undoing both, in proportion to what each actually was. The brief's formula is correct, with two refinements.

Approved, with refinements returnValue = Σ line (price × qty − discount + tax) // = sales_returns.total_amount invoiceOutstanding = effectiveOutstanding(linkedInvoice) // refinement 1 unpaidPortion = min(returnValue, invoiceOutstanding) paidPortion = returnValue − unpaidPortion where effectiveOutstanding(inv) = max(0, inv.invoiceTotal − Σ ReceiptVoucher(completed, inv) − Σ AdvanceApplication(APPLIED, inv) − Σ ReturnCreditApplication(APPLIED, inv)) // refinement 2

Refinement 1 — the split is against the invoice, resolved under the existing lock

assertReturnableQuantitiesStillAvailable already takes a PESSIMISTIC_WRITE lock on the linked sales_invoices row before anything is written, precisely so a concurrent return cannot race the quantity check. The split must be computed inside that same lock, from the same locked row. No new locking is needed, and nothing about the split can be trusted from the client.

The split is also per-invoice, not per-customer. SalesReturn.linkedInvoice is a single string: there is exactly one target invoice, so there is exactly one outstanding figure to split against. Multi-invoice returns do not exist today and should not be introduced to serve this.

Refinement 2 — outstanding must already be net of earlier return credits

Without the third term, two successive returns against the same part-paid invoice both see the same unpaid portion and both claim it. On a 10,000 invoice paid 6,000, two returns of 2,000 each would both compute unpaidPortion = 2,000, reducing AR by 4,000 while only 4,000 was ever outstanding — correct by luck — and three such returns would drive it negative. The term closes it by construction rather than by a floor.

What the formula does to the brief's §3 models

Models A, B and C are not alternatives to D. They are the boundary cases of D, and which one applies is a fact about the invoice, never a choice at the till.

The brief's §3 worked example, answered

Invoice 10,000, paid 6,000, outstanding 4,000, return 2,000. unpaidPortion = min(2,000, 4,000) = 2,000, paidPortion = 0.

The intended result is Model A. The receivable falls 4,000 → 2,000 and no cash, card or bank refund is possible, because the customer has not yet paid for the goods they are returning. The refund-method dropdown has no legitimate money-moving option in this scenario, and the system should say so rather than offer five.

This is also the exact case the post-fix audit flagged as commercially wrong today: the cashier can press Cash Refund, hand over 2,000, and leave the customer still owing 4,000. Under the split model that outcome is unreachable, not merely discouraged.

§4 — return greater than outstanding

Invoice 10,000, paid 8,000, outstanding 2,000, return 5,000. unpaidPortion = 2,000, paidPortion = 3,000.

Yes — the split should occur automatically. 2,000 cancels the receivable; 3,000 is money the customer has already paid and is owed back, settled by the chosen method. The brief's four sub-questions, answered explicitly:

QuestionAnswerWhy
Can a return exceed the invoice outstanding? Yes The constraint on a return is quantity, enforced against the invoice lines. A fully paid sale has zero outstanding and must still be returnable. Value is never the gate.
Can a refund exceed the outstanding? Yes Of course — a fully paid sale refunds in full against zero outstanding. The real limit is paidPortion, not outstanding.
Can the customer balance become negative? No min() caps the AR allocation at the invoice's own outstanding, so AR cannot be pushed below zero by a return. Negative AR becomes structurally impossible rather than floored after the fact.
Can customer credit exceed the invoice outstanding? Yes Held customer credit is a liability, not negative AR. It is bounded by paidPortion and reported as its own figure, never netted into outstanding. Same treatment the statement already gives an unapplied advance.

The GL consequence: no change to the return journal

This is the result that makes the model cheap. The return journal posts Cr AR = returnValue = unpaidPortion + paidPortion. The settlement leg posts Dr AR = paidPortion. The net credit to AR is therefore exactly unpaidPortion — which is exactly the reduction the allocation makes to invoice.balance.

Cr AR (return journal) returnValue Dr AR (settlement leg) paidPortion ─────────── net Cr AR unpaidPortion ≡ Δ invoice.balance ✓

GL AR and the AR sub-ledger agree by construction, for every refund method, with no new journal shape and no per-method branching. The five-row settlement table survives untouched. The only change on the settlement side is that the amount is paidPortion instead of totalAmount — and all four paths already read it from refundAmount.

§10 — the refund method must stop being the accounting policy

Under the split, it cannot be. The method applies only to paidPortion; the unpaid portion always becomes an AR allocation and is never offered as a choice. The sequence inverts: compute the split first, then present the eligible settlement options.

ConditionRule
paidPortion = 0Cash / card / bank / voucher are disabled. The only settlement is the AR allocation. The screen states the reason: the customer has not paid for these goods.
0 < refundRequested ≤ paidPortionAllowed, no authorization beyond the existing cash-value threshold.
refundRequested > paidPortionRequires supervisor authorization, through the existing SalesReturnAuthorizationService with a new reason code REFUND_EXCEEDS_PAID_PORTION.

The brief offers "disabled", "paid portion only", "supervisor authorization" and "always allowed" as alternatives. The recommendation is the second and the third: paid portion by default, more only with sign-off. Blocking outright is the wrong default because a real commercial case exists — goodwill, a disputed delivery, a damaged consignment the branch wants to settle immediately — and a hard block pushes cashiers into cancelling and reissuing invoices, which destroys the audit trail the block was meant to protect. An authorized, reason-coded override records the decision instead of hiding it.

D

AR model — one source of truth

The authoritative formula

The brief's §7 asks for one shared definition. The right one is shorter than today's, because the return term moves out of the formula and into the data.

effectiveOutstanding(customer) = Σ opening_invoices.outstanding + Σ sales_invoices.balance // for non-cancelled, non-draft invoices heldCustomerCredit(customer) = Σ return credit issued − Σ return credit allocated − Σ return credit refunded out

Two figures, never netted into one. effectiveOutstanding can never be negative because invoice.balance is floored at zero per invoice and the allocation is capped at the invoice's own outstanding. heldCustomerCredit is a liability reported beside it — exactly how the statement already presents an unapplied advance with excludeFromBalance = true.

Why this is the cheapest correct answer

Every surface in the brief's §7 list already computes Σ invoice.balance or Σ opening.outstanding, or both:

  • CustomerService.getAllCustomers — sumOutstandingBalanceByCustomerCode + sumOutstandingByCustomerCode
  • CustomerService detail — the single-customer forms of the same two
  • CustomerCreditService.assertWithinLimit — findOutstandingBalanceByCustomerCode
  • FinancialReportService.generateARAgingReport — inv.getBalance() per invoice
  • SubLedgerReconciliationService.reconcileAR — sumGlobalOutstandingBalance()
  • StatementService — invoice statement entries + opening-balance calculation
  • AR reports and dashboards — invoice.balance

So the work is not "extend the netting to five more surfaces". It is: make invoice.balance correct, then delete sumLedgerCreditByCustomerCode, sumLedgerCreditForCustomerCode and sumLedgerCreditBeforeDate along with their three call sites. All seven surfaces become correct at once and the codebase ends up with fewer AR formulas than it started with — which is the only end state where they cannot drift apart again.

The mechanism

One new table, modelled on advance_applications

sales_return_credit_applications id bigserial sales_return_id bigint not null → sales_returns.id return_number varchar not null (denormalised, for queries and traceability) invoice_number varchar not null → the invoice whose balance this reduces customer_code varchar not null applied_amount numeric(15,2) not null applied_date date not null (the return's authoritative business date) status varchar not null APPLIED | REVERSED | REFUNDED created_at timestamp not null index (invoice_number), index (return_number), index (customer_code, status)

Immutable rows, same as advance_applications. A reversal is a new row, never an update. The status vocabulary matches the advance ledger's APPLIED | REFUNDED plus REVERSED for a cancelled return.

One new term in the recompute — in a method that does not yet exist

R17 is the obstacle. invoice.balance has two owners that do not know about each other: finalizeInvoiceTotals computes invoiceTotal − amountPaid on every invoice save, and syncLinkedInvoice computes it from receipts and advance applications on every receipt change. Adding the return term to only one of them guarantees that the other erases it — the same "two independent predicates for one fact" failure mode the audit already found in the stock path.

Extract one owner, call it from both: recomputeInvoiceBalance(invoice): totalPaid = Σ ReceiptVoucher(completed, invoice.id) + Σ AdvanceApplication(APPLIED, invoice.invoiceNumber) credited = Σ ReturnCreditApplication(APPLIED, invoice.invoiceNumber) ← new invoice.amountPaid = totalPaid invoice.returnCredited = credited ← new column, for display invoice.balance = max(0, invoice.invoiceTotal − totalPaid − credited) invoice.status = resolveInvoiceStatus(...)

returnCredited as a stored column is not required for correctness — it is derived — but an invoice screen that shows a reduced balance with no visible reason is a support ticket, and an invoice that reads total 10,000 / paid 6,000 / credited 2,000 / balance 2,000 explains itself.

Where the allocation is written

Inside the approval transaction, between the return journal and the settlement legs, under the invoice lock already held by assertReturnableQuantitiesStillAvailable: 

├─ assertReturnableQuantitiesStillAvailable()   already locks sales_invoices
├─ resolveSettlementSplit(saved)                 NEW — computes unpaid/paid, overrides refundAmount
├─ applyBatchReturns / applyNonBatchStockReturns
├─ postJournalForApprovedReturn                  unchanged — Cr AR for the full returnValue
├─ applyReturnCreditToInvoice(saved)             NEW — allocation row + recomputeInvoiceBalance

resolveSettlementSplit must override refundAmount, not default it. The client currently sends the full total and applyEntryPointDefaults only fills nulls (R15), so a server that merely defaults would keep trusting the browser for the amount of cash that leaves the drawer.

02

Customer Credit as a real instrument

With the split model in place, Customer Credit splits into two different things that today share one name:

  • The AR allocation — the unpaidPortion. Not a credit balance at all: it is the cancellation of a debt, consumed at the instant it is created, recorded in sales_return_credit_applications. This happens on every return with an unpaid portion, whatever refund method was chosen. It is not a method.
  • Held customer credit — a paidPortion the customer chooses to leave on account rather than take back as money. This is the real instrument, and it is what the CUSTOMER_CREDIT refund method should mean from here on.

Definition of held customer credit

Because they are not substitutes, and the difference is structural rather than cosmetic:

What must be deleted is the derived Customer Credit — the subtraction over refund_method that currently reduces an outstanding balance with no record of what was reduced.

CUSTOMER_CREDIT stops being the one method with no settlement leg. It gets the same shape as the other four, facing a liability account instead of cash. G

Inventory / COGS model

The cost source — settled

resolveActualCogs already walks the right priority order, and that order is the answer to the brief's §14 question:

  1. DeliveryNoteBatchConsumption — the exact batch / WAC cost consumed at the original sale. Authoritative where it exists.
  2. SalesInvoiceItem.cost — the cost-at-sale snapshot stamped at POS checkout. Survives a later change to the product master.
  3. ProductPricing.cost — current master cost, for legacy rows predating both snapshots.

"Current product cost" is correctly last, and a restockable return whose cost resolves to nothing is already rejected at approval with the offending item codes named. No change needed.

The inbound movement must carry that unit cost

reverseOutboundStock never sets unitCost, so sumGlobalInventoryValue() ignores the inbound row while the GL debits 1200 by the resolved COGS. reconcileInventory drifts by that amount on every restocked return, against a 1.00 AED tolerance.

Decision: stamp it

The trade-off that justified the null was WAC protection — a null-cost inbound row cannot move the weighted average. That argument no longer holds, for two reasons.

First, the cost now being resolved is the cost the units left at, from the DN consumption snapshot. Re-entering units at the cost they departed at restores the pre-sale weighted average exactly; it does not distort it. Distortion was only ever a risk under the old "current master cost" behaviour, which is now the third fallback rather than the default.

Second, and decisively: the GL has already debited 1200 by that number. Refusing to stamp it does not avoid a wrong valuation — it guarantees two different valuations, one of which is the audited artefact. Consistency with the posted GL beats WAC purity.

So: unitCost = resolvedLineCogs / returnQty, stamped on every inbound return movement, from the same figure the journal uses. One number, two ledgers.

One predicate for "did stock come back"

R4 is the prerequisite and is independent of any business decision. Two predicates currently decide the same fact: resolveReturnWarehouseId returning non-null (so a movement is posted) and itemStatus == "Good" (so 1200 is debited). They can disagree, and when they do the GL records inventory that never arrived.

The fix is to make the journal consume the result of the stock step rather than re-deriving it: applyBatchReturns and applyNonBatchStockReturns return the set of lines and costs actually posted, and postJournalForApprovedReturn debits 1200 by that and nothing else. A line that could not resolve a warehouse then fails the approval with a stated reason instead of silently diverging.

Damaged / scrap returns — the brief's §15

Today DAMAGED, OPENED, DEFECTIVE and EXPIRED post no stock movement and no inventory journal, so the cost stays in COGS as an immediate loss. Batch allocations and serials are still flipped to RETURNED for traceability. The goods are physically in the store and in no system.

The accounting-correct treatment is two steps, not one:

Step 1 — receipt into quarantine (at approval, same as a GOOD return) stock_movements +qty into the branch QUARANTINE warehouse, unit_cost = resolved COGS Dr 1200 Inventory / Cr 5001 COGS Step 2 — disposition (a separate, dated, authorized action) scrap → Dr 7xxx Stock Loss / Cr 1200, −qty out of quarantine supplier claim → Dr 1150 Supplier Claims Receivable / Cr 1200 repair & resell → transfer quarantine → sellable, no GL effect

That makes the loss explicit, dated and attributable instead of implicit in a COGS figure, and it makes "where is the damaged stock" an answerable question. It also separates the two facts that are currently fused: the customer's return was accepted, and the business decided to eat the cost.

Not implementable yet — two business facts are missing

Does the branch physically retain damaged returns, or discard them at the counter? And are supplier claims pursued for defective goods? If goods are discarded at the counter, quarantine is fiction and today's immediate write-off is the honest model — in which case the only change needed is to post an explicit Dr Stock Loss / Cr 1200 rather than leaving the cost silently in COGS. Both answers are defensible; they are not a code decision. See §J.

inventory_balances staleness

InventoryBalanceService.refresh is REQUIRES_NEW and is called from inside the approval transaction, so it recomputes from a ledger that does not yet contain the movement just inserted, and the exception handler swallows the failure. Move it to an after-commit hook. Independent of every decision here.

Business date, branch, linkage, idempotency

§16 — one business date

businessDate(return) = COALESCE(sales_returns.trading_date, sales_returns.return_date) stamped server-side at creation, from: POS entry → the validated open session's tradingDate back-office entry → the branch's current Business Day via BusinessDayWindowService never accepted at face value from the client

trading_date becomes the authoritative field rather than being removed. Three reasons, all from the current code: the column exists and is populated for every POS return; findDayReturnSnapshot already reads it with exactly this COALESCE; and BusinessDayWindowService.resolveCurrent(branchId).window() .tradingDate() is already the system-wide answer to "which Business Day is it", used by POS checkout, session management and day close.

That one date then governs every leg — the document, the return journal, the inventory journal, the settlement journal, the stock movement's movementDate, the drawer movement, the statement row, the credit-voucher issue date, the allocation row's appliedDate, and X / Z / day-close inclusion. Three call sites currently substitute LocalDate.now() and must take the stamped value instead: reverseOutboundStock (line 455), CreditVoucherService.issueForSalesReturn (line 121), and the date != null ? date : LocalDate.now() fallback in createJournalFromCreditVoucherIssue.

Fix R16 in the same change, or the overnight case stays wrong

The client sends returnDate: new Date().toISOString().slice(0,10) — a UTC date. In a UTC+4 branch every return taken between midnight and 04:00 local is already dated to the previous calendar day before any trading-day logic runs. Since the server will now stamp the business date itself, the cleanest fix is to stop accepting returnDate from the client at all for POS entry, exactly as Payment.posSessionId is already declared READ_ONLY for the same reason.

§19 — branch attribution

Cross-branch returns should not be permitted, and the gap that allows them for a global ADMIN should be closed.

The reason is that the alternative cannot be done honestly with the current chart of accounts. A return processed at branch B against a sale by branch A owes branch A a revenue reversal and branch B an inventory receipt, which requires inter-branch due-to / due-from accounts. None exist. Without them, every cross-branch return silently misstates two branches' P&L — which is what happens today, where branch B's P&L carries the reversal and branch A's stock rises.

SalesReturnEligibilityService:175 already asserts branch access on the invoice and already blocks this for a BRANCH_ADMIN. Extending the same assertion to a global ADMIN closes it. With that in place every leg is owned by one branch — the selling branch — and the question disappears rather than being answered.

If the business genuinely needs cross-branch returns, that is a chart-of-accounts project with inter-branch accounts and a defined transfer price, not a flag on the return screen. §J.

§20 — unlinked returns

Every return must link to an original invoice. POST without linkedInvoice should be rejected.

This is less a policy choice than an observation about what the module already is. Without a linked invoice the system has no quantity ceiling (the guard logs a warning and returns), no price or tax source (both are prorated from the invoice line), no cost source (the DN consumption snapshot is reached through the invoice), no warehouse (resolved from the invoice's DN), and now no outstanding to split against. An unlinked return is a free-text credit note with a stock movement attached.

If a genuine business need exists for crediting a customer without an invoice — goodwill, a disputed delivery, a pre-system sale — that is a manual credit note, a different document with its own authorization, no stock effect, and an explicit revenue account. It should not be a Sales Return with empty fields.

J

Open business decisions

Only questions the code cannot answer. Everything else in this document is determined by what BillBull already does. Each has a recommendation; none should be implemented on it alone.

1 · May a refund exceed the paid portion with supervisor authorization, or never?

Recommendation: allow it, reason-coded and authorized. A hard block pushes staff into cancelling and reissuing invoices to get the outcome they need, which destroys the audit trail the block existed to protect. An authorized override with REFUND_EXCEEDS_PAID_PORTION records the judgement instead of hiding it. The authorization machinery already exists.

This is the only decision that changes the §04 table. If the answer is "never", three of its rows become hard errors rather than blocked options, and the branch loses the ability to settle a dispute at the counter.

2 · Does held customer credit expire?

Recommendation: no. A customer advance does not expire; a bearer voucher does, because an unredeemed bearer instrument is an indefinite liability against an unknown holder. Credit on a named trade account is closer to an advance, and expiring it is effectively confiscating money the customer has already paid. If local practice or audit requires a write-off window, it must be a dated, posted Dr 2062 / Cr other income with customer notification — not a status flip.

3 · Does held customer credit increase the customer's available credit limit?

Recommendation: yes — available = limit − effectiveOutstanding + heldCustomerCredit. A customer holding 3,000 of credit the business owes them is 3,000 less of an exposure. The audit's edge case (a customer at their limit who returns goods and is still refused) is fixed by the allocation for the unpaid portion; this decision only concerns the held residue. Conservative credit policy might say no. It is a credit-risk call.

4 · Are damaged returns physically retained, and are supplier claims pursued?

This is two facts about branch operations, and §G cannot be built without them. If goods are retained, quarantine plus a dated disposition is right. If they are binned at the counter, today's immediate loss is right and the only change needed is to post it explicitly as Dr Stock Loss / Cr 1200 rather than leaving the cost buried in COGS. If supplier claims are pursued, a receivable and a claim document are needed, which is a separate project.

Recommendation: ask the branches before designing anything. The four conditions may not even behave alike — an expired FMCG line and a defective appliance are unlikely to follow the same route.

5 · Is pos_day_close.net_sales restated for closed days, or only corrected going forward?

Recommendation: forward only. Write the corrected figures to new columns, leave the existing column as written, bump reportVersion from "1.0" — the field exists for exactly this — and state the effective date on the report. Restating a signed Z-Report is a different kind of act from fixing a formula, and the two should not be bundled.

6 · Are cross-branch returns permitted at all?

Recommendation: no, and close the ADMIN gap. If the business says yes, it is a chart-of-accounts project — inter-branch due-to / due-from accounts and a defined transfer price — not a permission change. Quantify the existing population first (§05); if it is zero, the guard costs nothing.

7 · Does account 2062 get created, and under whose sign-off?

One new liability account, 2062 — Customer Credit Notes Unapplied, between 2060 (advances) and 2061 (vouchers). Needs the finance owner's approval and a SystemAccountSeeder entry so every tenant gets it. Mechanically trivial; listed here because adding a GL account to fourteen client databases is not a developer's unilateral decision.

8 · Should an exchange / replacement document exist?

X and Z have buckets for it that can only ever read zero, because the UI never emits Replacement. Recommendation: remove the dead buckets now and treat exchange as a separate question. An exchange is economically a return plus a new sale, and modelling it as one document is a real design exercise, not a field.

9 · Is a manual credit note needed, now that unlinked returns are rejected?

§20 rejects returns with no linked invoice. If staff currently use that path for goodwill credits or pre-system disputes, closing it leaves them nowhere to go. Recommendation: quantify how many unlinked returns exist before enforcing the rule; if the count is material, the manual credit note needs to ship alongside the guard rather than after it.

Implementation sequence

Ordered so nothing is rewritten by a later step, and so the work that needs no sign-off is not blocked by the decisions that do.

Phase 0 — no decision needed, no behaviour change

  1. Reject status: APPROVED on POST /api/sales/returns (R7). Two lines; removes a phantom-return vector.
  2. Audit every approval, not only supervisor-gated ones (R11). PosAuditService.logReturnInitiated and RETURN_APPROVED already exist with no callers.
  3. Fix the stale javadoc on createJournalFromSalesReturn and AdvanceApplicationService.apply, and the stale comment at PosSessionService:2704. All three currently mis-state the system to the next reader — including to anyone implementing this document.
  4. Run every quantification query in §05 and record the results. This scopes everything below and changes nothing.

Phase 1 — mechanical, independently valuable, no model dependency

  1. Bucket X/Z returns on refund_method and publish the real cash-refund figure (R10). Stops reporting Customer Credit as money paid out.
  2. Make the stock-posted test and the journal's restock test one predicate (R4), so 1200 cannot be debited for goods that never moved.
  3. Move InventoryBalanceService.refresh to after-commit (R12).
  4. Stamp unitCost on inbound return movements (R5), now that cost resolution is reliable.
  5. Stop accepting returnDate from the client; stamp the business date server-side as COALESCE(tradingDate, businessDay) and thread it through all legs (R8, R16).
  6. Close the cross-branch gap for global ADMIN (R6), subject to decision 6.

Every item in Phase 1 is a defect fix that the target model assumes. None of them changes an accounting outcome that anyone has to approve, and all of them are testable in isolation.

Phase 2 — the split, after the §C model is approved

  1. Extract recomputeInvoiceBalance(invoice) and call it from both current owners (R17). Behaviour-neutral; it must land before any new term is added.
  2. Create sales_return_credit_applications and account 2062 (decision 7). New Flyway migration above the highest applied number.
  3. Compute the split at approval under the existing invoice lock, and override refundAmount with paidPortion (R15). Every settlement path then pays the right amount with no further change.
  4. Write the allocation row and call recomputeInvoiceBalance.
  5. Give CUSTOMER_CREDIT its settlement leg, Dr 1100 / Cr 2062, and a held-credit ledger entry.
  6. Return the split in the eligibility response so the screen can constrain the method list before the cashier chooses, with reasons.
  7. Delete sumLedgerCreditByCustomerCode, sumLedgerCreditForCustomerCode, sumLedgerCreditBeforeDate and their three call sites. This is the step that makes all seven AR surfaces agree, and it removes code rather than adding it.
  8. Change RETURN_REFUND's predicate to paidPortion > 0; add CREDIT_HELD and CREDIT_APPLICATION statement rows.
  9. Write the invariant checks from §I as tests. Invariants 1, 2 and 4 are unit-testable against the split; 3, 5 and 7 belong in the reconciliation report.

  1. Held-credit allocation: manual, and FIFO auto-apply mirroring applyAgainstOutstandingInvoices.
  2. Held-credit refund to cash, reversal, and the open-credit-pool report.
  3. Refund Payment rows for cash, card and bank (§F), which also makes the dormant totalRefunds metric meaningful.
  4. POS Net Sales net of returns on a VAT-inclusive base, forward-dated (decision 5). Fix the back-office gross-profit basis mix in the same change.
  5. Reject unlinked returns (§20), with a manual credit note if decision 9 requires one.
  6. Scrap routing (decision 4). Remove the dead exchange buckets (decision 8).
  7. Historical remediation, last, with accounting sign-off on posting dates.
The one thing to protect

Every item above fits inside the five-row settlement table: one return journal, one settlement leg per method, the method choosing only which account faces AR. Nothing here proposes a different return journal per refund method, and nothing should. If a proposal ever requires one, it is solving the problem in the wrong place.

The second thing to protect is the direction of the dependency. The split is computed from the invoice and persisted on the return; the settlement reads the persisted figure. Never the reverse. A settlement that recomputes its own amount is a settlement that can disagree with the allocation, which is the defect this whole model exists to remove.
