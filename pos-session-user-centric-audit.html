POS Session Architecture Audit — Terminal-Centric (As-Built), Pre-Migration to User-Centric Session Roaming

Purpose of this document: a complete, code-grounded audit of the *existing* Terminal-Centric session model, produced before any redesign work toward a User-Centric ("session roaming" — a cashier's session follows them across terminals) model. No code was changed. Where something wasn't directly verified this pass, it is flagged rather than assumed.

Primary sources (this pass, line-verified): pos/session/{PosSession,PosSessionService,PosSessionScheduler,PosSessionRepository,PosCashMovement*}.java, pos/terminal/{PosTerminal,PosTerminalRepository,PosTerminalService,PosTerminalController}.java, pos/counter/{PosCounter,PosCounterService,PosCounterController}.java, config/JwtFilter.java, auth/AuthController.java region, plus the full prior architecture pass (entities, migrations, frontend) carried forward and re-verified against current source.

1. Session Lifecycle

1.1 Creation — PosSessionService.openSession(terminalId, counterName, openingCash) (pos/session/PosSessionService.java:196-279)

Ownership is established entirely by who the current authenticated user is at the moment of the call (currentUser()), scoped to (branchId, terminalId) — there is no user-level session registry independent of a terminal. Sequence:

  1. Resolve Branch via branchAccessService.getRequiredCurrentUserBranch() — this is JWT-branch-context-derived, not terminal-derived (see §4).
  2. Resolve businessDate for that branch (PosBusinessDateService).
  3. Guard — day already closed: 403 if businessDateService.isDateClosed(branchId, businessDate).
  4. Guard — stale prior-day session: repo.findUnclosedSessionsBeforeDate(branchId, businessDate) — if any unclosed session exists from before today's business date for this branch (not scoped to this terminal), throws 409 PREVIOUS_DAY_SESSION_OPEN: Session #{id} ... terminal {terminalId} ... Close the previous day's session before starting a new one. This is branch-wide, so a stale session on Terminal A blocks opening a *new* session on Terminal B for the same branch/day only insofar as the frontend's day-status flow surfaces it — the service call itself does not filter by terminal, meaning any unclosed prior-day session anywhere in the branch blocks all new session opens branch-wide. Worth flagging for a user-centric design where a user might want to open elsewhere while an old session is stuck.
  5. Resolve the PosTerminal entity by terminalId string (terminalRepository.findByTerminalId) — used purely to get the lock target and denormalize terminalPk/counterId, not for any identity/auth check at this point.
  6. App-level duplicate check: repo.findByBranchIdAndTerminalIdAndStatus(branchId, terminalId, OPEN). If found:
    • If currentUser().equals(existing.getOpenedBy()) → hand the existing session back (idempotent "resume" — see §1.2).
    • Else → 409 "Terminal is already in use by active cashier: {openedBy}".
      1. Build a new PosSession: branchId/Name, terminalId (string), counterName (as passed by the client, not re-derived from the terminal record), openedBy = currentUser(), openedByDisplayName resolved via resolveDisplayName, sessionDate = business date, openedAt/lastActivityAt = now, status=OPEN, openingCash, all totals zeroed. If the terminal entity was found: terminalPk and counterId (from terminal.getCounterId()) are stamped — **counterId here is a snapshot from the terminal's *current* counter assignment at open time, never re-synced later**.
      2. Idle/hard-timeout snapshot: PosSettings.sessionIdleTimeoutMinutes/sessionMaxDurationHours are copied onto the session row (idleTimeoutMinutes, sessionTimeoutAt = now + maxHours) — per-session values frozen at open time; a later settings change does not retroactively affect already-open sessions.
      3. repo.save(session) — INSERT.
      4. Terminal lock acquisition: if the terminal entity was resolved, terminalRepository.setOpenSession(terminal.getId(), saved.getId()) — a native atomic UPDATE pos_terminals SET current_open_session_id = :sessionId WHERE id = :terminalId AND current_open_session_id IS NULL. If 0 rows affected (another session already holds the lock, lost the race), the just-inserted PosSession row is deleted and 409 "Terminal is already occupied by another session." is thrown. If the terminal entity was *not* found (i.e., terminalId didn't resolve to a registered PosTerminal), no lock is taken at all — the session is created lock-free. This is a notable gap: a session can exist with no corresponding terminal-lock discipline if the terminal record is missing/mismatched.
      5. Audit log (PosAuditService.logSessionOpened) and terminal activity touch (PosTerminalActivityService.recordActivity(terminalId, "SESSION_OPEN")).

1.2 Resume

There is no separate "resume" endpoint for a session still OPEN — step 6 above *is* the resume path: calling openSession again with the same terminal+user returns the existing OPEN session unchanged (idempotent). For a SUSPENDED session, resume is explicit: resumeSession(id) (line ~477) — only valid from SUSPENDED, sets status back to OPEN and touches lastActivityAt. No ownership re-check is performed in resumeSession itself (no comparison of currentUser() to openedBy was found in this method) — resume is closer to "un-suspend this session row" than "resume as the recorded owner."

Terminal-level resume-on-mount (frontend) is GET /api/pos/sessions/active?terminalId= → getActiveSession(terminalId) (line 300-327): looks up the OPEN session for branch+terminalId; if found and currentUser().equals(openedBy), returns it; if found under a different user, throws 409 "Terminal is locked by active cashier: {openedBy}" (this is the message the frontend's Supervisor Takeover flow reacts to); if not found at all, checks whether the terminalId is registered to a *different* branch and throws a distinct 409 if so (stale cross-branch cached id).

1.3 Closing

closeSession(...) — see the prior architecture pass (§5/§6) for the full breakdown; key points reconfirmed relevant to migration risk: closing releases the terminal lock via a matching atomic clearOpenSession(terminalId, sessionId) conditioned on the session id still matching — i.e., the lock-release is tied to the session row, not the user, so if ownership were ever reassigned mid-session (reassignSessionOwner, §1.5) the lock-release logic still works because it keys off session id, not openedBy.

1.4 Expiry — PosSessionScheduler (pos/session/PosSessionScheduler.java, @Scheduled(fixedRate=60_000))

Critical distinction for the migration: idle/hard-timeout expiry does not close a session — it suspends it (status = SUSPENDED). The terminal lock is not released on this auto-suspend (no call to clearOpenSession in PosSessionScheduler) — a suspended session still holds pos_terminals.current_open_session_id, meaning the terminal remains "occupied" and blocks any *new* session open on that terminal until the suspended session is either resumed or explicitly closed. Two independent triggers:

  • Hard wall-clock limit: repo.findTimedOutSessions(now) — sessions where sessionTimeoutAt < now (set once at open time from PosSettings.sessionMaxDurationHours, never recalculated).
  • Idle timeout: two-phase query — repo.findIdleSessionsBefore(now.minusMinutes(1)) (a conservative 1-minute floor query, since idle windows vary per-session) followed by an in-memory per-session check against that session's own frozen idleTimeoutMinutes, comparing lastActivityAt (or openedAt if never touched) against now.minusMinutes(idleTimeoutMinutes).

lastActivityAt is kept fresh by: the frontend's useIdleTimeout hook pinging touchSessionActivity(sessionId) every 30s, and server-side by recordInvoiceOnSession (every checkout) and PosTerminalActivityService.recordActivity calls from various flows.

1.5 Ownership reassignment (adjacent to lifecycle, directly relevant to User-Centric migration)

Two distinct mechanisms already exist for changing *who* owns an open session, without changing *which terminal* it's tied to:

  • reassignSessionOwner(terminalId, newOwnerUsername) (line 286-298) — silent no-op if no OPEN session exists; otherwise overwrites openedBy/openedByDisplayName directly, no PIN/approval check inside this method itself (calling-context authorization, if any, lives upstream — not traced in this pass).
  • supervisorTakeover(sessionId, supervisorPin) — BCrypt-verifies against PosSettings.supervisorPin if set, then reassigns openedBy to the current user and forces status back to OPEN.

Both mechanisms prove the system already *can* decouple "session owner" from "who opened it," but always within the same terminal — there is no existing mechanism to move an open session's terminalId/terminalPk to a different physical terminal. That capability does not exist anywhere in the codebase today.

2. Terminal Lifecycle

2.1 Registration

PosTerminalController.register (ungated, self-service) → PosTerminalService.registerOrRefresh — resolves by terminalId claim, falling back to (deviceFingerprint, branchId) composite unique lookup. Enforces PosSettings.maxTerminalsPerBranch (excludes ARCHIVED/DECOMMISSIONED from the count) for *new* terminals only. If PosSettings.requireTerminalApproval, starts PENDING_REGISTRATION.

2.2 Activation

approve/reject only from PENDING_REGISTRATION. Heartbeat (heartbeat(terminalId, ip), 403 unless not ARCHIVED/DECOMMISSIONED/BLOCKED) auto-promotes OFFLINE → ACTIVE/IDLE.

2.3 Ownership — currentOpenSessionId

This is the crux of the terminal-centric model. PosTerminal.currentOpenSessionId is a single nullable Long column, the sole mechanism representing "which session currently has this terminal locked." It is:

  • Set only via the native atomic UPDATE setOpenSession (compare-and-swap on IS NULL), never via a normal JPA setter+save path in the observed session-open flow.
  • Cleared only via the matching atomic clearOpenSession (compare-and-swap on = :sessionId), called from closeSession. Not called from suspendSession or the scheduler's auto-suspend — meaning a SUSPENDED session still holds the terminal.
  • Read implicitly by archive/decommission guards (409 if currentOpenSessionId != null) — terminal lifecycle actions are gated on this column, not on querying PosSession directly.
  • There is no reverse consistency check found in this pass ensuring PosTerminal.currentOpenSessionId and PosSession.terminalPk/status always agree — they're kept in sync procedurally (both written inside the same openSession/closeSession transaction) rather than enforced by a DB constraint (e.g., no FK from pos_terminals.current_open_session_id to pos_sessions.id was confirmed — not explicitly checked this pass, flagged as unread).

This column is the single biggest architectural obstacle to User-Centric session roaming: the entire "is this terminal available" question is answered by one nullable FK-like column on the terminal row, not by any query over sessions filtered by user. Moving to a model where a session isn't pinned to one terminal would require either repurposing this column's semantics or removing the terminal as the lock owner entirely.

2.4 Validation

Register: rejects (403) if terminal status is BLOCKED/MAINTENANCE/DECOMMISSIONED/ARCHIVED. Heartbeat: rejects if ARCHIVED/DECOMMISSIONED/BLOCKED (MAINTENANCE excluded deliberately). Archive/decommission: rejects (409) if currentOpenSessionId != null.

2.5 Locking

Exactly the CAS mechanism in §2.3 — no other locking primitive (@Version, synchronized, pessimistic lock) is used anywhere in the terminal or session write paths for this purpose.

2.6 Authentication

None, at the terminal level. There is no terminal credential, terminal-scoped token, or terminal-specific claim in the JWT — confirmed by reading config/JwtFilter.java in full for this pass: the filter resolves BranchContextHolder/OwnershipContextHolder from the JWT's user/branch claims and an optional X-Branch-Id header (used only to let a multi-branch user pick their active branch, validated against their allowed-branch set — resolveActiveBranchId, lines 144-162). No terminal identifier appears anywhere in JwtFilter. Terminal identity is established purely by the request body's deviceFingerprint/terminalId at registration time and trusted thereafter — any authenticated user's browser can register as, or heartbeat, any terminal it has the string id for, with no cryptographic binding between a JWT and a terminal. This is a second major consideration for a user-centric redesign, since "terminal" today carries zero authentication weight of its own.

3. Counter Lifecycle

3.1 Assignment

Counters are assigned *to* terminals, never to sessions or users directly. PosTerminalService.assignCounter(terminalId, counterId) sets PosTerminal.counterId (404 if counter not found). There is no "assign counter to session" or "assign counter to user" operation anywhere in the codebase.

3.2 Validation

PosCounterService: unique (branchId, counterCode) on create (409 on duplicate); status change to INACTIVE/MAINTENANCE blocked (409) while any terminal is still assigned with an active status; delete blocked (409) while any terminal references the counter at all. No RBAC/permission gating exists on PosCounterController at all (confirmed again this pass) — isAuthenticated() is the only check, unlike the terminal controller's per-action ModulePermissionService gating.

3.3 Relationship with Terminal

Many-to-one: PosTerminal.counterId → PosCounter.id, nullable (a terminal can be unassigned). A counter can have many terminals pointed at it simultaneously — nothing prevents two terminals from both claiming the same counter concurrently; counter assignment carries no exclusivity lock analogous to the session lock.

3.4 Relationship with Session

Indirect and denormalized only. PosSession.counterId/counterName are copied from the *terminal's* counter assignment at the moment openSession runs (terminal.getCounterId()) and from the client-supplied counterName string parameter — there is no live FK from PosSession to PosCounter, and no re-sync if the terminal's counter assignment changes after the session opens. A session's "counter" is a point-in-time snapshot, not a relationship.

4. User Authentication

4.1 Login flow

Single, generic endpoint — no POS-specific login exists. Authenticates username/email+password (rate-limited via LoginRateLimiter/brute-force guard), issues one JWT (JwtUtil.generateToken) carrying the user's identity, primary branch, and role claims. This was confirmed in the prior pass and re-confirmed here by reading JwtFilter end-to-end: it never references anything POS-specific (terminal, counter, session).

4.2 "POS login"

Does not exist as a distinct concept — entering /sales/pos re-uses the ambient app JWT and instead triggers terminal registration (§2.1) as its bootstrap step. The user is already fully authenticated before any POS-specific state exists.

4.3 Cashier identification

Entirely by currentUser() (the JWT-derived username) at the moment of each POS API call — there is no separate "cashier badge" or PIN-based POS identity layer for the *primary* login. A PIN *does* exist, but only for the narrower supervisor takeover flow (PosSettings.supervisorPin, BCrypt-verified) — not for normal cashier identification.

4.4 Session ownership

As established in §1: ownership = PosSession.openedBy, a raw username string set from currentUser() at open time, mutable only via reassignSessionOwner/supervisorTakeover. It is not a JPA FK to User — it is a denormalized string, joined against User.username only when resolving display names (resolveDisplayName). This has a direct migration implication: any User-Centric model that wants strong referential integrity between session and user will need to introduce (or verify the presence of) a real FK, since today a rename of username (if that's ever mutable — not confirmed) would orphan the string reference.

4.5 Security validation

Branch scoping is the dominant security control for POS session operations — BranchAccessService.getRequiredCurrentUserBranch() is called at the top of every session-affecting service method, meaning all session validation is implicitly scoped to "the branch the caller's JWT/header context currently resolves to," not to any terminal- or session-specific credential. Terminal actions carry additional ModulePermissionService permission-key checks (§2 of the prior document); counter actions carry none; session actions carry only isAuthenticated() at the controller layer plus the ownership checks embedded in service logic (§1.2's openedBy comparison, §1.1's active-cashier conflict).

5. Startup Flow (Login → Usable POS Sales Screen)

1. App-wide login (src/auth/login.jsx) → JWT stored in sessionStorage.token
2. Navigate to /sales/pos → ResourceGuard(module="sales.invoice") passes
3. POSSales.jsx mounts → "POS initialization" useEffect fires:
     a. GET /api/pos/settings → posSettings (+ template designer fields)
     b. GET branch tax configuration → tax-inclusive flag, VAT rate
     c. registerTerminalAndResumeSession():
          i.   read/create deviceFingerprint (localStorage)
          ii.  read cached terminalId for this branch (localStorage)
          iii. POST /api/pos/terminals/register {terminalId, deviceFingerprint, deviceInfo}
                 -> 403 if terminal BLOCKED/MAINTENANCE/DECOMMISSIONED/ARCHIVED (hard stop, UI blocked)
                 -> else ACTIVE or PENDING_REGISTRATION terminal returned; cache terminal.terminalId
          iv.  GET /api/pos/sessions/active?terminalId=
                 -> resumes existing OPEN session owned by currentUser()
                 -> 409 "Terminal is locked by active cashier" if a DIFFERENT user's session is open
                    (frontend offers Supervisor Takeover)
          v.   GET /api/pos/sessions/day-status?terminalId=
                 -> surfaces any prior-day unclosed session as a blocking popup
4. Independent effects fire in parallel: departments, customers (paginated), products
   (paginated, infinite scroll), printer config, scanner config (localStorage-persisted),
   held sales, X-report cache warm (if a session is already active)
5. useHeartbeat(terminalId) starts (60s interval); useIdleTimeout(sessionId) starts (30s touch)
6. If no active session resumed: Start Session dialog (denomination entry) ->
   POST /api/pos/sessions/open -> currentView = 'touch-screen'
   If an active session WAS resumed: currentView = 'touch-screen' directly, cart state
   re-derived from held sales / fresh cart (not restored from any server-side cart snapshot
   tied to the session itself — POS carts are client-local until checkout, except for
   explicitly "held" sales, which persist via PosHeldSale.cartJson).
7. POS Sales screen (POSTouchScreen or TradePOSTouchScreen) becomes usable.

Note step 3.iii/3.iv: the terminal is the pivot of the entire startup sequence — a user cannot reach a usable sales screen without a successfully registered terminal, and their session resume query is filtered by terminalId first, current user second. This ordering (terminal-then-user) is precisely what a User-Centric redesign would need to invert.

9. Business Rules Extracted

  1. One OPEN session per terminal, enforced at two levels: application atomic CAS on pos_terminals.current_open_session_id, and a DB partial unique index. — *terminal-scoped, not user-scoped.*
  2. A session's owner is whichever user was authenticated when openSession (or a reassignment) last ran — no independent "user's active session" registry exists; the only way to find "does user X have an open session" is to scan pos_sessions for opened_by = X AND status = OPEN, which is not how the system currently queries (it always queries by terminal first).
  3. A terminal can only be un-locked by closing its session, not by suspending it — auto-suspend on idle/timeout leaves the lock held.
  4. A user can resume their own OPEN session automatically (idempotent openSession) but is blocked from a *different* user's OPEN session on the same terminal (409, requires Supervisor Takeover).
  5. Session ownership can be reassigned without closing the session, but only within the same terminal (reassignSessionOwner, supervisorTakeover) — proves the domain already tolerates "owner != opener," just not "session moves across terminals."
  6. New session opens are blocked branch-wide (not terminal-scoped) if any prior-day session anywhere in the branch is still unclosed.
  7. New session opens are blocked if the branch's business day is already closed.
  8. Terminal identity is per-branch (device_fingerprint + branch_id composite) — the same physical device registers as a *different* logical terminal on a different branch; no cross-branch terminal continuity exists.
  9. Terminal archive/decommission is blocked while a session is open on it — session state gates terminal lifecycle, one direction only.
  10. Counter assignment has no exclusivity — multiple terminals may point at the same counter with no conflict check, unlike the strict one-terminal-one-session rule.
  11. Idle/hard-timeout auto-suspend never releases the terminal lock — only an explicit closeSession call does.
  12. No terminal-level authentication or credential exists — any authenticated user's browser can register/heartbeat any terminal string id it knows, with the only real gate being terminal *status* (not identity).
  13. Session's counter reference is a point-in-time denormalized snapshot from the terminal's counter at open time, not a live relationship — later counter reassignment on the terminal does not affect already-open sessions.
  14. Role-based gating is minimal — only Day Close hardcodes roles (SUPERVISOR/MANAGER/ADMIN); everything else uses fine-grained permission keys (terminal) or nothing at all (counter), with session operations relying on ownership checks rather than roles.

11. Risks for Migration to a User-Centric Session Model

These are architectural assumptions baked into the current implementation that a User-Centric ("session roams with the user, independent of which terminal they're physically at") design will have to explicitly confront — not proposed fixes, just the load-bearing facts a redesign must reckon with:

  1. The lock primitive is on the terminal, not the user. pos_terminals.current_open_session_id is the *only* mechanism preventing double-booking. There is no equivalent "does this user already have an open session (anywhere)" check today — openSession's duplicate-check query is findByBranchIdAndTerminalIdAndStatus, never findByOpenedByAndStatus. A user-centric model needs an analogous atomic lock keyed on the user, and must decide what happens to the *existing* terminal-lock column — remove it, repurpose it, or run both in parallel during a transition.
  1. Every lookup path is terminal-first. Startup (GET /sessions/active?terminalId=), the duplicate-open check, and the lock CAS all take terminalId as the primary key parameter. A roaming session model needs a *user-first* lookup (GET /sessions/active?userId= or equivalent) as a first-class, equally-supported path — today that query shape doesn't exist anywhere in PosSessionRepository.
  1. Idle/hard-timeout expiry suspends without releasing the terminal lock (§1.4/§2.3). If sessions become user-centric and no longer terminal-pinned, "suspend" semantics need to be revisited — today a suspended session still monopolizes a terminal, which may be exactly wrong (or exactly right, depending on intent) once a user can resume from a *different* terminal.
  1. Session ownership reassignment already exists but is single-terminal. reassignSessionOwner/supervisorTakeover prove the domain model already separates "who opened it" from "who owns it now" — this is a reusable pattern — but neither method, nor anything else found, changes terminalId/terminalPk on an existing session. Moving a session between terminals is an entirely new code path, not an extension of an existing one.
  1. Counter and terminal-hardware bindings (printer/scanner/drawer, hardware profiles) are terminal-scoped, not user-scoped. If a user roams between terminals mid-shift, their receipt printer, cash drawer, and hardware profile all change with them physically — the current schema has no concept of "this user's preferred/assigned hardware," only "this terminal's hardware." A roaming session doesn't automatically carry hardware context; that's a separate design problem the migration will surface.
  1. No terminal authentication exists (§2.6) — terminal identity today is trust-on-first-use via deviceFingerprint. If a user-centric model relies more heavily on "this session belongs to this user regardless of device," the *absence* of terminal auth actually reduces risk on that front (nothing to unwind) but means device/location context can't be trusted as a secondary signal without adding it.
  1. counterId/counterName on PosSession are a denormalized snapshot from the terminal, taken once at open time (§3.4). In a user-centric model where a session might not have a fixed terminal (and therefore not a fixed counter) for its whole lifetime, this snapshot-at-open pattern breaks down — counter becomes either meaningless, or something that needs to become a per-transaction attribute rather than a per-session one.
  1. Branch-wide (not terminal-scoped) blocking on stale prior-day sessions (§1.1 step 4, §9 rule 6) — this rule already operates at the branch level, which is closer to user-centric thinking than terminal-centric; it's one of the few existing behaviors that likely translates cleanly.
  1. opened_by/performedBy are raw username strings, not FKs to users.id (§4.4) — a user-centric redesign that wants strong referential guarantees (e.g., cascading on user deactivation, or querying "all sessions for user #123" reliably across a username change) will need to confirm whether username is ever mutable and, if so, decide whether to backfill a real FK.
  1. GL posting on session close is tied to the session record, not the user or terminal, and is fire-and-forget (try/catch swallows failure) — this dependency is largely orthogonal to the terminal-vs-user question and likely carries over unchanged, but is worth confirming doesn't implicitly assume "one terminal, one till" bookkeeping anywhere in PostingEngineService.createJournalFromSessionClose (not read in this pass — flagged for follow-up before migration).
  1. Day Close (closeDay) reconciliation aggregates by branch+date across all sessions, already user/terminal-agnostic in its math — this is another piece of existing logic that likely needs little to no change for a user-centric model, since it never assumed one-session-per-user or one-session-per-terminal in its reconciliation formulas.
  1. No existing test coverage for cross-terminal session behavior was located in this pass (not exhaustively searched — PosSessionServiceTest.java exists per the repo's test tree but its contents weren't read here) — before migration work begins, worth confirming what the current test suite assumes about the terminal-session relationship, since those tests will need conscious updating rather than incidental breakage.
